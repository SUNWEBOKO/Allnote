## 1 为什么需要一个"不能被创建"的基类

第 15 章的例子是这样一个结构：基类 `animal` 有一个虚函数 `speak`，派生类 `dog`、`cat` 各自重写它。这个代码目前有个小问题——`animal` 对象是被允许创建的：

```cpp
animal a;
a.speak();      // 输出 "animal says something"
```

从语法上讲这行代码完全合法，但从语义上讲它没有意义。"动物"是一个抽象概念，不是一个具体的物种：没有一种通用的动物，因此也不存在"动物的叫声"。真实世界里会叫的只有狗、猫这些具体的动物；在这套类型里，我们真正关心的也只有 `dog`、`cat` 这些派生类。

更麻烦的是，这样的代码能编过就说明**程序员可能真的写出它**——也许是无意中漏了初始化，也许是把某个派生类对象切片了（第 15 章说过按值赋给基类会切片）。与其等运行时看到一个莫名其妙的基类输出，不如让这种对象根本创建不出来。

这就是抽象类要解决的问题：**用一个类只定义接口，并禁止它被实例化。**

## 2 纯虚函数与抽象类

### 2.1 写法

把虚函数的函数体删掉，在函数头的末尾写 `= 0`：

```cpp
struct animal
{
    virtual void speak() = 0;
};
```

这一行包含两个信息：

- `virtual` 和第 15 章一样，表示"这个函数可以被派生类重写，通过基类引用调用时按实际类型选择"；
- `= 0` 表示**本类不实现这个函数**，只声明它的存在。这样的函数叫**纯虚函数**（pure virtual function），那个 `= 0` 读作"赋值为零"。

注意纯虚函数的写法里没有函数体：`= 0;` 就是它的全部。派生类必须给出自己的实现：

```cpp
struct dog : animal
{
    void speak() override
    {
        std::cout << "dog says woof" << std::endl;
    }
};
```

### 2.2 什么类算抽象类

规则只有一条：**一个类里只要存在（或继承到）至少一个尚未被最终重写的纯虚函数，它就是抽象类。**抽象类不能被实例化——不能声明这种类型的变量，也不能用 `new` 创建这种类型的对象。

"（或继承到）"这几个字很关键，因为抽象性会**沿着继承链往下传**：

```cpp
struct animal
{
    virtual void speak() = 0;
};

struct mammal : animal        // 继承了 animal，但没有实现 speak
{
    void walk()
    {
        std::cout << "mammal walks on four legs" << std::endl;
    }
};

struct dog : mammal           // 到这一层才把 speak 补上
{
    void speak() override
    {
        std::cout << "dog says woof" << std::endl;
    }
};
```

在这段代码里，`mammal` 仍然是抽象类（`speak` 还欠着），只有 `dog` 才是可以创建对象的**具体类**。也就是说，一个类要变成具体类，必须把继承链上所有纯虚函数都实现掉；中间层可以只补充自己的东西（例如 `walk`），把纯虚函数继续留给下游。

这里还要说清一个顺带的好处：`mammal` 虽然抽象，但它提供的 `walk` 会被 `dog` 和 `cat` 一起继承。**接口的顶层负责规定"必须做什么"，中间层负责"补充所有下游都能用的东西"，具体类负责"把没实现的都实现掉"。**

### 2.3 抽象基类这个叫法

抽象类在英文里常写成 abstract base class（抽象基类）——因为它几乎总是被当作基类使用：自己不做对象，只给一族派生类提供统一的接口与共享的成员。本章后面就统一叫它抽象基类。

## 3 抽象类能做什么、不能做什么

先把边界划清楚，很多误用都来自搞混这两栏：

| 想做的事 | 抽象类行不行 | 说明 |
| --- | --- | --- |
| 声明这种类型的变量 `animal a;` | 不行 | 实例化被禁止 |
| `new animal` | 不行 | 同上，报 `invalid new-expression of abstract class type 'animal'` |
| 作为函数形参的类型（按值） | 不行 | 按值传参需要能创建对象，报 `cannot declare parameter 's' to be of abstract type 'shape'` |
| 作为函数形参的类型（引用或指针） | 可以 | 引用和指针不创建对象，只是"看待"已有的对象 |
| 定义这种类型的引用、指针变量 | 可以 | 同上，这是多态的标准用法 |
| 被继承 | 可以 | 这正是它的用途 |
| 作为容器元素类型 | 不行（直接放对象） | `std::vector<shape>` 无法工作；装 `shape*` 或 `unique_ptr<shape>` 才行 |
| 调用它自己的虚函数（有实现的那些） | 可以 | 抽象类里除了纯虚函数，仍然可以有普通成员函数和数据成员 |

这里补一句边界提醒：表格里说的装 `shape*` 或 `unique_ptr<shape>` 只是让容器**指向**派生对象，真正要小心的是**通过基类指针析构**。第 15 章讲过，用基类指针 `delete` 派生对象时，基类必须有虚析构函数，否则只调用基类析构、派生类那部分不会被清理，属于未定义行为。所以一个打算这样管理的抽象基类应当补上 `virtual ~shape() = default;`；本章例程里指针只指向栈上对象、不做 `delete`，因此没有写这一句。

一句话总结：**抽象类禁止的是"创建对象"，不禁止"被当作接口使用"。**它的价值恰恰在于后半句——

```cpp
// 这个函数只认识 shape 接口：name 和 area 怎么算，它不关心，也不需要知道
void show(const shape& s)
{
    std::cout << s.name() << ": area = " << s.area() << std::endl;
}
```

写 `show` 的人只需要知道接口存在；写 `square`、`circle` 的人只需要把接口实现出来。两边的开发可以完全独立：新增一种形状时，`show` 一行都不用改。

## 4 一个边界：纯虚函数也可以有函数体

`= 0` 的意思是"这个类不提供实现，派生类必须重写"，标准并不禁止你再额外给一份默认实现，只是这份实现必须写在**类外**：

```cpp
struct shape
{
    virtual void hello() = 0;
};

// 类外定义：这样的默认实现给派生类复用
void shape::hello()
{
    std::cout << "shape says hello" << std::endl;
}

struct circle : shape
{
    void hello() override
    {
        std::cout << "circle says hello" << std::endl;
        shape::hello();     // 用限定名才能取到基类那份实现
    }
};
```

三点要注意：

- 类内写成 `virtual void hello() = 0 { }` 是非法的，会报 `error: pure-specifier on function-definition`。`= 0;` 和函数体不能在类内同时出现。
- `shape` 依然是抽象类，依然不能创建对象。
- 想用到这份函数体，必须用限定名 `shape::hello()`（第 15 章讲过限定调用会绕过动态绑定）；直接写 `hello();` 会一直解析到自己，变成无限递归。

这份"默认实现"的用途是给派生类省掉重复代码：某个派生类如果不想重新写一遍逻辑，可以在自己的重写函数里先调一次基类版本，再叠加自己需要的部分。如果基类没有任何可复用的东西，那就不要写函数体。

## 5 什么该写成纯虚函数

把第 15 章的判断标准再往前一步：

- 基类**能给出一个合理默认实现**的函数 → 写成普通虚函数（第 15 章的做法），派生类按需重写。
- 基类**给不出任何有意义的默认实现**的函数 → 写成纯虚函数，逼派生类必须实现，同时把基类变成抽象类，禁止无意义的实例化。

"动物叫"属于第二种：没有一个能被所有动物共享的叫声。而"打印自己的信息""返回自己的名字"这类也一样——只有具体类型才知道答案。

两种函数可以在同一个基类里混用。例如一个图形基类可以有纯虚的 `area()`（每个图形算法都不同，没有默认实现），同时有带实现的普通虚函数 `describe()`（默认打印名字和面积，个别图形想改再重写）。**判断的依据始终是：这一层有没有一个说得通的默认行为。**

到这里，接口这一侧的故事讲完了：抽象基类规定"必须做什么"，具体派生类负责实现。接下来把视角从接口转向继承结构本身——当同一个基类经过多条路径被继承到同一个类里时，对象内部会出现什么，又该如何用虚继承解决。

## 6 从多层继承到菱形

第 15 章讲过继承在对象层面上到底意味着什么：写 `struct B : A` 之后，**一个 `B` 对象的内部包含一个 `A` 子对象**，`A` 的数据成员就存在这个子对象里，`B` 的构造函数在进入自己的函数体之前先把那个 `A` 子对象构造好。第 15 章又讲过，正因为存在这个子对象，`B*` 才能转成 `A*`、`B&` 才能绑定到 `A&`，运行时的虚函数调用才能顺着这个子对象找到正确的实现。

本章讨论的是把这套机制用在**多层、多路径**继承上会出现的麻烦。看下面这个层次：

```text
        A            共同基类
      /   \
     B     C         B 与 C 都从 A 派生
      \   /
        D            最派生类，同时从 B 和 C 派生
```

写成代码就是：

```cpp
struct A {};
struct B : A {};
struct C : A {};
struct D : B, C {};      // 一份 B、一份 C，两份 A
```

因为 `B` 里有 `A`、`C` 里也有 `A`，而 `D` 同时包含一个 `B` 子对象和一个 `C` 子对象，于是 **`D` 里出现了两个 `A` 子对象**：一个藏在 `B` 里面，一个藏在 `C` 里面。形状像个菱形，这个结构就叫菱形继承，它带来的问题叫菱形继承问题。

需要说明的是，`A` 被继承两次并不是编译器出错，而是"以子对象方式复用基类"这条规则的直接结果：规则说 `B` 里有一个 `A`，规则也说 `C` 里有一个 `A`，规则还说 `D` 里有 `B` 和 `C`，三条规则合起来就是两个 `A`。

## 7 重复的基类子对象带来什么

例程 `E:\CPP_Code\CppFromScratch\ch37_virtual_inheritance\diamond_constructors\diamond_constructors.cpp` 把上一节的骨架补成可运行的程序：`A`、`B`、`C`、`D` 的构造函数各打印一行自己的名字，`A` 里放一个数据成员 `value`，`main` 中创建一个 `D` 对象。

### 7.1 构造顺序与两次构造

运行结果的第一段：

```text
=== Demo A: construction order of a non-virtual diamond ===
A::A()
B::B()
A::A()
C::C()
D::D()
```

构造顺序有明确的规则：**先构造基类子对象（多个直接基类按声明顺序，从左到右），再执行自己的构造函数体**。这里 `D : B, C` 的声明顺序是 `B` 在前，所以先构造 `B`；而构造 `B` 之前又要先构造它的 `A` 子对象，于是先打印 `A::A()` 再打印 `B::B()`。轮到 `C` 时同理，它自己那个 `A` 子对象也要构造一次，于是屏幕上出现了第二次 `A::A()`。最后才是 `D::D()`。

这行输出就是菱形继承问题最直接的证据：**`A` 的构造函数跑了两次，说明对象里有不止一份 `A` 的数据**。

### 7.2 同一份数据存了两份

`D` 里既然有两个 `A` 子对象，`A` 的数据成员自然也就有两份。例程的第二段用限定名 `B::` 和 `C::` 分别指定要访问哪一个：

```cpp
d.B::value = 10;
d.C::value = 20;

std::cout << "d.B::value = " << d.B::value << std::endl;
std::cout << "d.C::value = " << d.C::value << std::endl;
```

输出是：

```text
=== Demo B: D contains two separate A subobjects ===
d.B::value = 10
d.C::value = 20
```

写进去两个不同的值，读出来还是两个不同的值——**这是两个完全独立的存储位置，不是同一个东西的两种叫法**。这就是"重复继承"的实际含义：你以为是同一个 `A`，程序里其实是两个。

顺带看一眼大小：

```text
=== Demo C: sizes ===
sizeof(A) = 4
sizeof(B) = 4
sizeof(C) = 4
sizeof(D) = 8
```

`sizeof(B)` 和 `sizeof(A)` 一样，说明只含一个 `A` 子对象的 `B` 没有额外开销；而 `sizeof(D)` 是 8，正好是 `B` 与 `C` 拼在一起的大小，`A` 的那 4 字节数据确实存了两遍。数据成员越多，浪费越大。

### 7.3 二义性：编译器不会替你猜

两个子对象带来了第二个问题：**不带限定的访问会变模糊**。如果写 `d.value`，编译器看到两个候选，无法判断你要哪一个，于是拒绝编译：

```text
error: request for member 'value' is ambiguous
```

向上转型同样失败——`A& a = d;` 会得到：

```text
error: 'A' is an ambiguous base of 'D'
```

这条错误的影响比表面看起来严重。第 15 章讲过，多态调用要靠基类的引用或指针：把派生类对象交给一个只认 `A&` 的函数，函数里再调用 `A` 的成员函数，运行时会走到派生类的实现。只要 `D` 无法转成 `A&` 或 `A*`，`D` 就没法参与这套以 `A` 为接口的多态协作，`A` 里定义的接口对最派生类也就形同废纸。

编译器为什么不选一个？因为选择权在语义上真的不明确：两个 `A` 子对象可以带着不同的值（上一段实验就是 `10` 和 `20`），随便挑一个都会让状态分裂——通过一条路径改动的数据，另一条路径看不到。与其制造难以发现的错误，不如在编译期就报错。这是编译器处理"意图不明确"的一贯做法。

## 8 用虚继承解决

问题的根源是"同一个基类在继承链上被算作了多个子对象"。既然规则可以描述这种重复，规则当然也可以描述"不要重复"：**把共同基类声明为虚基类**，方法是继承时在基类名前写 `virtual`。

```cpp
struct A
{
    A() { std::cout << "A::A()" << std::endl; }
    int value = 1;
};

struct B : virtual A      // A 是 B 的虚基类
{
    B() { std::cout << "B::B()" << std::endl; }
};

struct C : virtual A      // A 也是 C 的虚基类
{
    C() { std::cout << "C::C()" << std::endl; }
};

struct D : B, C           // D 中只保留一个 A 子对象
{
    D() { std::cout << "D::D()" << std::endl; }
};
```

标准对虚基类的规定是：**对于每个被声明为虚的基类，最派生类中只包含该类型的一个基类子对象**。不管从多少条路径继承到 `A`，只要这些路径上 `A` 都是虚基类，整个对象里就只有一份 `A`。

例程 `ch37_virtual_inheritance\virtual_base\virtual_base.cpp` 就是上一份例程只改了这两处 `virtual` 的版本。运行结果：

```text
=== Demo A: A is constructed only once ===
A::A()
B::B()
C::C()
D::D()
=== Demo B: one shared A subobject ===
settings.value = 42
=== Demo C: sizes ===
sizeof(A) = 4
sizeof(B) = 16
sizeof(C) = 16
sizeof(D) = 24
```

三点变化值得逐条对照：

1. **`A::A()` 只打印了一次。** 构造顺序仍然是"先基类后自身"，但 `A` 这个虚基类在最派生类中只有一个子对象，所以只构造一次，之后 `B::B()`、`C::C()`、`D::D()` 依次执行。屏幕上正好四行。
2. **共享是真正的共享，不是复制。** 例程里写了 `A& a = d;` 让引用绑定到那个唯一的 `A` 子对象上，再通过 `a.value = 42` 修改它，然后直接读 `d.value` 得到 `42`。能这么写，说明向上转型成功了，而且两条路径看到的是同一份数据——不再需要 `B::`、`C::` 这类限定名。
3. **代价出现了。** `sizeof(B)` 从 4 变成 16、`sizeof(D)` 从 8 变成 24。这份增长不是为了存数据，而是为了在运行时能定位那个被共享的子对象（具体数字取决于平台与编译器实现，本机是 MSYS2 UCRT64 / x86-64）。

## 9 配套规则与开销

虚继承不只是"加个关键字"，它同时改变了初始化规则和访问成本。

### 9.1 虚基类由最派生类初始化

既然整个对象里只有一个 `A` 子对象，那么它就只能被初始化一次；而多个派生类各自的构造函数都"想"初始化它，冲突不可避免。标准的处理方式是把这份责任交给最派生类：

> 虚基类的初始化由最派生类的构造函数负责；在继承链中间那些派生类的构造函数里写的初始化器，在作为最派生类构造时被忽略。

例程 `ch37_virtual_inheritance\virtual_base_init\virtual_base_init.cpp` 让这条规则留下可见的证据：`A` 只有一个带参数的构造函数 `explicit A(int id)`，它把参数存进 `value` 并打印出来；`B` 的初始化列表里写 `A(1)`，`C` 里写 `A(2)`，而 `D` 写 `A(99)`：

```cpp
struct D : B, C
{
    D() : A(99), B(1), C(2)
    {
        std::cout << "D::D()" << std::endl;
    }
};
```

运行结果：

```text
=== Who initializes the virtual base? ===
A::A(99)
B::B(1)
C::C(2)
D::D()
final value of A::value = 99
B(1) and C(2) were ignored: B passes 1, C passes 2
```

`A` 收到的是 `99`，也就是 `D` 给出的参数；`B` 里的 `A(1)`、`C` 里的 `A(2)` 都没有生效。这里还有一个写代码时要注意的细节：初始化列表里应当按"先虚基类、再直接基类"的真实顺序书写，也就是 `D() : A(99), B(1), C(2)`。写成 `B(1), C(2), A(99)` 也能编译，但顺序与真实初始化顺序不一致，`-Wall` 会给出 `-Wreorder` 警告。

如果 `A` 没有默认构造函数而最派生类又忘了初始化它，程序根本编译不过：

```text
error: no matching function for call to 'A::A()'
error: use of deleted function 'D::D()'
```

第二行是第一行的连带结果：`D` 的隐式默认构造函数因为无法初始化虚基类而被删除，接着 `main` 里那句 `D d;` 就找不到可用的构造函数了。

### 9.2 `virtual` 必须在每个直接派生处都写

虚基类的身份来自**声明 A 为虚基类的那些派生语句**，它不是一种会被自动继承下去的属性。如果 `B` 写了 `virtual` 而 `C` 没写，`D : B, C` 里仍然会有两个 `A` 子对象——`B` 那个是虚基类子对象，`C` 那个是普通的 `A` 子对象，不带限定的 `d.value` 依旧报 `error: request for member 'value' is ambiguous`。

也就是说，菱形里"把共同基类设为虚基类"这件事要在**每一条直接继承它的语句**上分别写清楚；漏掉一处，问题就回来了。

### 9.3 空间与访问成本

已经看到 `sizeof` 的变化，代价具体落在两处：

- **每个含虚基类的派生类对象里要存放定位信息**（通常是指向虚基类子对象的偏移，或者一张表），所以对象变大，并且可能出现额外的填充字节。
- **访问虚基类的成员要多一层间接寻址**。普通继承时子对象的偏移在编译期就定死了，访问就是"对象地址 + 固定偏移"；虚继承下偏移取决于运行时真正的对象类型（同一个 `B` 子对象可能是独立的 `B` 对象，也可能是 `D` 的一部分），编译器不能把偏移写死。
- **构造函数与析构函数的逻辑变复杂**，因为要判断本次构造中"我是不是最派生类"：是，就要初始化虚基类；不是（比如在构造 `D` 的过程中构造 `B` 子对象），就要跳过虚基类的初始化。

所以虚继承是"为了解决重复子对象而付的费"，不是免费的语法糖。

### 9.4 `virtual` 继承与 `virtual` 函数不是一回事

第 15 章的虚函数也用了 `virtual` 这个关键字，但两处的含义完全不同：

- 在成员函数前写 `virtual`，说的是"这个函数参与运行时动态绑定"，解决的是**调用哪个实现**的问题。
- 在基类名前写 `virtual`，说的是"这个基类在最派生类中只保留一个子对象"，解决的是**数据存放几份**的问题。

它们可以同时出现在一个继承层次里，也可以互不相干。读代码时看 `virtual` 后面跟的是"基类名"还是"函数声明"，就能分辨。

## 10 标准库里的菱形继承

菱形继承不是构造出来的场景，标准库自己的输入输出体系就是这样一个层次：

```text
                basic_ios
              /          \
      basic_istream    basic_ostream
              \          /
             basic_iostream
```

在 libstdc++ 的头文件里，这三处继承写成（尖括号里的 `<_CharT, _Traits>` 是类模板实例化语法，第 17 章展开）：

```cpp
class basic_istream : virtual public basic_ios<_CharT, _Traits>
class basic_ostream : virtual public basic_ios<_CharT, _Traits>
class basic_iostream
    : public basic_istream<_CharT, _Traits>,
      public basic_ostream<_CharT, _Traits>
```

`basic_ios` 保存的是流的状态（缓冲区、格式标志、错误状态等）。`basic_iostream` 同时继承输入流和输出流，如果 `basic_ios` 不是虚基类，它就会在 `basic_iostream` 里有**两个不同的子对象**：往输出侧写的格式标志、设置的错误状态，输入侧看不到，读写行为会各说各话。用虚继承之后只有一个 `basic_ios` 子对象，输入输出两侧共享同一份状态。

这就是从第 01 章开始一直在用的 `std::cout`、`std::cin` 所属的体系，也是文件流 `fstream`、字符串流 `stringstream` 的结构基础。可以说，**"两套接口共用一份状态"这件事，标准库本身就是靠虚继承实现的**。

## 11 什么时候该用虚继承

判断标准可以归成两条，两条同时成立才用：

1. 继承层次里**真的存在菱形**：同一个基类通过多条路径被继承到了同一个最派生类里。
2. 那个基类的子对象在语义上**必须唯一**：它承载的是"整条继承链共享的一份状态"，而不是"每个分支各自一份"。

两条只满足一条就不该用。只有一个层次的单继承、或者没有共同基类、又或者那个共同基类每次都确实希望各存一份数据（例如每个分支各自记录自己的日志信息），普通继承更简单、对象更小、访问更快。"预防性地到处加 `virtual`"只会让每个对象变大、每次访问变慢，而且把初始化职责搞得复杂。

还有一条常见做法可以避免动用虚继承：如果两个分支只是希望共用**接口**而不需要共用**数据**，就不要让它们继承同一个带数据成员的基类，而用一个不含状态的抽象类（本章第 2、3 节介绍的抽象基类）作为接口，状态放在最派生类里。共享状态与共享接口是两件事，虚继承解决的是前者。

### 12.1 实验一：纯虚函数把基类变成抽象类

`E:\CPP_Code\CppFromScratch\ch34_abstract_classes\abstract_basic\abstract_basic.cpp` 里 `animal::speak` 是纯虚函数，`dog`、`cat` 实现它，`main` 里只创建派生类对象，再向上转型成 `animal&` 调用。

**预期输出**：

```text

cat says meow
=== Demo B: an animal& can still refer to them ===

cat says meow
```

**验收标准**：两个 Demo 都输出派生类行为；代码里没有出现过 `animal` 类型的对象；编译 `-Wall` 无警告。

**改值实验**：在 `main` 里加一句 `animal a;` 再编译，应当看到编译失败：

```text
error: cannot declare variable 'a' to be of abstract type 'animal'
note: because the following virtual functions are pure within 'animal':
      'virtual void animal::speak()'
```

确认"抽象类不能创建对象"是编译期拦住的行为，看完把这句删掉。再做一次相反的实验：把 `animal::speak` 的 `= 0;` 换成一个正常函数体（即退回第 15 章的虚函数基类），`animal a;` 就能编译了，`a.speak()` 输出基类文字——这直接说明抽象性**只来自那一个纯虚函数**。

### 12.2 实验二：抽象性沿继承链传递

`E:\CPP_Code\CppFromScratch\ch34_abstract_classes\abstract_chain\abstract_chain.cpp` 里 `animal`（纯虚 `speak`）→ `mammal`（补上 `walk`，没实现 `speak`）→ `dog`、`cat`（实现 `speak`）。`main` 里用 `mammal&` 和 `animal&` 分别调用。

**预期输出**：

```text
=== Demo A: dog and cat are concrete classes ===
dog says woof
cat says meow
=== Demo B: an abstract mammal& still works ===
mammal walks on four legs
dog says woof
mammal walks on four legs
cat says meow
=== Demo C: so does an abstract animal& ===
dog says woof
```

**验收标准**：Demo B 里 `walk` 输出的是 `mammal` 提供的文字（它被两个派生类共享），而 `speak` 输出的是各自派生类的实现；编译 `-Wall` 无警告。

**改值实验**：给 `dog` 加一句 `mammal m;`，编译会失败并指出 `mammal` 是抽象类型（因为 `speak` 没实现）。然后把纯虚函数这一环去掉——在 `mammal` 里补上 `void speak() override`，此时 `mammal m;` 可以编译，`m` 的 `speak` 走 `mammal` 版本。这验证了"哪一层实现了纯虚函数，哪一层才变成具体类"。

### 12.3 实验三：把接口当作契约来使用

`E:\CPP_Code\CppFromScratch\ch34_abstract_classes\abstract_interface\abstract_interface.cpp` 里 `shape` 有三个纯虚函数（`name`、`area`、`hello`），其中 `hello` 在类外还给了默认实现；`main` 用一个只认识 `shape` 的函数 `show` 处理两种形状，并把它们放进 `std::vector<shape*>` 统一遍历。

**预期输出**：

```text
=== Demo A: a function that only knows the interface ===
square: area = 9
circle: area = 12.5664
=== Demo B: a group of shapes behind the interface ===
square: area = 9
circle: area = 12.5664
=== Demo C: a pure virtual function may still have a body ===
square says hello
circle says hello
shape says hello
shape says hello
```

**验收标准**：`show` 的形参是 `const shape&`（不是 `shape`，也不是 `shape*` 之外的方案），Demo A 与 Demo B 输出完全一致；Demo C 最后两行分别来自 `circle::hello` 里的限定调用和 `main` 里的 `sq.shape::hello()`；编译 `-Wall` 无警告。

**改值实验**：新增一个派生类 `rectangle`，把三个纯虚函数都实现掉（`name` 返回 `"rectangle"`，`area` 返回 `w * h`，`hello` 按需重写），再在 `main` 里创建它、往 Demo B 的 `vector` 里加一句 `push_back`。除了新增这个类和这一句 `push_back`，`show` 和循环体一个字都不用改，输出会多出一行 `rectangle: area = ...`。注意：如果只实现了 `name` 和 `area` 而漏掉 `hello`，编译在 `rectangle r;` 这一行就会失败，仍然报 `cannot declare variable 'r' to be of abstract type 'rectangle'`——**纯虚函数必须全部实现，少一个都不行**。然后再把 `show` 的形参改成按值 `void show(shape s)`，编译会失败：`error: cannot declare parameter 's' to be of abstract type 'shape'`——抽象类不能按值传递，这从另一个角度证明了"多态必须靠引用或指针"。
