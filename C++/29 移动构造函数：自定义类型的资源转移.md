# 29 移动构造函数：自定义类型的资源转移

## 学习目标

完成本章后，你应当能够：

1. 写出一个自定义类型的移动构造函数，并说明参数为什么写成 `T&&` 且不能加 `const`。
2. 说出什么情况下编译器不会隐式声明移动构造函数，以及为什么写了 `std::move` 却仍然发生复制。
3. 说出把移动构造函数写成 `noexcept` 的意义，以及不写时 `vector` 会怎么处理。
4. 说明移动构造函数执行完后源对象处于什么状态、哪些操作仍然合法。
5. 判断一段代码里的 `push_back` 会走复制还是移动，并说出理由。

## 1 从"知道要移动"到"自己写移动"

第 28 章讲了移动语义的三件事：怎么区分左值和右值、`std::move` 只是把值类别改成右值、移动之后的源对象处于"有效但未指定"的状态。也演示了 `unique_ptr` 被移动时会发生什么——但那是标准库类型，它的移动构造函数是别人写好的。

本章补上缺的那一块：**我们自己的类型，移动构造函数得自己写。** 编写这个函数最常出现的场景就是容器，因为容器天生要做一件事：把外面造好的对象收进来。

具体来说有两个理由让它必须发生：

- **有些类型根本不能复制。** `std::unique_ptr` 的拷贝构造函数被标准库标成了 `= delete`：它的语义是"独占所有权"，一旦允许复制，立刻就有两个指针认为自己独占同一块内存，两边都会去释放它（第 25 章讲的双释放就是这个后果）。这类类型**只能被移动**。
- **有些类型复制得起，但不划算。** 一个装着几百万个元素的容器，复制它要把每个元素都拷一遍，时间和内存都翻倍；而复制出来的那一份往往只用一次就丢掉。这一步拷贝是白花的。

要真正把这件事做对，光有第 28 章的 `std::move` 是不够的——`std::move` 只是"允许搬走"的一句话，**真正动手搬的是移动构造函数**。下面先看清"没有它的时候到底发生了什么"。

## 2 没有移动构造函数时会怎样

例程 `E:\CPP_Code\CppFromScratch\ch29_move_constructor\move_constructor_basic\move_constructor_basic.cpp` 里的类型故意让每条构造路径都打印一行，这样每次发生的是复制还是移动，从输出里就能直接看出来（节选，注释略）：

```cpp
struct S
{
    int value = 0;

    explicit S(int new_value = 0) : value(new_value)
    {
        std::cout << "Constructor! value = " << value << std::endl;
    }

    S(const S& other) : value(other.value)
    {
        std::cout << "Copy Constructor! value = " << value << std::endl;
    }

    S(S&& other) noexcept : value(0)
    {
        std::swap(value, other.value);
        std::cout << "Move Constructor! value = " << value << std::endl;
    }
};
```

`main` 里对三种写法各调用一次 `push_back`：

```cpp
std::vector<S> v1;
S s(10);
v1.push_back(s);              // 有名字的左值
```

`vector::push_back` 有两个重载，它们的分工是：

| 重载 | 参数类型 | 做的事 |
| --- | --- | --- |
| `push_back(const T& value)` | `const` 左值引用 | 把 `value` **复制**成新元素（第 14 章用的就是这个） |
| `push_back(T&& value)` | 右值引用 | 把 `value` 的资源**搬**进新元素 |

`s` 是有名字的变量，是左值，只能绑定到第一个重载，所以结果是复制。输出两行也正好对应两块内存：

```text
Constructor! value = 10
Copy Constructor! value = 10
```

第一行是 `main` 里那个 `s` 被构造出来，第二行是在 `vector` 的内存里构造出一个副本。

### 2.1 只加 `std::move` 并不能让它移动

按第 28 章的规则，给 `s` 套上 `std::move` 就应该走移动了。可是把例程改成下面这样，结果仍然是复制：

```cpp
std::vector<S> v2;
S t(20);
v2.push_back(std::move(t));   // 期望移动，实际仍然复制
```

原因不在 `std::move`，而在 `S` **根本没有移动构造函数**：`S` 里只写了普通构造函数和拷贝构造函数，没有 `S(S&&)`。`std::move(t)` 把一个右值交给了 `push_back`，`push_back(T&&)` 也确实被选中了，但它内部需要"用一个右值构造 `S`"，而此时**唯一能做到这件事的就是拷贝构造函数**（`const S&` 可以绑定右值），于是还是复制。

这里有一条必须记住的规则：

> **移动构造函数不会被隐式声明的条件：** 只要**拷贝构造函数、拷贝赋值运算符、移动赋值运算符、析构函数**这四者中有任意一个被用户声明过，编译器就**不**再隐式声明移动构造函数。

例程里的 `S` 用户声明了拷贝构造函数，正好落在第一条上。所以它从一开始就没有移动构造函数，`std::move` 只是让值类别变成右值，而**没有移动构造函数可用的右值只能退回复制**——这也再次印证了第 28 章那句话：`std::move` 不是强制命令。

## 3 移动构造函数长什么样

移动构造函数的形状和拷贝构造函数几乎一样，只有两处不同：

```cpp
S(const S& other);            // 拷贝构造函数：const 左值引用，只能读
S(S&& other) noexcept;        // 移动构造函数：右值引用，可以改
```

两处差别都有原因：

- **参数是 `S&&`（右值引用）。** 只有写成右值引用，这个函数才会在"实参是右值"时被优先选中；写成别的形式（例如 `S&`）就无法与拷贝构造函数形成一个清晰的"复制 / 移动"分工。
- **不能用 `const`。** 移动的本质就是把参数手里的东西搬到自己身上，这必然要修改参数（把它清空）。如果参数是 `const S&&`，函数体里就动不了它，移动也就无从谈起。这也是"移动之后源对象的值不再有意义"这条规则的另一面。

至于函数体里"搬"这个动作怎么实现，取决于这个类型持有的是什么。

**成员本身是"值"**（`int`、`double` 之类）时，搬与抄的代价一样，直接用 `std::swap` 把值换过来即可，例程 `move_constructor_basic` 用的就是这个写法：

```cpp
S(S&& other) noexcept : value(0)     // 先把新对象初始化为"空"值 0
{
    std::swap(value, other.value);   // 再把值换到自己身上，参数拿到的就是 0
}
```

这样写完之后，新对象拿到了对方的值，对方留下一个明确的"空"值，而不是一个不可预料的值。

**成员是资源**（裸指针、`unique_ptr`、容器、字符串等）时，应该把成员**移动构造**过来，而不是复制。这时候要在成员初始化列表里对成员用 `std::move`：

```cpp
int_buffer(int_buffer&& other) noexcept
    : data(std::move(other.data)), length(other.length)   // 接管对方的指针
{
    other.length = 0;                                     // 源对象进入"空但完好"的状态
}
```

**这里有个容易被忽略的坑：成员初始化列表里忘写 `std::move`，成员就会被复制。** 因为形参 `other` 虽然是个右值引用，但 `other` 这个**名字**本身是左值（第 28 章 4 节讲过"有名字的右值引用是左值"），不加 `std::move`，编译器就按"用一个左值初始化成员"处理，于是老老实实复制一份。结果就是：移动构造函数写是写了，资源却照抄了一遍，一点都没省。

最后是 `noexcept`。它出现在函数声明的末尾，含义是"这个函数承诺不抛异常"。移动构造函数该加它的理由是**容器要知道这件事**：`vector` 扩容时要把已有元素搬到新内存，如果搬的过程中抛了异常，旧内存里的元素已经被改动过，容器无法保证"要么全成、要么原样"（强异常安全）。所以库的规则是：**只有当元素的移动构造函数是 `noexcept` 时，`vector` 才敢用移动来搬元素；否则它退回去用复制**，因为复制只读源对象，出错时源对象还是完好的。加了 `noexcept` 而函数体里又真的抛异常，程序会直接 `std::terminate`，所以这个承诺必须是真的——对"交接指针"这类操作来说，它确实是。

> 除了移动构造函数，还有一个配套的**移动赋值运算符** `S& operator=(S&& other)`，它管的是"已存在的对象接手别人的资源"。规则与移动构造函数完全平行（第 27 章讲过运算符重载，写法可以直接类推），本章只讲构造函数，两者通常一起实现。

## 4 实现之后再运行：三条添加路径

补上移动构造函数之后，同样三种写法就分化成了三条路径：

| 写法 | 实参的值类别 | 选中的 `push_back` 重载 | 实际发生 |
| --- | --- | --- | --- |
| `v1.push_back(s)` | 左值 | `push_back(const S&)` | 拷贝构造函数 |
| `v2.push_back(std::move(t))` | 右值（`std::move` 转换而来） | `push_back(S&&)` | 移动构造函数 |
| `v3.push_back(S(30))` | 右值（无名临时对象） | `push_back(S&&)` | 移动构造函数 |

例程 `move_constructor_basic` 的完整输出把三条路径依次摆在了一起：

```text
=== Demo A: push_back with a named lvalue copies ===
Constructor! value = 10
Copy Constructor! value = 10
=== Demo B: std::move turns the same lvalue into an rvalue ===
Constructor! value = 20
Move Constructor! value = 20
t.value after the move: 0
=== Demo C: a temporary object is moved without std::move ===
Constructor! value = 30
Move Constructor! value = 30
=== Demo D: the three vectors really own their elements ===
v1[0].value = 10
v2[0].value = 20
v3[0].value = 30
```

逐段读：

- **Demo A** 是"不得不复制"的情形：`s` 后面可能还要用，编译器不会擅自把它搬空。
- **Demo B** 与 Demo A 的唯一差别就是参数外面多了一层 `std::move`。输出从 `Copy Constructor!` 变成了 `Move Constructor!`，说明移动确实是"我们明确允许之后"才发生的。`t.value after the move: 0` 这一行则说明移动是有代价的：`t` 被清成了空值。这是我们自己写的 `std::swap` 决定的，**源对象留下的具体值由实现者自己选**（对标准库容器就不要假设它一定是空的）。
- **Demo C** 说明临时对象不用写 `std::move`：它没有名字，用完就没了，编译器直接按右值处理。第 28 章 6 节的实用规则在这里同样成立——**具名对象要搬走必须显式 `std::move`，函数返回的临时对象不必写**。
- **Demo D** 是收尾检查：三种写法的最终结果完全一样，`vector` 里各装着一个值正确的元素。**移动与复制的区别只在于"怎么构造出来的"，不在于"构造出来的东西有什么不同"。**

## 5 什么类型是可移动的，什么类型只能移动

前面那条"用户声明了拷贝构造就没有隐式移动构造"的规则，展开来一共有四种常见情形。例程 `E:\CPP_Code\CppFromScratch\ch29_move_constructor\implicit_move_rules\implicit_move_rules.cpp` 用一个"探针"成员把它们逐个验证了一遍：探针在被复制和被移动时各打印一行，并把自己的来历记在 `origin` 成员里。

```cpp
struct plain                   // 什么特殊成员函数都不声明
{
    tracked member;
};

struct with_copy               // 用户声明了拷贝构造函数
{
    tracked member;
    with_copy() = default;
    with_copy(const with_copy& other) : member(other.member) { }
};

struct move_only               // 用户声明了移动构造函数
{
    tracked member;
    move_only() = default;
    move_only(move_only&& other) noexcept : member(std::move(other.member)) { }
};
```

运行结果：

```text
=== Demo A: no user-declared special member functions ===
plain: is_copy_constructible = true, is_nothrow_move_constructible = true
constructing p2 from std::move(p1):
    tracked: default constructor
    tracked: move constructor
    p2.member.origin = move
=== Demo B: a user-declared copy constructor suppresses the move constructor ===
with_copy: is_copy_constructible = true, is_nothrow_move_constructible = false
constructing w2 from std::move(w1):
    tracked: default constructor
    tracked: copy constructor
    w2.member.origin = copy
=== Demo C: a user-declared move constructor deletes the copy constructor ===
move_only: is_copy_constructible = false, is_nothrow_move_constructible = true
constructing m2 from std::move(m1):
    tracked: default constructor
    tracked: move constructor
    m2.member.origin = move
```

三种类型，三段输出，可以得到三条结论：

1. **`plain`：什么都不声明，编译器全都给你。** 隐式声明的移动构造函数会逐个成员地移动，并且会继承成员的 `noexcept` 性质（探针的移动构造是 `noexcept`，所以 `plain` 也是），因此 `is_nothrow_move_constructible` 为 `true`。这也是"默认情况下类型就是可移动的"的原因。
2. **`with_copy`：声明了拷贝构造，移动构造就不生成。** 结果是 `std::move` 传进来的右值只能退回复制（输出里是 `tracked: copy constructor`），`is_nothrow_move_constructible` 变成了 `false`——因为退回用的那个拷贝构造函数并不保证不抛异常。同理，**用户声明析构函数**也会产生同样的后果（这是同一条规则里的第四项）：只要类型需要自定义清理动作，编译器就不再擅自生成移动构造函数。
3. **`move_only`：声明了移动构造，拷贝构造被定义为删除。** 于是 `is_copy_constructible` 变成 `false`，`move_only m3 = m1;` 直接编译失败，这个类型只能移动。独占所有权的类型正是这个形状。

这两个 traits（`std::is_copy_constructible_v`、`std::is_nothrow_move_constructible_v`）不是摆设：标准库内部就是用后者判断"能不能放心搬元素"的。看清这一点，也就看清了上一节 `noexcept` 为什么重要。

顺带说明一个易错点：`std::is_move_constructible_v<with_copy>` 是 `true`——**这不代表它真的能"移动"**，只代表"可以用一个右值把它构造出来"，而那一步实际走的是复制。判断"移动是否高效"要看 `is_nothrow_move_constructible`，判断"到底调用了哪个函数"只能看运行结果。

## 6 让移动真正搬走资源

上面例程用的成员是 `int`，搬和抄的代价一样，看不出差别。差别要在**持有堆内存**的类型上才看得到。例程 `E:\CPP_Code\CppFromScratch\ch29_move_constructor\move_constructor_resource\move_constructor_resource.cpp` 里的 `int_buffer` 持有一块动态分配的 `int` 数组，两条路都显式写了出来：

```cpp
// 拷贝：必须另申请一块内存，再把每个元素抄一遍
int_buffer(const int_buffer& other)
    : data(std::make_unique<int[]>(other.length)), length(other.length)
{
    for (std::size_t i = 0; i < length; ++i)
    {
        data[i] = other.data[i];
    }
}

// 移动：不申请内存，只把指针接过来
int_buffer(int_buffer&& other) noexcept
    : data(std::move(other.data)), length(other.length)
{
    other.length = 0;
}
```

运行结果：

```text
=== Demo A: a buffer with four elements ===
a.size() = 4
a[0] = 7, a[3] = 7
=== Demo B: copying allocates a second block ===
b and a share the same block: false
b.size() = 4, b[0] = 7
=== Demo C: moving hands the block over ===
c keeps a's old block: true
a is empty now: true
a.size() = 0
=== Demo D: the moved-to buffer still works ===
c.size() = 4, c[0] = 7, c[3] = 7
=== Demo E: the buffer can be moved into a vector ===
buffers.size() = 1
buffers[0].size() = 4, buffers[0][0] = 7
```

Demo B 和 Demo C 是这一章的中心对照，两句话就能说清：

- **复制得到的是一块新内存**（`b and a share the same block: false`）。元素内容一样，但成本是"申请 + 逐个拷贝"，元素越多越慢。
- **移动得到的是原来那块内存**（`c keeps a's old block: true`）。整个过程只交接了一个指针，**成本与元素个数无关**——这正是"移动比复制便宜"的确切含义，而不是"移动一定更快一点点"。
- **移动之后源对象进入可安全销毁的空状态**（`a.size() = 0`）：`unique_ptr` 成员被移走后变成空指针，`length` 被我们显式清零。它仍然是一个完好的对象：可以销毁（`delete` 空指针是合法的）、可以重新赋值，但**它的旧内容已经不属于它了，不该再去读**（第 28 章第 5 节那条"有效但未指定"的规则）。
- **Demo E** 回到本章的动机：把资源交给容器时，具名对象要写 `std::move`，这一步之后 `vector` 就真的持有了那份资源，而不是把它复制一份。

### 7.2 实验二：隐式声明规则（`implicit_move_rules`）


**预期现象**：输出与 5 节的十八行逐字符一致（`plain` 走移动、`with_copy` 走复制、`move_only` 走移动且不可复制）。

**验收标准**：`-Wall` 无警告；能说出 `with_copy` 的 `is_nothrow_move_constructible` 为什么是 `false`，以及为什么它的探针成员 `origin` 是 `copy`。

**改值实验**：给 `plain` 补一个用户声明的析构函数：

```cpp
struct plain
{
    tracked member;

    ~plain() { }
};
```

先判断结果。预期是 Demo A 的两行 traits 变成 `is_nothrow_move_constructible = false`，并且 `p2.member.origin` 从 `move` 变成 `copy`，整段输出与 Demo B 完全一样——**声明析构函数会按同一条规则抑制隐式移动构造函数**。这个实验请务必动手做一次，它是"写了析构函数的类型为什么忽然变慢了"的答案。

**必做实验**：把 `with_copy` 的拷贝构造函数改成 `with_copy(const with_copy& other) noexcept : member(other.member) { }`（只多一个 `noexcept`），重新编译运行。**预判**：`is_nothrow_move_constructible` 变成 `true`，但 `origin` 仍然是 `copy`。这说明"`noexcept` 只影响容器敢不敢搬，**不会凭空造出一个移动构造函数**"。

### 7.3 实验三：资源转移的真实成本（`move_constructor_resource`）

`move_constructor_resource\move_constructor_resource.cpp` 里的 `int_buffer` 自己管理一块堆内存，用来对比复制与移动的实质区别。

```text
E:\msys64\ucrt64\bin\g++.exe -std=c++20 -Wall -g move_constructor_resource.cpp -o move_constructor_resource.exe
./move_constructor_resource.exe
```

**预期现象**：输出与 6 节的十五行逐字符一致（复制不共享内存、移动接管原内存、移动后源对象为空、移交进 `vector` 后仍可正常使用）。

**验收标准**：`-Wall` 无警告；能说出 `c keeps a's old block: true` 证明了什么（移动**没有**申请新内存，也没有拷贝任何 `int`）；能说出 Demo C 之后为什么不能再去读 `a` 的内容。

**改值实验**：把移动构造函数里 `data(std::move(other.data))` 的那一层 `std::move` 去掉，重新编译运行。**预判**：编译直接失败，`unique_ptr` 不能复制，报错里会出现 `error: use of deleted function 'std::unique_ptr<...>::unique_ptr(const std::unique_ptr<...>&)'`。这条实验把 3 节那句"成员初始化列表里忘写 `std::move`，成员就会被复制"从规则变成了看得见的后果——只不过 `unique_ptr` 连复制都不允许，问题会更早暴露。看完还原，并把 `other.length = 0;` 这一行也试着删掉再运行一次，确认输出从 `a.size() = 0` 变成 `a.size() = 4`：**源对象的"空状态"不是自动出现的，是移动构造函数自己安排的。**

## 8 常见错误与排查

| 报错或现象 | 原因 | 处理 |
| --- | --- | --- |
| `error: use of deleted function 'constexpr S::S(const S&)'`（附注 `'S' declares a move constructor or move assignment operator`） | 类型声明了移动构造函数，而拷贝构造函数没有被用户声明，于是被定义为删除 | 要么显式写出拷贝构造函数（第 26 章），要么确认这类对象本来就该只移动、把复制点删掉 |
| `error: use of deleted function 'buffer::buffer(const buffer&)'`（报错链里出现 `unique_ptr(const unique_ptr&)`） | 成员里有 `unique_ptr` 这类不可复制的资源，默认拷贝构造是删除的 | 移动它：`buffer b = std::move(a);`；确实需要共享所有权则用 `shared_ptr`（第 20 章） |
| 明明写了 `std::move`，输出里却仍然是 `Copy Constructor!` | 类型没有移动构造函数（用户声明过拷贝构造、拷贝赋值、移动赋值或析构函数，导致它没被隐式声明） | 自己写 `S(S&&) noexcept`；若类型确实不该被搬走，那么复制就是正确行为 |
| `vector` 扩容时元素的复制次数远多于移动次数，程序比预期慢 | 移动构造函数没有标 `noexcept`，`vector` 不敢用它搬元素，退回复制 | 给移动构造函数补上 `noexcept`（前提是函数体真的不抛异常） |
| 移动构造函数里只写了打印，资源仍然被复制 | 成员是资源类型，却在初始化列表里直接写了 `other.data`——具名的右值引用是左值，不带 `std::move` 就是复制 | 成员用 `std::move(other.data)` 移动构造（见 3 节） |
| 写成 `S(S& other)` 之后，普通的 `S b = a;` 竟然把 `a` 搬空了 | 参数是非 `const` 左值引用时，它比 `const S&` 更匹配非 `const` 左值，于是"移动"被用在了复制上 | 移动构造函数的参数必须写成 `S&&` |
| 移动之后读源对象，得到 0、空值或奇怪结果 | 源对象处于"有效但未指定"状态，它的旧值已经没有意义 | 只允许对它做两件事：重新赋值或让它销毁；需要"确认资源已交出"就查空指针之类的明确保证 |
| `error: cannot bind rvalue reference of type 'int&&' to lvalue of type 'int'` | 右值引用只接受右值，而给的是一个具名变量 | 确实要搬就写 `std::move(x)`；只是要转交所有权则检查是不是漏了 `std::move` |
