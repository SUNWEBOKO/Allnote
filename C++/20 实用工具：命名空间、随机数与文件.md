## 1 命名冲突从哪来

代码写大以后，名字会变成稀缺资源。一个项目里有几十个类、上百个函数，还常常要用别人写的库；函数名要能说明它做什么（第 04 章那条“见名知意”的要求），于是 `print`、`size`、`init`、`data` 这类名字会被反复使用。名字撞车是迟早的事。

碰撞的判定标准前几章已经讲过：**两个函数的函数名相同、参数列表也相同，就是同一个函数**，函数体不同不算区分。所以在同一个作用域里写两个 `print` 是直接冲突的：

```cpp
void print()
{
    std::cout << "来自全局命名空间：Hello C++" << std::endl;
}

void print()
{
    std::cout << "来自命名空间 a：Hello C++" << std::endl;
}
```

编译器会报错（实测文本）：

```text
error: redefinition of 'void print()'
note: 'void print()' previously defined here
```

信息里的 `redefinition`（重定义）说得毫不含糊：在编译器眼里，这两个函数是**同一个东西定义了两次**。即使它们的函数体完全不同、即使调用处根本无从判断该用哪一个，也不会被当成两个函数。

要注意的是，这种冲突**不限于一个文件之内**。同一个程序的不同源文件里各自写了一个 `print`，它们最终会被编译到一起（第 01 章讲过编译与链接的过程），冲突就会在链接阶段暴露（实测文本）：

```text
multiple definition of `print()'; ... first defined here
collect2.exe: error: ld returned 1 exit status
```

所以“我把它们放到不同文件里”并不是解决办法。真正需要的是：**让这两个 `print` 分属不同的名字范围。**

## 2 用命名空间把名字隔开

`namespace` 就是为此设计的关键字。把其中一个 `print` **包进去**：

```cpp
void print()
{
    std::cout << "来自全局命名空间：Hello C++" << std::endl;
}

namespace a
{
    void print()
    {
        std::cout << "来自命名空间 a：Hello C++" << std::endl;
    }
}
```

现在两个函数可以同时存在，编译也通过了。原因是它们的**完整名字**不同：

- 第一个叫 `print`，属于**全局命名空间**（global namespace）；
- 第二个叫 `a::print`，属于命名空间 `a`。

命名空间是一个**名字的容器**，也可以理解为一层作用域：包在里面的名字只属于这个容器，和外面的同名名字互不干扰。**要隔离什么名字就把它包进去**——函数、变量、结构体、类都能装（下面例子里是变量、结构体、函数和嵌套命名空间）。

### 2.1 不带限定的名字怎么找

包进命名空间之后，一个问题马上出现：`main` 里写一句 `print();`，编译器会选哪一个？

规则是**由内向外逐层查找**：

1. 先看当前作用域（例如函数体内部有没有定义 `print`）；
2. 找不到就往外一层（外层作用域）；
3. 一直找到**全局命名空间**为止，这里有 `print`，于是调用它。

关键在于：**命名空间 `a` 里的名字不会“顺便”出现在全局命名空间里**。`a::print` 只属于 `a`，所以不带限定的 `print()` 找不到它，只能找到全局那个。例程 `E:\CPP_Code\CppFromScratch\ch44_namespaces\namespace_basic\namespace_basic.cpp` 的实测结果印证了这一点：

```text
=== Demo A: 不带限定地调用 print() ===
来自全局命名空间：Hello C++
```

这也解释了一个容易误会的写法：**把两个函数同名，留一个在全局、另一个放进命名空间，并不会形成“重载”**。它们是两个分属不同作用域的名字，编译器按上面的查找顺序各找各的，谁也不会去“挑选更合适的那个”。

## 3 访问命名空间里的名字

要访问命名空间里的名字，用它 **`命名空间名 + 作用域解析运算符 ::`**：

```cpp
a::print();
```

`::` 的左边写命名空间，右边写里面的名字，含义是“到 `a` 里面去找 `print`”。例程的输出：

```text
=== Demo B: 用作用域解析运算符指定命名空间 ===
来自命名空间 a：Hello C++
```

这套写法我们其实从第 01 章就在用了：**整个标准库都装在命名空间 `std` 里**，所以 `std::cout`、`std::vector`、`std::thread` 全都是“命名空间 `std` 里的名字”。以前写 `std::` 只是照着习惯写，现在应该能说出它的作用了——它把标准库的名字和我们自己写的东西分开，所以我们完全可以定义自己的 `vector` 或 `count` 而不与标准库打架。

`::` 左边也可以什么都不写，写成 `::print`，意思是“**从全局命名空间开始找**”：

```text
=== Demo C: ::print() 明确从全局命名空间找 ===
来自全局命名空间：Hello C++
```

平时用不到这种写法，它的价值在于**把意图写清楚**：当局部作用域里也可能有同名名字时，`::name` 明确表示“我要的就是全局那一个”。

## 4 命名空间里能装什么

命名空间能装的东西比想象中多：函数、变量、结构体、类都能装（下面例子里是变量、结构体、函数和嵌套命名空间），甚至别的命名空间。例程 `ch44_namespaces\namespace_types\namespace_types.cpp` 里做了一个对比——全局有一个 `point`，`geometry` 里也有一个 `point`（成员不同），`acme` 里还有第三个：

```cpp
struct point
{
    int x;
    int y;
};

namespace geometry
{
    constexpr double pi = 3.14159;

    struct point
    {
        double x;
        double y;
    };

    double circleArea(double radius)
    {
        return pi * radius * radius;
    }
}

namespace acme
{
    struct point
    {
        int x;
        int y;
        int z;
    };
}
```

这三个 `point` 是**三个互不相同的类型**，各自有自己的成员，所以可以同时使用而不冲突：

```text
=== Demo A: 三个同名的 point 是三个互不相同的类型 ===
全局的 point：整点 (1, 2)
geometry::point：浮点坐标 (1.5, 2.5)
acme::point：三维点 (1, 2, 3)
```

变量和函数的访问方式一样，用限定名写清楚就行：

```text
=== Demo B: 命名空间里的变量与函数 ===
geometry::pi = 3.14159
geometry::circleArea(2) = 12.5664
```

有一点值得留意：命名空间成员是**有作用域、有类型、遵循语言规则**的实体，和“宏”那种纯文本替换完全不同；成员既可以是变量（有存储、有生命周期），也可以是常量——上面例子里 `geometry::pi` 就是一个 `constexpr` 常量。往命名空间里放变量，本质上就是放了一个全局变量，只是它的名字被限定在命名空间里——需要全局状态时这样写比散落的全局变量清楚得多，但**全局状态本身要小心**，这一点在前面的章节里已经反复强调过。

## 5 可以反复打开、可以嵌套、可以起别名

命名空间有三个很实用的性质。

**第一，同一个命名空间可以在文件里多处打开。** 例程 `ch44_namespaces\namespace_split\namespace_split.cpp` 里，`app` 被打开了两次：

```cpp
namespace app
{
    void start()
    {
        std::cout << "app::start（第一次打开命名空间时写的）" << std::endl;
    }
}

namespace app
{
    void stop()
    {
        std::cout << "app::stop（第二次打开同一个命名空间时写的）" << std::endl;
    }
}
```

`start` 和 `stop` 是在两个不同的地方写进去的，但它们属于同一个 `app`，都用 `app::` 访问。实测输出：

```text
=== Demo A: 同一个命名空间在多处被打开 ===
app::start（第一次打开命名空间时写的）
app::stop（第二次打开同一个命名空间时写的）
```

**这条性质解释了标准库是怎么做出来的**：`std` 命名空间分散在几十个头文件里，每个头文件各自打开 `std` 往里放东西（`<iostream>` 放 `cout`、`<vector>` 放 `vector`、`<thread>` 放 `thread`），最后拼成一个完整的 `std`。如果没有“可反复打开”这条规则，标准库就得挤在一个文件里。

**第二，命名空间可以嵌套**，用来把实现细节和对外接口分层：

```cpp
namespace geometry
{
    namespace detail
    {
        double square(double value)
        {
            return value * value;
        }
    }
}
```

按约定把 `detail` 当作给 `geometry` 内部用的实现细节（这只是命名约定，编译器并不阻止外部访问），完整的名字写作 `geometry::detail::square`。

**第三，太长的名字可以起别名**：

```cpp
namespace gd = geometry::detail;
```

别名只是同一个实体的另一个叫法——它**不产生新的命名空间，也不复制任何东西**。上面三点的实测输出：

```text
=== Demo C: 嵌套命名空间与命名空间别名 ===
geometry::detail::square(3) = 9
gd::square(4) = 16
```

## 6 using 声明与 using 指令

每次都写 `geometry::circleArea(...)` 未免啰嗦，C++ 提供了两种省事的写法，但它们的影响范围差别很大，必须分清楚。

**`using` 声明（using-declaration）：只引入一个名字。**

```cpp
using geometry::circleArea;

std::cout << "circleArea(1) = " << circleArea(1.0) << std::endl;
```

它把 `circleArea` 这一个名字带进**当前作用域**（上面写在 `main` 函数体里，所以只在 `main` 里有效）。实测输出：

```text
=== Demo D: using 声明把某个名字引入当前作用域 ===
circleArea(1) = 3.14159
```

因为它只引入一个名字，和已有的名字撞车的机会很小，是**推荐**的省事方式。

**`using` 指令（using-directive）：把整个命名空间的名字都带进来。**

```cpp
using namespace app;
```

例程 `namespace_split.cpp` 把它写在一对花括号里，实测：

```text
=== Demo B: using 指令只在它所在的作用域内生效 ===
花括号内可以直接写 start()：app::start（第一次打开命名空间时写的）
出了花括号就必须写全名：app::start（第一次打开命名空间时写的）
```

出了花括号 `start()` 就不认识了，必须写回 `app::start()`——**它的作用范围就是它所在的那个作用域**，这一点和上面的 `using` 声明一致。

那么风险在哪里？在于它把**所有**名字都带进来，而这些名字可能与已有的名字撞车。例程 `namespace_basic.cpp` 的 `main` 里加一句 `using namespace a;` 之后，原来那句 `print();` 就变成了：

```text
error: call of overloaded 'print()' is ambiguous
    • candidate 1: 'void a::print()'
    • candidate 2: 'void print()'
```

编译器找到了两个都叫 `print`、都没有参数的候选，无法决定用哪一个，于是**在歧义面前放弃编译**——这正是第 04 章重载解析里讲过的“歧义即错误”的另一种表现形式。变量也一样：全局有一个 `counter`、命名空间里也有一个，加一句 `using namespace` 之后读 `counter` 会得到

```text
error: reference to 'counter' is ambiguous
```

把这张对比表记下来就够了：

| 写法 | 引入什么 | 生效范围 | 风险 |
| --- | --- | --- | --- |
| `using geometry::circleArea;` | 一个指定的名字 | 它所在的作用域 | 很小，名字明确 |
| `using namespace app;` | 该命名空间里的所有名字 | 它所在的作用域 | 可能与已有名字歧义，或在包含这个头文件的别的文件里产生意外 |

**实践上的结论**：`using namespace` 写在**函数体内部**（越靠近使用处越好）风险可控；写在**文件开头（全局作用域）、尤其是写在头文件里**则影响面很大——头文件会被很多源文件包含，等于在别人不知情的情况下往他们的作用域里塞进一堆名字。本课程从第 01 章起一直老老实实写 `std::cout` 而不写 `using namespace std;`，原因就在这里。

命名空间解决的是“名字放哪里”的问题，它本身不产生任何数据。接下来看标准库另一组常用设施——`<random>` 头文件提供的随机数生成。

## 7 随机数解决什么问题

有一类程序需要一个“看起来没有规律”的序列：模拟骰子、抽卡、洗牌、随机采样、给算法生成测试输入、给仿真加入扰动。C++ 把这些能力集中在 `<random>` 头文件里，它由两部分组成：

- **随机数引擎**（engine）：产生一串无规律的数值；
- **分布**（distribution）：把引擎产生的数值转换成我们真正需要的范围与形状。

这两部分可以自由组合，这是 `<random>` 最重要的设计。本章先讲引擎，再讲分布，最后把它们拼成“掷骰子”这个经典例子。

### 7.1 为什么不用 `std::rand()`

在 C++11 之前，C 风格的 `std::rand()`（`<cstdlib>`）是唯一的选择，今天它仍然能用，但已经不适合承担正经工作，原因有四条：

1. **范围太窄。** `rand()` 返回 $0$ 到 `RAND_MAX` 之间的整数，本机（GCC 16 + UCRT）实测 `RAND_MAX = 32767`。想要 $10^6$ 级别的值就必须拼接多次调用。
2. **取模会带来明显偏差。** `rand() % 6 + 1` 是最常见的写法，但 `RAND_MAX + 1 = 32768` 不是 6 的整数倍，点数 1、2 出现的概率比 5、6 高出一截。
3. **只有一个全局状态。** 所有代码共用同一个隐藏序列，没法同时维护两条互不干扰的随机序列；它也不是线程安全的。
4. **质量与可移植性没有保证。** 标准没有规定 `rand()` 用什么算法，不同平台的速度、周期和统计性质差别很大，而 `<random>` 把算法（引擎）和用途（分布）都写清楚了，还能自己选。

## 8 随机数引擎

### 8.1 `std::random_device`：非确定性来源

`std::random_device` 是标准库提供的**非确定性**随机数来源：它不是伪随机算法，而是去问操作系统要熵（在 Windows 上最终落到系统的随机数设施上）。用法和函数调用一样：

```cpp
#include <iostream>
#include <random>

int main()
{
    std::random_device rd;

    for (int i = 0; i < 3; ++i)
    {
        std::cout << rd() << " ";
    }
    std::cout << std::endl;

    return 0;
}
```

`rd()` 每次给出一个范围很宽的无符号整数，反复运行程序会得到不同的结果——这正是“非确定性”的含义。注意这个例子的输出无法写进文档作为预期输出，因为它在设计上就不该可复现。

标准只要求 `random_device` 提供均匀分布的整数，并不保证它一定有硬件熵源。当平台拿不到熵时，实现可以退化成伪随机（此时 `rd.entropy()` 会返回 `0`）。所以 `random_device` 的正确用法不是大量取数，而是**取一个种子**。

### 8.2 伪随机数引擎：`std::mt19937`

伪随机数引擎是一个**确定性的状态机**，它做两件事：

1. 用内部状态算出一个数值交给调用者；
2. 把内部状态推进到下一步。

调用方式就是 `gen()`——引擎对象可以像函数一样被调用，因为它重载了函数调用运算符 `operator()`（第 18 章的函数对象在这里就用上了）。C++11 起提供的标准引擎家族有：

| 家族 | 代表类型 | 特点 |
| --- | --- | --- |
| 线性同余引擎 | `std::minstd_rand` | 状态最小、最快，但周期短、统计性质较弱 |
| 梅森旋转引擎 | `std::mt19937`、`std::mt19937_64` | 周期极长（约 $2^{19937}-1$）、质量好，状态较大（`mt19937` 内部有 624 个字） |
| 带进位减法引擎 | `std::ranlux24_base`、`std::ranlux48_base` | 介于两者之间，配合 `ranlux` 系列可以得到更高质量 |

这几类引擎在随机数质量、内部状态占用的内存、生成速度上各有取舍，选哪一个取决于任务：要快、要省内存，还是要长周期与高质量。本章统一用 `std::mt19937`——它的质量足够好，而且标准把它的算法（当年松本与西村提出的梅森旋转）**完全规定死**了，因此同一个种子在任何标准库上都给出同一条序列。

`std::mt19937` 的名字可以拆成两部分：`mt` 指 Mersenne Twister，`19937` 指它的周期是 $2^{19937}-1$。`std::mt19937_64` 是同族的 64 位版本，一次给出 64 位整数。

## 9 种子：伪随机数的可复现性

引擎的初始状态由**种子**（seed）决定。同一个种子必然给出同一条序列，这就是“伪随机”的准确含义：**序列看起来没有规律，但它完全由种子和算法决定，没有任何真正的偶然**。

```cpp
std::mt19937 gen {42};      // 用 42 作为种子
std::cout << gen() << std::endl;
```

42 这个数字本身没有任何特殊含义，换成任意整数都是等价用法——它的唯一作用是把引擎的状态按确定的规则摆到一个位置。例程 `engine_fixed_seed` 实测了三种情形：两个用 42 构造的引擎给出完全相同的 5 个值；换成 49 得到另一条序列；同一个引擎继续调用时给出的是序列的第 6 到第 10 个值，不会重来。

种子的长度只有一个整数，而 `mt19937` 的内部状态有 624 个字，这一个整数会被引擎的构造函数“摊开”填满整个状态。需要传入一组种子值时可以用 `std::seed_seq`：

```cpp
std::seed_seq seq {1, 2, 3, 4, 5};
std::mt19937 gen {seq};     // 把 5 个种子值混合后铺满整个状态
```

它的用处是避免“相邻的种子给出相关的序列”这类问题。日常用一个整数就够了。

### 9.1 该用固定种子还是随机种子

| 目的 | 做法 | 结果 |
| --- | --- | --- |
| 结果必须可复现：调试、测试、教学文档比对 | `std::mt19937 gen {42};` | 每次运行完全相同 |
| 每次运行都要不一样：游戏、仿真、抽样 | `std::mt19937 gen {std::random_device {}()};` | 每次运行不同，且不可复现 |

第二种写法把 `random_device` 的一次取值作为种子传给引擎，这是 `<random>` 里最常见的组合模式：用非确定性的来源播种，用高质量的伪随机算法产生大量数值——`random_device` 只需要给一个值，剩下的工作交给引擎。

**本课程的例程一律用固定种子**，这样“文档里写的预期输出”和“你实际运行看到的输出”才能逐字符对照。第 17 章也会做一个“编译期和运行期”的对照实验，理由相同。

## 10 分布：把引擎的输出变成需要的形状

引擎给出的整数落在 `[min(), max()]`（`std::mt19937` 是 `[0, 4294967295]`）这个很宽的区间里，通常不是我们想要的东西。我们想要的可能是“1 到 6 的整数”、“0 到 1 之间的小数”、“均值为 0 标准差为 1 的数”。把宽区间映射到目标区间、并保证正确的概率形状，是**分布对象**的工作。

```cpp
std::mt19937 gen {42};
std::uniform_int_distribution<int> dice {1, 6};

std::cout << dice(gen) << std::endl;     // 掷一次骰子
```

两点必须记住：

- 调用分布时要**把引擎喂进去**（`dice(gen)`），而不是 `dice()`。分布自己不含随机来源，它只是引擎输出的“翻译器”。
- 分布对象和引擎没有绑定关系：同一个引擎可以依次喂给多个不同的分布；同一个分布也可以换一个引擎来喂。引擎是“来源”，分布是“形状”，两者独立。

### 10.1 `std::uniform_int_distribution`：闭区间

`std::uniform_int_distribution<int> dice {1, 6};` 的两个构造参数是区间的两个端点，语义是**闭区间** $[1, 6]$：1 和 6 都能被取到，每个整数出现的概率都是 $1/6$。这正是六面骰子。

`uniform` 的意思是均匀：区间内每个值被取到的概率相同。例程 `dice_uniform` 把 6000 次投掷的结果按点数分类统计，每个点数都在 1000 次附近（实测 1029 / 927 / 999 / 1042 / 1010 / 993），这就是“均匀”可以直接观察到的样子。

### 10.2 区间约定：整数闭、实数半开

这是最容易记错的一处：`std::uniform_int_distribution`（整数）的区间**两端都包含**，而 `std::uniform_real_distribution`（实数）的区间是**半开**的 $[a, b)$——`a` 可能取到，`b` 取不到。

原因在于实数区间上取到某个具体值的概率是 0，闭区间的端点没有实际意义，半开区间能让 `[0.0, 1.0)` 这类写法自然地把整个单位长度不重不漏地切分。整数则相反：两端都是真实存在的取值，包含进来正是我们要的。

### 10.3 取模不是分布

很多人第一反应是 `gen() % 6 + 1`：它确实落在 1 到 6，也真的能跑，但和分布不是一回事，而且有偏差。以 `std::mt19937` 为例，它一次给出 $2^{32} = 4294967296$ 个可能值，按 6 取模：

$$4294967296 = 6 \times 715827882 + 4$$

余数为 $0,1,2,3$ 的那 4 个值各多出一次机会，也就是点数 1、2、3、4 比 5、6 更容易出现。区间长度越不接近 $2$ 的幂，偏差越明显。`std::uniform_int_distribution` 内部会处理这种不均匀（例如丢弃掉无法均分的尾部取值），保证每个值严格等概率。

例程 `dice_uniform` 的 Demo C 用同一种子分别走分布和取模两条路，输出完全不同——这说明“取模”不是分布的另一种写法，而是另一种算法。

## 11 标准库里的其他分布

`<random>` 提供的分布不止均匀整数一种，常用的有：

| 分布 | 类型 | 产生的值 |
| --- | --- | --- |
| 均匀整数 | `std::uniform_int_distribution<T>` | 闭区间 $[a,b]$ 上的整数，每个值等概率 |
| 均匀实数 | `std::uniform_real_distribution<T>` | 半开区间 $[a,b)$ 上的实数，概率密度恒定 |
| 正态（高斯） | `std::normal_distribution<T>` | 构造参数为均值 $\mu$ 与标准差 $\sigma$，钟形分布 |
| 伯努利 | `std::bernoulli_distribution` | 只有两种结果，构造参数是“成功”的概率 $p$ |
| 泊松 | `std::poisson_distribution<T>` | 单位时间/面积内的事件次数 |
| 离散/分段 | `std::discrete_distribution<T>`、`std::piecewise_constant_distribution<T>` | 按自定义权重取整数，或按自定义密度取实数 |

例程 `distribution_variants` 演示了其中的均匀实数、正态和伯努利三种：正态分布用 10000 个样本反推均值与标准差，实测 0.009327 与 1.008012，贴着构造时给的 $\mu = 0$、$\sigma = 1$；伯努利分布以 $p = 0.5$ 抛 1000 次硬币，得到 490 次正面、510 次反面。

**一个必须说明的边界**：标准规定了各分布的概率性质，但没有规定它们内部用什么算法（引擎的算法反而是规定死的）。所以“同一个引擎 + 同一个分布 + 同一个种子”在**同一套标准库**上输出可复现、在**不同标准库之间**具体数值可能不同。本课程所有随机数输出都是在 GCC 16.1.0 的 libstdc++ 上实测的，换到别的编译器上，引擎那部分的数值仍然一模一样，分布那部分可能不一样。想把随机数写进测试用例时，这一点要记住。

## 12 引擎该放在哪里

最容易踩的坑是把引擎构造放在循环里：

```cpp
for (int i = 0; i < 5; ++i)
{
    std::mt19937 gen {42};      // 每一轮都造一个新的、同种子的引擎
    std::cout << gen() << " ";
}
```

实测输出是 `1608637542 1608637542 1608637542 1608637542 1608637542`——每次都从同一个初始状态重新开始，于是每次都拿到序列的第一个值。正确做法是**把引擎构造在循环外面**，循环里只调用 `gen()`。

同理，如果多个函数都要用同一个引擎，应该把引擎**按引用**传进去（第 08 章讲过按引用传递），而不是在每个函数里各自构造一个。函数的形参写成 `std::mt19937&`，函数内部每调用一次 `gen()`，都在推进同一个引擎的状态。

还有一条关于代价的提醒：`std::mt19937` 的内部状态有 624 个字，构造一个引擎（用种子填满状态）不是零成本的操作。在整个程序里维护一个引擎，而不是每次都新建，既正确又快。

随机数能让程序每次运行都“变”出不同的数据，但程序一退出，这些数据和屏幕输出一样都会消失。要让数据活过程序的结束，就需要把它们写进文件。

## 13 为什么需要文件

到本章第 12 节为止，程序的所有数据都活在两个地方：变量里和屏幕上。这两处都是**临时的**——程序一退出，变量没了；屏幕上的输出滚过去就找不回来了。

需要让数据活过程序的结束，就得把它写进**文件**：程序算出来的结果要留档，运行日志要能在事后翻看，配置和输入数据要能由外部提供。C++ 标准库把这套能力放在 `<fstream>`（file stream，文件流）头文件里，它提供三种文件流：

| 类型 | 全名 | 用途 |
| --- | --- | --- |
| `std::ofstream` | output file stream | 只写 |
| `std::ifstream` | input file stream | 只读 |
| `std::fstream` | file stream | 又读又写 |

它们的名字由前缀加 `fstream` 组成：`o` 是 output，`i` 是 input。本章用前两种，因为绝大多数场景里“写数据的程序”和“读数据的程序”本来就是分开的。

## 14 写入文件：`std::ofstream`

例程 `write_squares` 把 0 到 9 的平方写进 `squares.txt`，核心只有三行：

```cpp
#include <fstream>
#include <iostream>

int main()
{
    std::ofstream output {"squares.txt"};     // 打开（不存在就新建）

    for (int i = 0; i < 10; ++i)
    {
        output << i * i << " ";               // 和往屏幕上打印写法完全相同
    }
    output << std::endl;

    output.close();                           // 显式关闭
    return 0;
}
```

（节选自例程 `write_squares\write_squares.cpp`，完整版本还包括打开失败的检查。）

### 14.1 文件流与 `std::cout` 是同一类东西

`std::cout` 是输出流，`std::ofstream` 也是输出流，两者共享同一套接口，所以 `<<` 的写法完全一样：数字、字符、字符串、`std::endl` 都能直接往文件里送。这一点是流设计的好处——第 01 章学过的输出写法，换到文件上不需要重新学一遍。

区别只有数据落到哪里：`std::cout` 落到标准输出，`std::ofstream` 落到打开的那个文件。

### 14.2 打开：构造对象就等于打开文件

`std::ofstream output {"squares.txt"};` 这一行做了两件事：构造对象、尝试打开文件。默认的打开模式是 `out | trunc`，含义是“要写，并且把已有内容截断成 0 字节”：

- 文件不存在 → 新建一个（实测运行本程序后当前目录出现了 28 字节的 `squares.txt`）；
- 文件已存在 → 原有内容全部丢失，从头开始写。

**每次运行都会覆盖上次的结果**，这一点必须记住。想保留旧内容要显式指定追加模式（见本章第 16 节）。

### 14.3 相对路径相对于什么

`"squares.txt"` 是相对路径，它相对于程序**运行时的当前目录**（current working directory，cwd），而不是相对于源码文件或 `.exe` 所在的目录。

```text
cd "E:/CPP_Code/CppFromScratch/ch46_file_io/write_squares"
./write_squares.exe
```

这样运行时，当前目录就是 `write_squares\`，文件生成在那里。如果换到别的目录去执行同一个 `.exe`（例如 `cd ..` 之后再 `./write_squares/write_squares.exe`），文件就会生成在那个新目录里，程序本身不会有任何察觉。**“读不到刚刚写下的文件”十有八九是当前目录不对**，而不是代码的问题。

写绝对路径可以避开这个不确定性，例如 `"E:/CPP_Code/data.txt"`，但这样一来程序就绑死在某个位置上，不适合在不同机器上运行。

### 14.4 什么时候关闭文件

`close()` 做两件事：把流缓冲区里剩下的数据真正写出去、把文件交还给操作系统。不显式调用也不会丢数据——文件流对象在**析构**时会自动关闭（第 12 章讲过析构函数承担的清理职责），`main` 结束时 `output` 被销毁，文件自然被关闭。

显式 `close()` 的价值有两点：写入过程中出错能在这一处就暴露出来；紧接着可以重新打开同一个文件。还有一种更省事的做法是把流对象放进一对花括号里，让作用域结束时的析构替我们关闭（`read_squares` 和 `append_log` 就是这么写的）。

另外，`std::endl` 除了写换行还会**刷新缓冲区**，所以用 `std::endl` 收尾的文件，内容会立即落盘。

### 14.5 文本模式下的换行

文件默认以**文本模式**打开。在 Windows 上，文本模式会把每个 `'\n'` 写成两字节的 `\r\n`（CRLF），读取时再自动还原成一个 `'\n'`。实测例程 `append_log` 生成的 `log.txt`，末尾三个字节是 `t`、`\r`、`\n`——写代码时我们只写了 `std::endl`。这层转换由流对象负责，不用手动处理；但也意味着**同一个文件在 Windows 和 Linux 上字节数不同**（`binary` 模式下才不做任何转换）。

## 15 读取文件：`std::ifstream`

### 15.1 用 `>>` 逐个读入

`std::ifstream` 的用法和 `std::cin` 一致，只是 `>>` 的方向朝着变量，表示“从流里取数据放进变量”：

```cpp
std::ifstream input {"squares.txt"};
int value = 0;

while (input >> value)
{
    std::cout << value << " ";
}
std::cout << std::endl;
```

（节选自例程 `read_squares\read_squares.cpp`。）

`>>` 在取数之前会**自动跳过所有空白字符**：空格、制表符、换行符都算。所以写文件时用来分隔数字的那个空格、以及文件末尾的换行，读取时都不用我们处理。这是 `>>` 与本章第 15.2 节的 `getline` 最本质的区别。

### 15.2 `while (input >> value)` 为什么能读到文件末尾

`input >> value` 这个表达式的结果是流对象本身，而流对象能被转换成一个布尔值：“这次操作成功了没有”。于是循环的含义是：**先读一次，读到了就进循环体，读不到就结束**。

- 读到的一个合法的 `int` → 为真，进入循环；
- 数据读完（遇到文件末尾）→ 为假，循环结束；
- 读到格式不对的内容（比如往 `int` 里读 `"abc"`）→ 同样为假，循环结束。

因为这个写法不依赖“文件里到底有几个数”，读多少算多少，它是处理数字文件的标准写法。例程 `read_squares` 实测：文件里 10 个数，循环执行 10 次，计数 10、求和 285（$0^2 + 1^2 + \dots + 9^2 = 285$）。

### 15.3 `getline`：按整行读取

`std::getline(流, 字符串)` 一次取出一整行，把行尾的换行符丢掉，行内的空格原样保留：

```cpp
std::ifstream in {"log.txt"};
std::string line;

while (std::getline(in, line))
{
    std::cout << line << std::endl;
}
```

（节选自例程 `append_log\append_log.cpp`。）

两种读法的分工很清楚：**文件里是“一堆同类型的值”就用 `>>`，是“一行一条记录”就用 `getline`**。混用要当心一个经典陷阱：`>>` 读到数字就停住，后面的空白（包括换行符）还留在流里，紧接着的 `getline` 会把这一行的剩余部分（常常只剩一个换行）当成一行读出来，看起来就像“凭空多了一个空行”。

### 15.4 流是“消耗品”

一个流读到文件末尾之后就不能接着用了：它已经停在末尾，再读也读不到东西。想从头再读一遍文件，得**新建一个流对象**（或先 `close()` 再 `open()`）：

```cpp
std::ifstream again {"squares.txt"};     // 重新打开，从头开始
```

例程 `read_squares` 里做了两遍读取：第一遍逐个打印，第二遍重新打开做计数与求和。

## 16 打开模式

构造文件流时可以给出第二个参数指定打开模式，常见的几种：

| 模式 | 含义 |
| --- | --- |
| `std::ios::out` | 可写（`ofstream` 的默认值） |
| `std::ios::in` | 可读（`ifstream` 的默认值） |
| `std::ios::trunc` | 打开时清空已有内容（`ofstream` 默认带上它） |
| `std::ios::app` | 追加：写位置总在文件末尾，原有内容保留 |
| `std::ios::ate` | 打开后定位到末尾，但写入位置可以再移动 |
| `std::ios::binary` | 二进制模式，不做换行转换 |

多个模式用按位或连接，例如 `std::ios::out | std::ios::app`。

最常用的是追加模式，写日志几乎总是用它：

```cpp
std::ofstream out {"log.txt", std::ios::app};
```

例程 `append_log` 把这个区别做成了对照实验：先用默认模式写两行（`boot: ok`、`load: ok`），再用 `std::ios::app` 追加一行（`run: start`），读回来共三行；随后又用一次默认模式打开同一个文件写 `reset`，再读回来就**只剩 `reset` 一行**——前面三行被截断掉了。**默认模式是“清空重写”，不是“接着写”**，这是文件读写里最容易搞错的一处。

例程开头还有一句 `std::remove("log.txt");`（来自 `<cstdio>`），它在每次运行前删掉上次留下的文件，让重复运行的结果完全一致。这和本章第 9 节的固定种子是同一个目的：**让输出可复现、可逐字符比对**。

## 17 打开失败：必须检查

文件打不开是很常见的事：路径写错、文件不存在、目录没有写权限、要写的目录不存在。这时 `ifstream` 和 `ofstream` **既不会抛异常，也不会终止程序**，只是让对象处于“文件没打开”的状态，之后所有读写操作都静默失败。

```cpp
std::ifstream input {"no_such_file.txt"};

if (!input.is_open())
{
    std::cout << "cannot open no_such_file.txt" << std::endl;
    return 1;
}
```

不检查的后果非常隐蔽，例程 `open_failure` 把它实测出来了：读一个不存在的文件，`while (input >> value)` 一次都没进循环，计数结果是 `0`，程序**正常退出、没有任何报错**。如果后面还有一段“根据读到的数据计算结果”的代码，错误会一路传下去，最后表现为“结果是 0 / 是空的”，而真正的原因在几千行之外。

所以规则只有一条：**每次打开文件之后立刻检查 `is_open()`**，打不开就报错返回；写出方向同样要检查（例程里写一个不存在的目录 `no_such_dir/out.txt`，`is_open()` 同样是 `false`）。

顺便说明一个容易混淆的地方：`clear()` 只是把流的状态标志清理干净，**不会**替我们打开文件；想重新尝试打开必须显式调用 `open()`。例程里对同一个错误文件名先 `clear()` 再 `open()`，两次检查的结果都还是“没打开”。

### 实验一：`namespace_basic` 同名函数与作用域解析运算符

`namespace_basic\namespace_basic.cpp` 里有一个全局的 `print` 和一个 `namespace a` 里的 `print`，`main` 里分别用不加限定、`a::print()`、`::print()` 三种方式调用。

来自全局命名空间：Hello C++

**验收标准**：输出与上面逐字符一致；编译时 `-Wall` 没有警告。

**改值实验一（注释掉全局的那个）**：把全局的 `print` 函数整体注释掉，重新编译。**先预测**会发生什么，再看结果。实测报错（第一处）：

```text

note: 'a::print' declared here
```

这句话正好说明了本章第 2.1 节的规则：**命名空间里的名字不会自动进入全局查找**，`a::print` 不会因为“没有别的候选”就被选中，编译器只是提示你“是不是想写 `a::print`"。另外 Demo C 那一行的 `::print();` 也会报错，内容是 `error: '::print' has not been declared; did you mean 'a::print'?`——因为全局命名空间里确实已经没有 `print` 了。看完请把全局的 `print` 恢复。

**改值实验二（再加一个同名的）**：在文件里再加一个全局函数

```cpp
void print()
{
    std::cout << "第二个全局 print" << std::endl;
}
```

重新编译，实测报错：

```text
error: redefinition of 'void print()'
note: 'void print()' previously defined here
```

这就是本章开头那个问题本身。**命名空间能解决的正是它**：把新函数放进另一个命名空间（例如 `namespace b`）就没事了。看完请把这第二个全局 `print` 删掉。

**改值实验三（制造歧义）**：在 `main` 里 Demo A 那句 `print();` **之前**加一句 `using namespace a;`，重新编译。实测报错：

```text
error: call of overloaded 'print()' is ambiguous
```

两个 `print` 现在都出现在查找范围里（一个来自全局，一个来自 `using` 指令），编译器无法选择。把 `using namespace a;` 删掉即可恢复。这个实验说明的是本章第 6 节的结论：**`using namespace` 会把整个命名空间的名字带进当前作用域，代价是可能产生歧义。**
