## 1 命名冲突从哪来

代码写大以后，名字会变成稀缺资源。一个项目里有几十个类、上百个函数，还常常要用别人写的库；函数名要能说明它做什么（第 08 章那条"见名知意"的要求），于是 `print`、`size`、`init`、`data` 这类名字会被反复使用。名字撞车是迟早的事。

碰撞的判定标准前几章已经讲过：**两个函数的函数名相同、参数列表也相同，就是同一个函数**，函数体不同不算区分。所以在同一个作用域里写两个 `print` 是直接冲突的：

```cpp
void print()
{
    std::cout << "来自全局命名空间：Hello C++" << std::endl;
}

void print()
{
    std::cout << "来自命名空间 a：Hello C++" << std::endl;
}
```

编译器会报错（实测文本）：

```text
error: redefinition of 'void print()'
note: 'void print()' previously defined here
```

信息里的 `redefinition`（重定义）说得毫不含糊：在编译器眼里，这两个函数是**同一个东西定义了两次**。即使它们的函数体完全不同、即使调用处根本无从判断该用哪一个，也不会被当成两个函数。

要注意的是，这种冲突**不限于一个文件之内**。同一个程序的不同源文件里各自写了一个 `print`，它们最终会被编译到一起（第 02 章讲过编译与链接的过程），冲突就会在链接阶段暴露（实测文本）：

```text
multiple definition of `print()'; ... first defined here
collect2.exe: error: ld returned 1 exit status
```

所以"我把它们放到不同文件里"并不是解决办法。真正需要的是：**让这两个 `print` 分属不同的名字范围。**

## 2 用命名空间把名字隔开

`namespace` 就是为此设计的关键字。把其中一个 `print` **包进去**：

```cpp
void print()
{
    std::cout << "来自全局命名空间：Hello C++" << std::endl;
}

namespace a
{
    void print()
    {
        std::cout << "来自命名空间 a：Hello C++" << std::endl;
    }
}
```

现在两个函数可以同时存在，编译也通过了。原因是它们的**完整名字**不同：

- 第一个叫 `print`，属于**全局命名空间**（global namespace）；
- 第二个叫 `a::print`，属于命名空间 `a`。

命名空间是一个**名字的容器**，也可以理解为一层作用域：包在里面的名字只属于这个容器，和外面的同名名字互不干扰。**要隔离什么名字就把它包进去**——函数、变量、结构体、类都可以（第 4 节会看一个都装进去的例子）。

### 2.1 不带限定的名字怎么找

包进命名空间之后，一个问题马上出现：`main` 里写一句 `print();`，编译器会选哪一个？

规则是**由内向外逐层查找**：

1. 先看当前作用域（例如函数体内部有没有定义 `print`）；
2. 找不到就往外一层（外层作用域）；
3. 一直找到**全局命名空间**为止，这里有 `print`，于是调用它。

关键在于：**命名空间 `a` 里的名字不会"顺便"出现在全局命名空间里**。`a::print` 只属于 `a`，所以不带限定的 `print()` 找不到它，只能找到全局那个。例程 `E:\CPP_Code\CppFromScratch\ch44_namespaces\namespace_basic\namespace_basic.cpp` 的实测结果印证了这一点：

```text
=== Demo A: 不带限定地调用 print() ===
来自全局命名空间：Hello C++
```

这也解释了一个容易误会的写法：**把两个函数同名，留一个在全局、另一个放进命名空间，并不会形成"重载"**。它们是两个分属不同作用域的名字，编译器按上面的查找顺序各找各的，谁也不会去"挑选更合适的那个"。

## 3 访问命名空间里的名字

要访问命名空间里的名字，用它 **`命名空间名 + 作用域解析运算符 ::`**：

```cpp
a::print();
```

`::` 的左边写命名空间，右边写里面的名字，含义是"到 `a` 里面去找 `print`"。例程的输出：

```text
=== Demo B: 用作用域解析运算符指定命名空间 ===
来自命名空间 a：Hello C++
```

这套写法我们其实从第 01 章就在用了：**整个标准库都装在命名空间 `std` 里**，所以 `std::cout`、`std::vector`、`std::thread` 全都是"命名空间 `std` 里的名字"。以前写 `std::` 只是照着习惯写，现在应该能说出它的作用了——它把标准库的名字和我们自己写的东西分开，所以我们完全可以定义自己的 `vector` 或 `count` 而不与标准库打架。

`::` 左边也可以什么都不写，写成 `::print`，意思是"**从全局命名空间开始找**"：

```text
=== Demo C: ::print() 明确从全局命名空间找 ===
来自全局命名空间：Hello C++
```

平时用不到这种写法，它的价值在于**把意图写清楚**：当局部作用域里也可能有同名名字时，`::name` 明确表示"我要的就是全局那一个"。

## 4 命名空间里能装什么

命名空间能装的东西比想象中多：函数、变量、结构体、类，甚至别的命名空间。例程 `ch44_namespaces\namespace_types\namespace_types.cpp` 里做了一个对比——全局有一个 `point`，`geometry` 里也有一个 `point`（成员不同），`acme` 里还有第三个：

```cpp
struct point
{
    int x;
    int y;
};

namespace geometry
{
    constexpr double pi = 3.14159;

    struct point
    {
        double x;
        double y;
    };

    double circleArea(double radius)
    {
        return pi * radius * radius;
    }
}

namespace acme
{
    struct point
    {
        int x;
        int y;
        int z;
    };
}
```

这三个 `point` 是**三个互不相同的类型**，各自有自己的成员，所以可以同时使用而不冲突：

```text
=== Demo A: 三个同名的 point 是三个互不相同的类型 ===
全局的 point：整点 (1, 2)
geometry::point：浮点坐标 (1.5, 2.5)
acme::point：三维点 (1, 2, 3)
```

变量和函数的访问方式一样，用限定名写清楚就行：

```text
=== Demo B: 命名空间里的变量与函数 ===
geometry::pi = 3.14159
geometry::circleArea(2) = 12.5664
```

有一点值得留意：命名空间里的变量是真正的变量（有存储、有生命周期），不是"常量"或"宏"。所以在命名空间里放变量，本质上就是放了一个全局变量，只是它的名字被限定在命名空间里——需要全局状态时这样写比散落的全局变量清楚得多，但**全局状态本身要小心**，这一点在前面的章节里已经反复强调过。

## 5 可以反复打开、可以嵌套、可以起别名

命名空间有三个很实用的性质。

**第一，同一个命名空间可以在文件里多处打开。** 例程 `ch44_namespaces\namespace_split\namespace_split.cpp` 里，`app` 被打开了两次：

```cpp
namespace app
{
    void start()
    {
        std::cout << "app::start（第一次打开命名空间时写的）" << std::endl;
    }
}

namespace app
{
    void stop()
    {
        std::cout << "app::stop（第二次打开同一个命名空间时写的）" << std::endl;
    }
}
```

`start` 和 `stop` 是在两个不同的地方写进去的，但它们属于同一个 `app`，都用 `app::` 访问。实测输出：

```text
=== Demo A: 同一个命名空间在多处被打开 ===
app::start（第一次打开命名空间时写的）
app::stop（第二次打开同一个命名空间时写的）
```

**这条性质解释了标准库是怎么做出来的**：`std` 命名空间分散在几十个头文件里，每个头文件各自打开 `std` 往里放东西（`<iostream>` 放 `cout`、`<vector>` 放 `vector`、`<thread>` 放 `thread`），最后拼成一个完整的 `std`。如果没有"可反复打开"这条规则，标准库就得挤在一个文件里。

**第二，命名空间可以嵌套**，用来把实现细节和对外接口分层：

```cpp
namespace geometry
{
    namespace detail
    {
        double square(double value)
        {
            return value * value;
        }
    }
}
```

`detail` 这个名字只在 `geometry` 内部可见，完整的名字写作 `geometry::detail::square`。

**第三，太长的名字可以起别名**：

```cpp
namespace gd = geometry::detail;
```

别名只是同一个实体的另一个叫法——它**不产生新的命名空间，也不复制任何东西**。上面三点的实测输出：

```text
=== Demo C: 嵌套命名空间与命名空间别名 ===
geometry::detail::square(3) = 9
gd::square(4) = 16
```

## 6 using 声明与 using 指令

每次都写 `geometry::circleArea(...)` 未免啰嗦，C++ 提供了两种省事的写法，但它们的影响范围差别很大，必须分清楚。

**`using` 声明（using-declaration）：只引入一个名字。**

```cpp
using geometry::circleArea;

std::cout << "circleArea(1) = " << circleArea(1.0) << std::endl;
```

它把 `circleArea` 这一个名字带进**当前作用域**（上面写在 `main` 函数体里，所以只在 `main` 里有效）。实测输出：

```text
=== Demo D: using 声明把某个名字引入当前作用域 ===
circleArea(1) = 3.14159
```

因为它只引入一个名字，和已有的名字撞车的机会很小，是**推荐**的省事方式。

**`using` 指令（using-directive）：把整个命名空间的名字都带进来。**

```cpp
using namespace app;
```

例程 `namespace_split.cpp` 把它写在一对花括号里，实测：

```text
=== Demo B: using 指令只在它所在的作用域内生效 ===
花括号内可以直接写 start()：app::start（第一次打开命名空间时写的）
出了花括号就必须写全名：app::start（第一次打开命名空间时写的）
```

出了花括号 `start()` 就不认识了，必须写回 `app::start()`——**它的作用范围就是它所在的那个作用域**，这一点和上面的 `using` 声明一致。

那么风险在哪里？在于它把**所有**名字都带进来，而这些名字可能与已有的名字撞车。例程 `namespace_basic.cpp` 的 `main` 里加一句 `using namespace a;` 之后，原来那句 `print();` 就变成了：

```text
error: call of overloaded 'print()' is ambiguous
    • candidate 1: 'void a::print()'
    • candidate 2: 'void print()'
```

编译器找到了两个都叫 `print`、都没有参数的候选，无法决定用哪一个，于是**在歧义面前放弃编译**——这正是第 09 章重载解析里讲过的"歧义即错误"的另一种表现形式。变量也一样：全局有一个 `counter`、命名空间里也有一个，加一句 `using namespace` 之后读 `counter` 会得到

```text
error: reference to 'counter' is ambiguous
```

把这张对比表记下来就够了：

| 写法 | 引入什么 | 生效范围 | 风险 |
| --- | --- | --- | --- |
| `using geometry::circleArea;` | 一个指定的名字 | 它所在的作用域 | 很小，名字明确 |
| `using namespace app;` | 该命名空间里的所有名字 | 它所在的作用域 | 可能与已有名字歧义，或在包含这个头文件的别的文件里产生意外 |

**实践上的结论**：`using namespace` 写在**函数体内部**（越靠近使用处越好）风险可控；写在**文件开头（全局作用域）、尤其是写在头文件里**则影响面很大——头文件会被很多源文件包含，等于在别人不知情的情况下往他们的作用域里塞进一堆名字。本课程从第 01 章起一直老老实实写 `std::cout` 而不写 `using namespace std;`，原因就在这里。

## 7 动手实验

例程在 `E:\CPP_Code\CppFromScratch\ch44_namespaces\` 下，三个程序各占一个文件夹，每个 `.cpp` 都是单文件自包含的。编译命令模板（先 `cd` 进例程目录）：

```text
E:\msys64\ucrt64\bin\g++.exe -std=c++20 -Wall -g namespace_basic.cpp -o namespace_basic.exe
./namespace_basic.exe
```

### 7.1 实验一：`namespace_basic` 同名函数与作用域解析运算符

`namespace_basic\namespace_basic.cpp` 里有一个全局的 `print` 和一个 `namespace a` 里的 `print`，`main` 里分别用不加限定、`a::print()`、`::print()` 三种方式调用。

**预期输出**（逐字符与实测一致，每次运行都相同）：

```text
=== Demo A: 不带限定地调用 print() ===
来自全局命名空间：Hello C++
=== Demo B: 用作用域解析运算符指定命名空间 ===
来自命名空间 a：Hello C++
=== Demo C: ::print() 明确从全局命名空间找 ===
来自全局命名空间：Hello C++
```

**验收标准**：输出与上面逐字符一致；编译时 `-Wall` 没有警告。

**改值实验一（注释掉全局的那个）**：把全局的 `print` 函数整体注释掉，重新编译。**先预测**会发生什么，再看结果。实测报错（第一处）：

```text
error: 'print' was not declared in this scope; did you mean 'a::print'?
note: 'a::print' declared here
```

这句话正好说明了第 2.1 节的规则：**命名空间里的名字不会自动进入全局查找**，`a::print` 不会因为"没有别的候选"就被选中，编译器只是提示你"是不是想写 `a::print`"。另外 Demo C 那一行的 `::print();` 也会报错，内容是 `error: '::print' has not been declared`——因为全局命名空间里确实已经没有 `print` 了。看完请把全局的 `print` 恢复。

**改值实验二（再加一个同名的）**：在文件里再加一个全局函数

```cpp
void print()
{
    std::cout << "第二个全局 print" << std::endl;
}
```

重新编译，实测报错：

```text
error: redefinition of 'void print()'
note: 'void print()' previously defined here
```

这就是本章开头那个问题本身。**命名空间能解决的正是它**：把新函数放进另一个命名空间（例如 `namespace b`）就没事了。看完请把这第二个全局 `print` 删掉。

**改值实验三（制造歧义）**：在 `main` 里 Demo A 那句 `print();` **之前**加一句 `using namespace a;`，重新编译。实测报错：

```text
error: call of overloaded 'print()' is ambiguous
```

两个 `print` 现在都出现在查找范围里（一个来自全局，一个来自 `using` 指令），编译器无法选择。把 `using namespace a;` 删掉即可恢复。这个实验说明的是第 6 节的结论：**`using namespace` 会把整个命名空间的名字带进当前作用域，代价是可能产生歧义。**

### 7.2 实验二：`namespace_types` 变量、结构体、类与嵌套、别名

`namespace_types\namespace_types.cpp` 里全局、`geometry`、`acme` 各有一个 `point`，`geometry` 里还有 `pi`、`circleArea` 和嵌套的 `detail`。

**预期输出**（逐字符与实测一致，每次运行都相同）：

```text
=== Demo A: 三个同名的 point 是三个互不相同的类型 ===
全局的 point：整点 (1, 2)
geometry::point：浮点坐标 (1.5, 2.5)
acme::point：三维点 (1, 2, 3)
=== Demo B: 命名空间里的变量与函数 ===
geometry::pi = 3.14159
geometry::circleArea(2) = 12.5664
=== Demo C: 嵌套命名空间与命名空间别名 ===
geometry::detail::square(3) = 9
gd::square(4) = 16
=== Demo D: using 声明把某个名字引入当前作用域 ===
circleArea(1) = 3.14159
```

**验收标准**：输出与上面逐字符一致；`-Wall` 无警告。

**改值实验**：把 Demo A 里 `geometry::point precise {1.5, 2.5};` 的初值改成 `{3, 4}`，**先预测**输出，再重新编译运行。预期第二行变成 `geometry::point：浮点坐标 (3, 4)`（整数能放进 `double` 成员），其余各行不变——实测正是如此。

再试一个更"越界"的改法：把 `point plain {1, 2};` 改成 `point plain {1.5, 2.5};`。这次**编译就通不过**，实测报错：

```text
error: narrowing conversion of '1.5e+0' from 'double' to 'int' [-Wnarrowing]
```

原因是全局那个 `point` 的成员是 `int`，而 `1.5` 是 `double`：第 03 章讲过用花括号初始化**不允许会丢失信息的窄化转换**，所以编译器直接拦下来。要存小数就得让成员是 `double`（这正是 `geometry::point` 存在的意义），或者显式写 `static_cast<int>(1.5)` 把意图说清楚。看完请把初值改回 `{1, 2}`。

**作用域实验**：把 `using geometry::circleArea;` 从 `main` 里挪到文件顶部（全局作用域），重新编译。实测照样通过、输出不变——因为它只引入一个名字，影响面小；再把它换回 `main` 里体会一下两种作用范围的区别。

### 7.3 实验三：`namespace_split` 反复打开与 `using` 指令的作用范围

`namespace_split\namespace_split.cpp` 里 `app` 被打开两次（一次放 `start`、一次放 `stop`），`main` 里在一对花括号内使用 `using namespace app;`，最后用 `::status()` 访问全局函数。

**预期输出**（逐字符与实测一致，每次运行都相同）：

```text
=== Demo A: 同一个命名空间在多处被打开 ===
app::start（第一次打开命名空间时写的）
app::stop（第二次打开同一个命名空间时写的）
=== Demo B: using 指令只在它所在的作用域内生效 ===
花括号内可以直接写 start()：app::start（第一次打开命名空间时写的）
出了花括号就必须写全名：app::start（第一次打开命名空间时写的）
=== Demo C: 全局作用域运算符 :: ===
::status() 找到的是全局命名空间里的函数
```

**验收标准**：输出与上面逐字符一致；`-Wall` 无警告。

**改值实验**：把 `using namespace app;` 从花括号里挪到 `int main()` **之前**（也就是全局作用域），并删掉那对花括号以及"出了花括号就必须写全名"那一行。**先预测**，再重新编译运行。实测程序照样编译通过、`app::start` 与 `app::stop` 都正常输出——`using` 指令在全局作用域里对后面所有代码都有效。比较一下两个版本：**指令的位置决定了它的影响面，而影响面越大越容易撞名**，这就是第 6 节建议"把它写在函数内部"的原因。做完请改回原来的写法。

## 8 常见错误与排查

| 报错或现象 | 原因 | 处理 |
| --- | --- | --- |
| `error: redefinition of 'void print()'`（常跟 `note: 'void print()' previously defined here`） | 同一个作用域里出现了两个同名同签名的函数；函数体不同不算区分 | 把其中一个放进自定义命名空间，用 `a::print` 访问它 |
| `multiple definition of 'print()'`（后面是 `collect2.exe: error: ld returned 1 exit status`） | 两个源文件里各有一个同名同签名的函数，链接时才被发现 | 同上；"放到不同文件"不能解决冲突，命名空间才可以 |
| `error: 'print' was not declared in this scope; did you mean 'a::print'?` | 想调用命名空间里的函数却漏写了限定名 | 写全 `a::print()`；或先用 `using a::print;` 把这个名字引入当前作用域 |
| `error: call of overloaded 'print()' is ambiguous` | 用了 `using namespace` 之后，当前作用域里有两个同名候选 | 删掉 `using namespace`，改用 `using a::print;` 或写全限定名 |
| `error: reference to 'counter' is ambiguous` | 变量名同样被 `using namespace` 带进了当前作用域，与已有变量重名 | 与上一条相同；变量也可以用限定名写清来源 |
| `error: 'nope' is not a member of 'geometry'` | 命名空间名写对了，但里面没有这个名字（拼写错、或该名字在另一个命名空间里） | 核对限定名里的每一段；确认名字确实定义在那个命名空间里 |
| `error: 'b' has not been declared` | 用了不存在的命名空间名（例如 `b::print()` 而 `b` 没定义） | 检查命名空间的拼写与定义位置；先定义后使用 |
| `error: 'cout' was not declared in this scope; did you mean 'std::cout'?` | 忘了写 `std::`（或者没包含 `<iostream>`） | 补上 `std::`；本章实验里"注释掉全局 `print`"的报错是同一个道理 |
| 改了命名空间里的函数名，调用处却没跟着改 | 限定名里的名字必须与定义处完全一致 | 一起改；把 `namespace` 里的名字当作"带前缀的名字"来理解就不容易漏 |
