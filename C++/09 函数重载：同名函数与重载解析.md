## 学习目标

完成本章后，你应当能够：

1. 说明为什么"功能相同、只处理不同类型数据"的函数应当共用同一个名字。
2. 写出两个同名函数，并说出编译器依据实参的哪些信息在它们之间选择。
3. 列出构成函数签名的三部分，并解释返回值类型为什么不能用来区分重载。
4. 按精确匹配、类型提升、类型转换的优先顺序预判一个调用会选中哪个重载。
5. 看懂"无法转换""调用有歧义""重定义"这三类与重载相关的报错。

## 1 名字应该描述"做什么"，而不是"处理哪种类型"

第 08 章的 `printArray` 只能打印 `std::array<int, 3>`。现在多一个需求：把 `std::array<float, 3>` 也打印出来。

最直接的做法是复制一份、改掉参数类型：

```cpp
void printIntArray(std::array<int, 3> array);
void printFloatArray(std::array<float, 3> array);
```

这样写能跑通，语法上没有任何问题。**代价不在代码里，而在使用者的脑子里**：调用的人必须记住"打印 int 数组要用哪个名字、打印 float 数组要用哪个名字"。而且需求会继续膨胀——今天加 `float`，明天加 `double`、加 `char`，名字就变成 `printIntArray`、`printFloatArray`、`printDoubleArray`……一套功能拖着四个名字。

问题的根源在于：**我们把"类型"编进了名字里**。而类型信息本来就写在实参上，不需要再复制到函数名里：

```cpp
std::array<float, 3> myFloatArray {1.1f, 2.2f, 3.3f};
printFloatArray(myFloatArray);   // 类型在实参里已经说清楚了，函数名里又重复一遍
```

C++ 给出的方案是：**允许几个函数共用同一个名字，由编译器根据实参去挑该调用哪一个。** 这个机制叫**函数重载**（function overloading），编译器挑版本的过程叫**重载解析**（overload resolution）。于是函数名回到它该有的样子——只描述做什么：

```cpp
std::array<int, 3> myIntArray {1, 2, 3};
std::array<float, 3> myFloatArray {1.1f, 2.2f, 3.3f};

printArray(myIntArray);      // 编译器选中处理 int 数组的那一份
printArray(myFloatArray);    // 编译器选中处理 float 数组的那一份
```

这也是第 08 章"把重复代码提取成函数"的延续：那一次消除的是**语句的重复**，这一次消除的是**名字的重复**。

## 2 用同一个名字写两个函数

例程 `E:\CPP_Code\CppFromScratch\ch09_overloading\overload_basic\overload_basic.cpp` 把上一节的设想写了出来：

```cpp
void printArray(std::array<int, 3> array)
{
    for (auto value : array)
    {
        std::cout << value << " ";
    }

    std::cout << std::endl;
}

void printArray(std::array<float, 3> array)
{
    for (auto value : array)
    {
        std::cout << value << " ";
    }

    std::cout << std::endl;
}
```

两个函数同名 `printArray`，参数列表里的类型一个是 `std::array<int, 3>`、一个是 `std::array<float, 3>`。编译、链接、运行都没有问题，`main` 里只需照常调用：

```cpp
std::cout << "=== Demo A: one name, two overloads ===" << std::endl;

printArray(myIntArray);
printArray(myFloatArray);
```

```text
=== Demo A: one name, two overloads ===
1 2 3 
1.1 2.2 3.3 
```

（两行数字后面各有一个空格，因为函数体是"元素 + 空格"逐个数打印的，最后一个元素后面也带一个空格。）

**怎么确认编译器真的调用了两个不同的函数，而不是碰巧把两行都打印成了同一个结果？** 把两个函数体改成截然不同的内容，比如让第二个函数打印别的字，重新编译运行，两行输出就会明显不同。更彻底的验证是**删掉其中一个函数**再编译——`printArray(myFloatArray)` 立刻报错，这说明那一行确实依赖着被删掉的那个版本，两个调用走的是两份不同的代码（动手实验 6.4 就是做这件事）。

## 3 函数签名：编译器靠什么区分两个同名函数

编译器判断"这两个同名函数是不是同一个"依据的是**函数签名**（function signature）。对普通函数来说，签名由三部分构成：

| 是否参与签名 | 内容 | 说明 |
| --- | --- | --- |
| 参与 | 函数名 | 名字不同就是两个函数，与重载无关 |
| 参与 | 参数的**个数** | `f(int)` 与 `f(int, int)` 是两个函数 |
| 参与 | 参数的**类型**（含顺序） | `f(int, double)` 与 `f(double, int)` 是两个函数 |
| **不参与** | 返回值类型 | 只有返回值类型不同 → 编译错误 |
| **不参与** | 参数名 | `f(int a)` 与 `f(int b)` 是同一个函数 |
| **不参与** | 函数体 | 函数体写得完全一样，也是同一个签名 |

**返回值类型不参与签名**这一条最容易记反。它的理由很实际：**调用处通常用不上返回类型来消歧**。看这两行：

```cpp
printArray(myIntArray);   // 返回值被丢掉，这里根本没有"要什么类型"的信息
auto value = pick();      // 如果 pick() 有两个只差返回类型的版本，这里该选哪个？
```

第一行里返回值压根没被使用，第二行里 `auto` 的含义恰恰是"由函数决定"。如果允许返回类型参与重载，编译器在大多数调用点上都找不到任何依据来选版本，所以标准直接规定：**两个函数声明如果只差返回类型，不能构成重载**。在 GCC 下这会产生这样一条错误：

```text
error: ambiguating new declaration of 'double area(int)'
note: old declaration 'int area(int)'
```

（`ambiguating` 的意思是"造成歧义"，是 GCC 对"同名同参、只差返回类型"这种情况的固定说法。）

顺带一提，函数体不参与签名意味着：**函数体的重复并不构成重载的理由**。上一节的 `printArray` 两个版本函数体一模一样，那是重复代码，第 10 章会用函数模板把它合并成一份；这里之所以能写成两个函数，仅仅因为参数类型不同。

### 3.1 参数个数与顺序不同也算不同签名

例程 `ch09_overloading\overload_signature\overload_signature.cpp` 演示另外两种签名差异：

```cpp
// 参数个数不同：一个参数算正方形面积，两个参数算矩形面积
int area(int side)
{
    return side * side;
}

int area(int width, int height)
{
    return width * height;
}

// 参数个数与类型集合都相同，只是顺序相反
void combine(int first, double second)
{
    std::cout << "combine(int, double): " << first << " " << second << std::endl;
}

void combine(double first, int second)
{
    std::cout << "combine(double, int): " << first << " " << second << std::endl;
}
```

```text
=== Demo B: overloads differing in parameter count ===
area(4) = 16
area(3, 5) = 15
=== Demo C: overloads differing in parameter order ===
combine(int, double): 2 3.5
combine(double, int): 2.5 3
```

这里要提醒一句**能用不等于该用**：`combine(2, 3.5)` 与 `combine(2.5, 3)` 之间只差两个实参的先后，读代码的人极容易看错。参数顺序不同可以用来"区分"，但它**表达不了任何含义**；真正需要按含义区分的两个功能，应该给它们不同的名字，或者用不同的类型把含义写进签名里（后续章节的类型系统正是干这个的）。

## 4 重载解析：编译器怎么挑

当几个候选函数的参数类型都"差不多能接受"同一个实参时，编译器不会随便挑，而是给每个实参到形参的转换打一个等级，等级高的胜出。等级从高到低是：

1. **精确匹配**（exact match）：实参类型与形参类型一致。`int` 到 `int`、`double` 到 `double` 都属于这一级；可以忽略的顶层 `const` 之类的小差别也算精确匹配。
2. **类型提升**（promotion）：不丢有效位的"加宽"，例如 `char`、`short` 到 `int`，`float` 到 `double`。规则上它比第 3 级"更好"。
3. **类型转换**（conversion）：其余能编译通过的类型转换，例如 `int` 到 `double`、`double` 到 `int`——**可能丢信息**，是三级里最低的。

例程 `ch09_overloading\overload_resolution\overload_resolution.cpp` 只有 `show(int)` 与 `show(double)` 两个版本，但每个调用都能明确落在某一级上，于是"选谁"完全由规则决定：

```cpp
show(7);       // 精确匹配 show(int)
show(7.5);     // 精确匹配 show(double)
show('A');     // char -> int 是提升，char -> double 是转换，选 show(int)
show(2.5f);    // float -> double 是提升，float -> int 是转换，选 show(double)
show(small);   // small 是 short：short -> int 是提升，选 show(int)
```

```text
=== Demo D: exact match wins ===
show(int) <- 7
show(double) <- 7.5
=== Demo E: promotion beats conversion ===
show(int) <- 65
show(double) <- 2.5
show(int) <- 4
```

两处值得停下来看：

- `show('A')` 打印的是 `65`：`'A'` 走的是整型提升变成 `int`（`char` 的编码值就是 65），**没有**被当成浮点数。
- `show(2.5f)` 打印的是 `2.5`：`float` 走的是浮点提升变成 `double`，**没有**被截成整数。许多人凭直觉以为"`2.5f` 是 float，`show(int)` 也是数字，可能选 int"，实际上"提升优于转换"这条规则把它稳稳地送到了 `show(double)`。

**只有当没有任何一个候选比其他候选更好（或者几个候选打平）时**，编译器才报"调用有歧义"并拒绝编译。这也是重载设计的一条实用准则：**让各个版本在实参上互相"不亲近"**。如果两个版本都只能靠隐式转换接受同一个实参，就很容易踩到歧义，或者更糟——猜错版本。

## 5 让重载可用的两条前提

**前提一：参与选择的候选必须是"在调用点已经看见的"。** 编译器是从上往下读源文件的，如果某个重载写在调用点之后，它在那个位置还不存在。第 08 章讲过"先定义、后使用"，重载的情形会更迷惑人：函数名已经能在上文找到，编译器于是只用看得见的那个版本去匹配实参，报出来的错是"转换不了"，而不是"没有这个函数"：

```text
error: could not convert 'myFloatArray' from 'array<float,[...]>' to 'array<int,[...]>'
```

**前提二：不要指望隐式转换替你找版本。** 隐式转换会让"看起来不匹配"的调用也能编过，从而悄悄选到一个你不想要的版本。例如只有 `show(int)` 与 `show(double)` 时写 `show(3u)`（`unsigned int`）：`unsigned int` 到 `int` 和到 `double` 都是普通转换，等级相同，于是编译器报歧义：

```text
error: call of overloaded 'show(unsigned int)' is ambiguous
```

歧义不是"编译器不够聪明"，而是在说：**代码的意图不明确**。这类错误必须靠改代码消除（加显式类型转换、或者给这个类型专门写一个重载），而不是靠调整参数顺序去绕过。

## 6 动手实验

例程都在 `E:\CPP_Code\CppFromScratch\ch09_overloading\` 下，三个程序各占一个文件夹，每个 `.cpp` 都是自包含的单文件。

### 6.1 实验一：重载的基本形态

`overload_basic\overload_basic.cpp`：两个同名 `printArray`，`main` 里对 int 数组与 float 数组各调用一次。

```text
cd "E:/CPP_Code/CppFromScratch/ch09_overloading/overload_basic"
"E:/msys64/ucrt64/bin/g++.exe" -std=c++20 -Wall -g overload_basic.cpp -o overload_basic.exe
./overload_basic.exe
```

**预期输出**（注意每行末尾都有一个空格）：

```text
=== Demo A: one name, two overloads ===
1 2 3 
1.1 2.2 3.3 
```

**验收标准**：两行数据分别是 `1 2 3 ` 和 `1.1 2.2 3.3 `（含行末空格），编译 `-Wall` 无警告。

**改值实验**：把 `myFloatArray` 的初值改成 `{4.5f, 5.5f, 6.5f}`，先自己预测第二行输出，再重新编译运行，应得到：

```text
=== Demo A: one name, two overloads ===
1 2 3 
4.5 5.5 6.5 
```

第一行完全不受影响——因为两份函数的函数体各自独立，改动只落在被改的那个实参上。

### 6.2 实验二：参数个数与参数顺序

`overload_signature\overload_signature.cpp`：`area` 有 1 参数和 2 参数两个版本，`combine` 有参数顺序相反的两个版本。

```text
cd "E:/CPP_Code/CppFromScratch/ch09_overloading/overload_signature"
"E:/msys64/ucrt64/bin/g++.exe" -std=c++20 -Wall -g overload_signature.cpp -o overload_signature.exe
./overload_signature.exe
```

**预期输出**：

```text
=== Demo B: overloads differing in parameter count ===
area(4) = 16
area(3, 5) = 15
=== Demo C: overloads differing in parameter order ===
combine(int, double): 2 3.5
combine(double, int): 2.5 3
```

**验收标准**：输出与上面逐行一致，`-Wall` 无警告。**改值实验**：把 `area(4)` 改成 `area(6)`，应输出 `area(6) = 36`；把 `combine(2, 3.5)` 改成 `combine(2.0, 3.5)` 后重新编译，两个实参都成了 `double`，第一个版本要把 `3.5` 转成 `int`、第二个版本要把 `2.0` 转成 `int`，两个候选打平，于是编译失败：

```text
error: call of overloaded 'combine(double, double)' is ambiguous
```

这也是"参数顺序相反"这种重载的真实风险：一旦调用处的实参类型和签名差一点，它就从"能编过"直接掉进"歧义"。看完把这一行还原。

### 6.3 实验三：重载解析的取舍顺序

`overload_resolution\overload_resolution.cpp`：只有 `show(int)`、`show(double)`，靠实参的类型落在不同的转换等级上来决定选中谁。

```text
cd "E:/CPP_Code/CppFromScratch/ch09_overloading/overload_resolution"
"E:/msys64/ucrt64/bin/g++.exe" -std=c++20 -Wall -g overload_resolution.cpp -o overload_resolution.exe
./overload_resolution.exe
```

**预期输出**：

```text
=== Demo D: exact match wins ===
show(int) <- 7
show(double) <- 7.5
=== Demo E: promotion beats conversion ===
show(int) <- 65
show(double) <- 2.5
show(int) <- 4
```

**验收标准**：五行调用分别落在 `show(int)`、`show(double)`、`show(int)`、`show(double)`、`show(int)` 上，与预期输出一致。

**改值实验**：把 `show(7);` 改成 `show(7.0);`，其余不动。`7.0` 是 `double`，精确匹配 `show(double)`，因此第一行会变成 `show(double) <- 7`。再把 `show(2.5f);` 改成 `show(2.5);`，输出仍是 `show(double) <- 2.5`：前者靠浮点提升、后者精确匹配，**路径不同但都落在 `show(double)` 上**。这说明"选中哪个版本"与"做了哪种转换"是两件事——输出看起来没变，不代表编译器走的还是原来那条路。

### 6.4 实验四：三类失败现场

三处改动各自独立，做完一处看到报错就还原，再试下一处。

1. **删掉 float 那个重载**（把第二个 `printArray` 整个删掉），重新编译 `overload_basic.cpp`，应看到：

```text
error: could not convert 'myFloatArray' from 'array<float,[...]>' to 'array<int,[...]>'
```

   这正好证明 `printArray(myFloatArray)` 原本调用的就是被删掉的那一份，而不是 int 版本。看完还原。

2. **把 int 那个重载原样复制一份、只改函数体**（例如让第二份打印 `hello world`），重新编译，应看到：

```text
error: redefinition of 'void printArray(std::array<int, 3>)'
note: 'void printArray(std::array<int, 3>)' previously defined here
```

   **函数体不同也救不了重复的签名**：编译器在参数列表这一层就分不出该调用哪一个，于是直接判定为同一个函数的重复定义。看完还原。

3. **在 `overload_resolution.cpp` 的末尾加一句 `show(3u);`**，重新编译，应看到：

```text
error: call of overloaded 'show(unsigned int)' is ambiguous
```

   看完删掉这一句。亲手见一次歧义报错，将来看到它就知道该去找"哪个实参有两个同样好的候选"，而不是去怀疑编译器。

## 7 常见错误与排查

| 报错或现象 | 原因 | 处理 |
| --- | --- | --- |
| `error: could not convert 'myFloatArray' from 'array<float,[...]>' to 'array<int,[...]>'` | 没有与实参类型匹配的重载，编译器只能拿参数类型不同的版本去试 | 检查实参类型；需要支持这个类型就给一份对应参数类型的重载，或确认是否漏写了 / 把某个重载写到了调用点之后 |
| `error: redefinition of 'void printArray(std::array<int, 3>)'` | 两个同名函数的参数类型完全一致，函数体不同也算同一个签名 | 让参数列表真正不同；若只是函数体重复，应该合并成一份（第 10 章的模板） |
| `error: ambiguating new declaration of 'double area(int)'` | 两个函数只差返回值类型 | 返回值类型不参与签名；改成不同的参数列表，或换一个函数名 |
| `error: call of overloaded 'show(unsigned int)' is ambiguous` | 多个候选需要的转换等级相同，没有唯一最佳 | 给该类型单独写一个重载，或在调用处用显式类型转换（如 `show(static_cast<int>(x))`）把意图写清楚 |
| `error: 'printIntArray' was not declared in this scope` | 函数定义写在了调用之后（第 08 章的老问题） | 把定义挪到调用之前 |
| 调用点报"转换不了"，但文件下面明明有匹配的重载 | 那个重载写在调用点之后，在本行还不可见 | 把重载的声明/定义移到调用之前 |
| 函数体重写了一遍却"没有报错"，但两个版本行为不一致 | 两个重载的函数体各自独立，改了一处另一处不会跟着变 | 这是重载的固有代价；把重复的函数体合并掉（第 10 章函数模板） |
| `warning: no return statement in function returning non-void` | 某个重载版本漏写了 `return`（第 08 章的坑） | 逐条看完 `-Wall` 的警告，补上 `return` |
