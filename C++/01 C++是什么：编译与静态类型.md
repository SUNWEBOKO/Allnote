## 1 从一句话认识 C++

要描述 C++，一句话就够了：**C++ 是一种静态类型的编译语言**。

这句话很短，但它定下了后面所有内容的基调。程序里写的每一行代码最终都要变成处理器能执行的指令，而"编译"和"静态类型"分别规定了这件事在什么时候、以什么方式发生：编译决定了**你的源码必须先被翻译成可执行文件才能运行**；静态类型决定了**每个值的类型必须在翻译完成之前就确定下来**。本章把这两个词拆开讲清楚，然后写出、编译、运行第一个 C++ 程序。

配套例程在 `E:\CPP_Code\CppFromScratch\ch01_what_is_cpp\`，分 `main\` 和 `exit_code\` 两个文件夹，本章最后会逐个跑通。

## 2 编译语言：源码不是可以直接运行的东西

### 2.1 编译语言与解释语言的区别

在 Python 这类语言里，你写完 `print("hi")` 保存成 `.py`，直接用 Python 解释器运行它，解释器一边读一边执行，源码本身就是要运行的东西。

C++ 不是这样。你写出来的 `.cpp` 文件只是**给人看的文本**，处理器不认识它，操作系统也不认识它。要让它跑起来，必须先交给一个叫**编译器**（compiler）的程序，把它翻译成机器能执行的**可执行文件**。翻译发生在运行之前，是一次性的；一旦可执行文件生成好了，再运行它就不需要编译器参与了。

这个差别带来两个直接后果，后面会反复用到：

- **运行之前就能发现一部分错误。** 语法错误、类型不匹配这类问题在翻译阶段就会被编译器挡下来，程序根本不会开始运行。
- **改了源码不会自动生效。** 因为可执行文件是上一次翻译的结果，源码改了必须重新翻译一遍。这是第 5 节要专门讲的一个高频困惑。

### 2.2 从源码到可执行文件要经过四步

编译器驱动（我们是 `g++`）把源码变成可执行文件，中间经过四个阶段：

| 阶段 | 做什么 | 产物 |
| --- | --- | --- |
| 预处理 | 展开 `#include`、处理宏和条件编译指令 | 展开后的完整源码 |
| 编译 | 把 C++ 代码翻译成汇编代码，并做语法和类型检查 | 汇编代码 |
| 汇编 | 把汇编代码翻译成机器指令 | 目标文件（`.o` / `.obj`） |
| 链接 | 把若干目标文件和标准库拼成一个完整的可执行文件 | 可执行文件（`.exe`） |

平时的报错主要来自中间两步，而"某个名字找不到"这类错误往往发生在链接阶段——第 6 节的排查表里会区分它们。

要提醒的是，`g++` 只是一个**驱动**：它按顺序调用预处理器、编译器本体、汇编器和链接器，把四步串起来。你只敲一条命令，四步都在后台完成了。

### 2.3 编译器与标准库的分工

编译器只负责翻译你的代码，语言本身还带一个**标准库**：容器、算法、输入输出等常用功能都已经写好，你直接用即可。本课程后面用到的 `std::cout`、`std::array` 都来自标准库，用法是"包含对应头文件 + 调用其中的设施"。

## 3 静态类型：每个值都有类型

### 3.1 类型说明这个值是什么

程序里到处是值：`0` 是值，`3.14` 是值，一段文字也是值。在 C++ 里，**每一个值都属于某个类型**，类型告诉你这个值在表示什么——是整数，是带小数的浮点数，是"真/假"，还是一段字符。

### 3.2 类型决定能对值做哪些运算

类型不只是标签，它还决定了这个值能参与哪些运算、这些运算又是什么意思。例如两个整数可以相加、取余；两个字符串可以拼接。**类型不对，运算就写不出来**——`"abc" - 1` 这种写法编译器会直接拒绝，因为字符串类型上根本没有"减法"这个约定。

这也是本课程后面反复出现的一种思维方式：看到一个值，先问"它是什么类型"，能做的操作、结果的类型、输出的形式就都跟着确定了。

### 3.3 静态：类型在编译期就固定下来

"静态"指的是时机。**类型必须在编译期确定，并且确定之后不能在运行期改变。** 一个变量被定义成整数，它在整个程序运行过程中就一直是整数，不会变成浮点数，也不会变成字符串。

这带来两个好处：

- **编译器能生成正确的机器指令。** 整数加法和浮点数加法在处理器上是不同的指令。编译器必须在编译期就知道是哪种，才能挑对指令。
- **错误能提前暴露。** 把字符串和整数直接相加这类错误在编译期就被发现，而不是等到运行到那一行才出问题。

整型、浮点、布尔、字符这些内置类型统称为**基础类型**，第 03 章会系统梳理它们；本章只需要记住"每个值都有类型、类型在编译期定死"。

## 4 最简的 C++ 程序：main 函数

`E:\CPP_Code\CppFromScratch\ch01_what_is_cpp\main\main.cpp` 是能写出来的最短的 C++ 程序（去掉注释后只有三行）：

```cpp
int main()
{
    return 0;
}
```

这短短三行里包含了一个函数的全部组成部分，逐块拆开看：

| 成分 | 作用 |
| --- | --- |
| `int` | **返回类型**。这个函数执行完之后要交回一个整数。 |
| `main` | **函数名**。函数是"给一串代码起的名字"，调用这个名字就会执行函数体里的语句。 |
| `()` | **参数列表**。括号里是函数需要的输入；这里是空的，表示这个函数不接收任何输入。 |
| `{ }` | **函数体**。花括号里的语句就是调用这个函数时会真正执行的内容。 |
| `return 0;` | **返回语句**。`return` 是 C++ 的关键字，表示"结束函数并把后面的值交回去"；语句末尾的分号是 C++ 语句的结束标记，不能漏。 |

这里的 `main` 有一个特殊身份：**它是整个程序的执行起点**。可执行文件被加载运行时，操作系统会找到名为 `main` 的那个函数，从它函数体的第一条语句开始执行。所以不管 `main` 写在哪个源文件里、写在文件的哪个位置，程序都从它开始跑。一个程序必须有且只有一个 `main`，否则链接阶段会报错。

### 4.1 关键字与标识符

`int`、`return` 这类词是语言保留的**关键字**，有固定含义，不能拿来当变量名或函数名。反过来，`main`、`var_one` 这类你自己起的名字叫**标识符**，命名时要用能说明用途的英文，别用 `a1`、`x2` 这种过几天自己都看不懂的名字。

### 4.2 平台差异：可执行权限

课程视频在 Linux 下演示，`ls -l` 会看到可执行文件比源码多了一个执行权限位，运行时写 `./main`。**Windows 上没有这种权限位**，可执行文件以 `.exe` 结尾，运行时写上文件名即可。这是两个平台在"怎么运行"上的差别，不影响 C++ 代码本身。

## 5 动手实验：编译、运行、查看退出码

### 5.1 本机工具链

本机使用 MSYS2 的 UCRT64 工具链，编译器是 `g++` 16.1.0：

```text
E:\msys64\ucrt64\bin\g++.exe     编译器驱动：把 .cpp 翻译成 .exe
E:\msys64\ucrt64\bin\gdb.exe     调试器：F5 调试时使用
```

`E:\CPP_Code` 根目录下的 `.vscode` 已经替你把工程配好了，四件事都不用手动做：IntelliSense 指向 `g++`、C++ 标准是 `c++17`、集成终端的 `PATH` 里包含 `E:\msys64\ucrt64\bin`、调试配置用 `gdb` 启动当前文件生成的 `.exe`。

### 5.2 实验一：编译并运行最简程序

**材料与设置**：VS Code 打开文件夹 `E:\CPP_Code`（注意打开的是文件夹，不是单个文件，否则 `.vscode` 里的配置不生效）；打开 `E:\CPP_Code\CppFromScratch\ch01_what_is_cpp\main\main.cpp`。

**操作步骤与预期现象**，两种方式任选：

方式一（VS Code）：

1. 按 `Ctrl+Shift+B`，选择 `C++: 编译当前文件 (MSYS2 UCRT64)`。
2. 终端只有编译命令，**没有任何报错输出**，说明编译通过，同目录下出现 `main.exe`。
3. 按 `F5`（或选任务 `C++: 编译并运行当前文件`）运行它。

方式二（终端，在 Git Bash 或 PowerShell 里执行）：

```text
E:\msys64\ucrt64\bin\g++.exe -std=c++17 -Wall -g main.cpp -o main.exe
./main.exe
```

这时**屏幕上什么都不会出现**。这不是程序没跑起来，而是因为 `main` 里只有一句 `return 0;`——它除了结束程序，没有做任何输出。要确认它真的正常结束了，看退出码：

| 终端 | 查看上一条命令退出码 |
| --- | --- |
| cmd（命令提示符） | `echo %ERRORLEVEL%` |
| PowerShell | `echo $LASTEXITCODE` |
| Git Bash | `echo $?` |

看到 `0` 就表示程序正常结束。

**验收标准**：`main.exe` 生成成功；运行后无输出；退出码为 `0`。

### 5.3 实验二：把退出码改成 12

打开 `E:\CPP_Code\CppFromScratch\ch01_what_is_cpp\exit_code\exit_code.cpp`，它与实验一的唯一区别是把 `return 0;` 换成了 `return 12;`。

按同样的方式编译运行，然后查看退出码，这次得到的应该是 `12`。屏幕上依然什么都没有——**这个程序"说"的话不在屏幕上，而在退出码里**。

**验收标准**：退出码为 `12`，且屏幕无输出。

### 5.4 退出码是什么

上一节反复提到的"退出码"就是 `main` 返回值的去向。函数返回值交给操作系统之后，成为这个进程的**退出码**（exit code）：

- `0` 是约定俗成的"一切正常"；
- 非 `0` 表示出现了某种异常，具体含义由程序自己规定。

这就是为什么 `main` 的返回类型必须是 `int`：它需要一个整数把"这次运行的结果如何"汇报出去。批处理脚本、构建系统、自动化测试都是靠读取退出码来判断上一步是否成功，而不是靠屏幕输出——因为屏幕输出要人工看，退出码可以自动判断。

## 6 编译型语言的直接后果：改源码必须重新编译

现在回到第 2 节留下的那个问题。假设你打开 `main.cpp`，把 `return 0;` 改成 `return 12;` 保存，然后**直接再运行一次 `main.exe`**——得到的退出码仍然是 `0`。

原因很直白：`.exe` 是上一次编译的产物，它里面记的是上一次那份代码。你新写的源码对已经生成的 `.exe` 没有任何影响。必须重新执行一次编译命令，让编译器按新的源码生成新的 `.exe`。

这就是"编译型语言"最日常的后果，也是初学者最常见的困惑之一——**"我明明改了啊，怎么没反应"，十有八九是忘了重新编译**。VS Code 里的 `F5` 和"编译并运行"任务都带了"先编译"这一步，用它们就不会踩这个坑。

## 7 常见错误与排查

按"先工具链、再命令、最后代码"的顺序排查，效率最高。

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `'g++' 不是内部或外部命令` / `command not found` | 终端的 `PATH` 里没有编译器目录 | 用绝对路径 `E:\msys64\ucrt64\bin\g++.exe`，或从 VS Code 的集成终端里执行（工程已配好 `PATH`） |
| `g++: error: main.cpp: No such file or directory` | 当前目录不对，或文件名拼错 | 先 `cd` 到 `.cpp` 所在目录，再用 `ls` / `dir` 确认文件名 |
| 运行后无任何输出 | 本程序的 `main` 里确实没有输出语句 | 用退出码确认运行结果（见 5.2），不要把它当成失败 |
| 改了源码，运行结果却没变 | 没有重新编译 | 重新编译一次；不要直接运行旧的 `.exe` |
| `error: 'main' must return 'int'` | 返回类型写成了 `void` 或漏写 | `main` 的返回类型必须是 `int` |
| `undefined reference to 'main'` | 没有定义 `main`（链接阶段错误） | 补上 `main` 函数；注意大小写，`Main`、`mian` 都不行 |
| `error: expected ';' before '}' token` | 漏了分号 | 看编译器提示的行号，补上 `;` |

读编译器报错的方法：**从第一条开始修**。后面的一堆报错往往只是第一条错误的连锁反应，把第一条改对，其余的常常一起消失。GCC 的报错格式是 `文件名:行号:列号: error: 具体原因`，先看行号再读原因。
