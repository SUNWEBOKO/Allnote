## 1 从互斥锁到原子操作

第 42 章用一把锁解决了共享数据的并发访问：谁要动共享数据，谁就先进临界区，同一时刻只放一个线程进去。这个方法通用、可靠，但代价也很直接——**每个线程都要排队**，本来可以并行的部分被串行化了。

于是自然要问：有没有更轻的办法？考虑最普通的一种共享数据：一个计数器。多个线程各自把同一个计数器加一，除此之外什么也不做。对这种"单个变量上的单个操作"，C++ 提供了比锁更贴身的工具——**原子操作**（atomic operation）。

本章安排是先看清问题的本质（为什么三步操作会出错），再引入原子类型，最后划清"原子能做什么、不能做什么"的边界。

## 2 读-改-写与丢失更新

先把一句看起来最简单的代码拆开：

```cpp
counter += 1;
```

这行代码在机器层面不是"一步"，而是三步：

1. **读**：把 `counter` 当前的值从内存读到寄存器；
2. **改**：在寄存器里把它加一；
3. **写**：把结果写回 `counter` 所在的内存位置。

单线程里这三步紧挨着发生，没有人能插进来，所以看起来像一步。多线程里就不同了：**线程切换可以发生在任意两条指令之间**，也可能两个线程真的在不同核心上同时执行。假设 `counter` 当前是 0，两个线程各自执行一次 `counter += 1`：

| 时刻 | 线程 1 | 线程 2 | 内存里的 counter |
| --- | --- | --- | --- |
| 1 | 读到 0 |  | 0 |
| 2 |  | 读到 0 | 0 |
| 3 | 算出 0 + 1 = 1 |  | 0 |
| 4 |  | 算出 0 + 1 = 1 | 0 |
| 5 | 写回 1 |  | 1 |
| 6 |  | 写回 1 | 1 |

两个线程都做了"加一"，`counter` 却只从 0 变成 1。这就是**丢失更新**（lost update）：一次递增的效果被另一次覆盖了。

例程 `E:\CPP_Code\CppFromScratch\ch43_atomics\atomic_counter\atomic_counter.cpp` 的 Demo A 把这种交错的窗口**故意拉长**，让它每次运行都必然发生：

```cpp
int sharedValue = 0;

void slowIncrement()
{
    const int value = sharedValue;

    std::this_thread::sleep_for(std::chrono::milliseconds(20));

    sharedValue = value + 1;
}
```

读和写之间夹了 20 毫秒，第二个线程几乎必然在第一个线程写回之前就已经完成了"读"这一步。`main` 里启动两个这样的线程并汇合，实测输出（多次运行都相同）：

```text
=== Demo A: 把竞争窗口拉长，两个线程各递增 1 次 ===
期望值：2
实际值：1
结论：两次递增只留下一次的效果
```

**这份输出是要留下来的核对依据**：两次递增、结果却是 1，说明有一份被覆盖了。拉长窗口只是为了"让错误稳定出现"——真实程序里这个窗口可能只有几个时钟周期，所以同样的错误往往是偶发、难查的（这一点下一节会看到实测统计）。

## 3 数据竞争与未定义行为

上面这件事在标准里有一个名字。按 C++ 内存模型的说法：

> 如果一个表达式的求值要写某个内存位置，另一个表达式的求值要读或改同一个内存位置，这两个求值就是**冲突的**；如果程序里有两个冲突的求值、它们来自不同的线程、而又没有同步措施保证一个在另一个之前发生，那么这个程序就发生了**数据竞争**（data race）。**存在数据竞争的程序的行为是未定义的。**

标准同时给出了避免数据竞争的三种途径：

1. **让两个操作在同一个线程里**。单线程程序里不存在数据竞争——同一个线程内的操作天然有先后顺序。
2. **使用标准原子操作**。如果这些操作本身是原子的，它们就不再"冲突"，本章讲的就是这条路。
3. **建立发生顺序（先行关系）**。如果一个冲突操作保证在另一个之前发生，就不构成竞争。**加锁正是建立这种顺序的手段**：第 42 章里 `lock_guard` 保证同一时刻只有一个线程在临界区里，临界区之间的先后关系被锁排好了。

"未定义行为"这个词在第 03、18 章出现过，含义在这里比以往任何时候都重要：

- **它不等于"一定出错"**，而是"标准不再对结果作任何承诺"：可能算错，可能这次恰好算对，也可能以想不到的方式出错。
- 所以**"我运行了几次都对"完全不能证明代码没有数据竞争**。

用本章的例程可以亲手验证这件事。Demo B 让两个线程各循环 100000 次 `total += 1`（普通 `int`，不加任何保护），把 `timesPerThread` 的值改小再运行，会看到下面这样一组实测统计：

| 每个线程的循环次数 | 期望值 | 实测（运行次数） | 结果 |
| --- | --- | --- | --- |
| 100 | 200 | 10 次 | 10 次全部恰好等于 200 |
| 1000 | 2000 | 6 次 | 6 次全部恰好等于 2000 |
| 10000 | 20000 | 5 次 | 5 次全部恰好等于 20000 |
| 50000 | 100000 | 5 次 | 5 次全部恰好等于 100000 |
| 100000 | 200000 | 20 次 | 13 次小于 200000（如 152515、177667），7 次恰好等于 200000 |

这正是把丢失更新的窗口放大到极限时的后果：**循环次数少时，一个线程往往在另一个线程真正开始之前就跑完了，两次递增自然不重叠，结果"看起来完全正确"；循环次数一多，重叠的机会多了，错误才开始露面——而且即便在这个规模上，也仍有三分之一的运行看不出任何异常。**

视频里演示的正是这件事：循环 100 次时每次都得到正确结果，把次数加大以后结果开始在期望值以下波动。**要记住的结论是：存在数据竞争时结果不可信，而不是"小循环就没问题"。**

## 4 std::atomic：把三步变成一步

如果一个问题来自"读-改-写三步会被交错"，那么解决办法就是让这三步**不能再被拆开**。这就是原子操作的含义：**一个原子操作在执行过程中不可被分割，两个原子操作之间必定有一个先完成、另一个后完成，绝不会出现"都读到同一个旧值"的中间状态。**

C++ 把它做成了类型：`std::atomic<T>` 定义在头文件 `<atomic>` 里（cppreference 上关于原子操作的族系都列在这个头文件下）。把 Demo B 里的累加函数换成原子的版本：

```cpp
void addManySafe(std::atomic<int>& total, int times)
{
    for (int i = 0; i < times; ++i)
    {
        ++total;
    }
}
```

用法上的变化只有一处：**类型从 `int` 变成 `std::atomic<int>`**。`++`、`+=` 这些运算符原子类型都有，写法和普通整数一样，只是每一次运算都是不可分割的原子读-改-写。于是两个线程的 `++` 被排成了一个确定的前后顺序：

| 时刻 | 线程 1 | 线程 2 | 内存里的 total |
| --- | --- | --- | --- |
| 1 | 读到 0，加一，写回 |  | 1 |
| 2 |  | 读到 1，加一，写回 | 2 |

Demo C 的实测输出（多次运行都相同）：

```text
=== Demo C: 两个线程各递增 100000 次，用 std::atomic<int> ===
期望值：200000
实际值：200000
```

**每一次运行都精确等于期望值**，与 Demo A 的稳定复现错误、Demo B 的时对时错形成完整对照。注意这里**没有用锁**：同一个计数器由两个线程同时递增，但每一次递增都是原子的，所以不会互相覆盖。用"锁"和用"原子"都能消除这一类竞争，区别在于原子操作不需要线程排队等待临界区（对单个变量的单次操作尤其划算）。

顺便说一个相关的概念：原子类型在底层尽量用处理器提供的原子指令实现，这样的实现叫**无锁（lock-free）**。`std::atomic<int>::is_always_lock_free` 是一个编译期常量，用来问"这个类型是不是总是无锁实现"；例程 `atomic_ops.cpp` 打印的实测结果是：

```text
std::atomic<int> 是否总是无锁实现：是
```

如果某个类型太宽（远远超过机器字长），标准库可能不得不借助内部的锁来模拟原子性——那时"原子"仍然正确，只是可能不快。这个标志回答的正是这个问题，而**不影响正确性**。

## 5 原子类型与成员函数

整数、无符号整数等常见类型都有对应的别名，写法上比模板形式更短：

```cpp
std::atomic_int a {10};              // 等价于 std::atomic<int> a {10};
std::atomic_uint b {5u};             // 等价于 std::atomic<unsigned int>
std::atomic<long long> c {0};        // 没有专门别名时就用模板形式
```

访问原子变量的方式有两类，语义上有差别，值得分清楚。

**第一类是运算符**：`+=`、`-=`、`++`、`--` 以及按位运算 `&=`、`|=`、`^=`。它们读起来和普通整数一样，但每一次都是原子的。例程 `E:\CPP_Code\CppFromScratch\ch43_atomics\atomic_ops\atomic_ops.cpp` 里对 `a` 连续做了这些运算，实测输出：

```text
=== Demo A: 原子整数上的算术运算符 ===
a 初始值：10
a += 5 之后：15
a -= 3 之后：12
++a 之后：13
a 的值（--a 之后）：12
```

**第二类是成员函数**，它们能做运算符做不到的事：

| 成员函数 | 作用 | 需要留意的点 |
| --- | --- | --- |
| `load()` | 读出当前值 | 读这个动作本身也是原子的，不会读到"改到一半"的状态 |
| `store(v)` | 写入一个值 | 写入是原子的 |
| `fetch_add(n)` | 加 `n`，返回**加之前**的旧值 | "取出旧值再加"是一步完成的，可以当发号器用 |
| `fetch_sub(n)` | 减 `n`，返回旧值 | 同上 |
| `exchange(v)` | 写入 `v`，返回写入前的旧值 | 换值一步完成 |
| `compare_exchange_weak(expected, desired)` | 比较后写入：当前值等于 `expected` 才写入 `desired` 并返回 `true` | 第一个参数是引用，失败时会被回填成当前实际值 |

`fetch_add` 返回旧值这点很容易误判，例程专门把它打了出来：

```text
=== Demo B: fetch_add 交回的是加之前的旧值 ===
fetch_add(100) 交回：12
之后 a 的值：112
```

`++a` 这种写法在底层就是 `fetch_add(1)`，只是不要返回值而已。

`compare_exchange_weak` 是这几个成员函数里最需要理解的一个。它的意思是"**如果当前值还是我期望的那个，就把它换成新值**"，常用于"只在没人动过的情况下才更新"。它的第一个参数既是输入也是输出：**失败时会把当前实际值写回这个参数**，所以调用之后这个变量里可能已经不是你写的期望值了。例程把调用前后的值都打印出来，实测输出：

```text
=== Demo C: exchange 与 compare_exchange_weak ===
exchange(7) 交回：112
之后 a 的值：7
调用前：a = 7，期望值 = 7
compare_exchange_weak(把 7 换成 42) 是否成功：1
调用后：a = 42，期望值参数 = 7
```

这次期望值正好等于实际值，所以换成功了，`a` 变成 42。名字里的 `weak` 表示它**允许"假失败"**：即使值相等也可能返回 `false`（它在某些处理器上由两条指令组合实现），因此标准用法是把它放进一个循环里重试。**只要记住"失败时它会回填"，就不会被它搞得莫名其妙。**

最后一个必须知道的限制：**原子类型不可拷贝、不可移动**。它是"某个特定内存位置"的代表，拷贝一份就变成两个不同的原子变量了，所以编译器直接禁止这件事。要用它就得按引用传：

```cpp
std::atomic<int> total {0};
// 传给线程时按引用捕获（第 41 章的规则在这里同样适用）
myThreads.emplace_back([&total]() { /* ... */ });
```

## 6 什么时候用原子、什么时候必须用锁

原子操作看起来比锁轻便得多，但它能做的事比锁少得多。它保护的是**单个变量上的单次操作**，仅此而已。

| 场景 | 选择 | 原因 |
| --- | --- | --- |
| 一个计数器被多个线程各自加一 | `std::atomic<int>` | 单变量的单次读-改-写，原子操作正好覆盖 |
| 一个标志位被线程置位、被别的线程读取 | `std::atomic<bool>` | 同上，读写都是原子操作 |
| 把一个数按位设置/清除（如状态位） | 原子类型的 `\|=`、`&=` | 位运算同样是原子读-改-写 |
| 一段输出必须整行不被拆开 | 互斥锁 | 要保护的不是一个变量，而是"一串操作作为整体" |
| 两个变量之间必须保持某种关系（如第 42 章的"两个账户总额不变"） | 互斥锁 | 两次独立的原子操作之间仍可能被别的线程插进来，关系照样会被破坏 |
| 临界区里要读写多个变量、或者要调用别的函数 | 互斥锁 | 原子类型只能保护它自己那一次操作 |

把这张表压成一句话：**原子操作保证"这一个变量上的这一次操作"完整，锁保证"这一段代码"独占**。选哪种，取决于你要保护的东西是一个变量，还是一段逻辑。

需要强调的是：**用原子操作替换锁，只有在"共享数据恰好只是一个变量、且对它的每一次访问都是单次操作"时才成立**。如果你把第 42 章的转账例子里的两个 `balance` 都改成原子变量，各扣各加，那么"总额不变"这个不变量一样会被破坏——因为两次原子操作之间仍然存在空隙。这种时候必须回到互斥锁。

### 7.1 实验一：`atomic_counter` 三种累加的对照

`atomic_counter\atomic_counter.cpp` 里分三段：Demo A 用拉长窗口的方式稳定复现竞争，Demo B 用普通 `int` 紧跟视频里的循环实验，Demo C 把同一个循环换成 `std::atomic<int>`。

**预期输出**：Demo A 与 Demo C 每次运行都完全一致，Demo B 的"实际值"与"结论"两行取决于当次运行（下面是一次实测的完整输出）：

```text
=== Demo A: 把竞争窗口拉长，两个线程各递增 1 次 ===
期望值：2
实际值：1
结论：两次递增只留下一次的效果
=== Demo B: 两个线程各递增 100000 次，用普通 int ===
期望值：200000
实际值：186096
结论：实际值小于期望值，有更新被覆盖了
=== Demo C: 两个线程各递增 100000 次，用 std::atomic<int> ===
期望值：200000
实际值：200000
```

**验收标准**：

1. Demo A 的两行（`实际值：1`、`结论：两次递增只留下一次的效果`）必须每次都是这个样子——这是本章"稳定复现数据竞争"的依据；
2. Demo C 必须每次都精确等于 `200000`，20 次运行零例外；
3. Demo B：连续运行 20 次并记录，把结果分成"小于 200000"和"恰好等于 200000"两类分别数一数（我这里的实测结果是 13 次小于、7 次恰好相等）。**两类都算通过**，因为 Demo B 要证明的正是"有竞争时结果不可信"；
4. 编译时 `-Wall` 没有警告。

**改值实验（对应视频里的对比）**：把 `const int timesPerThread = 100000;` 改成 `100`，**先预测** Demo B 会变成什么样，再重新编译运行。实测结果和我这里的统计如下：

- `100` 次：连续 10 次运行，Demo B **每次都恰好等于 200**（视频里"小循环时结果正确"就是这么来的）；
- `1000` 次：连续 6 次运行，每次都恰好等于 2000；
- `10000` 次：连续 5 次运行，每次都恰好等于 20000；
- `50000` 次：连续 5 次运行，每次都恰好等于 100000。

**这条实验的结论比数字更重要**：Demo B 的代码从头到尾一个字没变，只是循环次数不同，结果就时而正确、时而错误。**"结果正确"从来不是"没有数据竞争"的证据**，Demo A 的稳定复现才是这份代码真正状态的暴露。做完请把数值改回 `100000`。

**改值实验**：把 Demo C 里的 `int expected = 7;` 改成 `int expected = 6;`，**先预测**会发生什么，再重新编译运行。预期是：比较失败（`a` 的实际值是 7，不等于 6），所以 `是否成功` 变成 `0`、`a` 仍然是 7；同时因为失败，`expected` 这个参数被**回填**成实际值 7。实测输出：

```text
调用前：a = 7，期望值 = 6
compare_exchange_weak(把 6 换成 42) 是否成功：0
调用后：a = 7，期望值参数 = 7
```

最后一行正是"失败时回填"的直接证据——这也解释了为什么这个参数要传引用、为什么标准用法要放在循环里（回填之后下一轮重试就有了新的期望值）。看完把 `6` 改回 `7`。

### 7.3 实验三（可选）：把原子换成锁

如果手边还留着第 42 章的例程，可以把 `mutex_sum.cpp` 里的 `addSafe` 改写成原子版本（把 `long long total` 换成 `std::atomic<long long>` 并按引用传），再对比：

- **结果**：两者都必须精确等于 1000000；
- **结构**：原子版本不需要 `std::mutex`、不需要 `#include <mutex>`，循环里也没有临界区；
- **代价**：原子版本没有线程排队，但保护的只是一个变量——这也正是第 6 节那张表要说明的边界。

## 8 常见错误与排查

| 报错或现象 | 原因 | 处理 |
| --- | --- | --- |
| `error: 'atomic' is not a member of 'std'`（常跟 `note: 'std::atomic' is defined in header '<atomic>'`） | 没有包含 `<atomic>` | 加 `#include <atomic>` |
| `error: use of deleted function 'std::atomic<int>::atomic(const std::atomic<int>&)'` | 试图拷贝一个原子变量，或把它按值传给函数 | 原子类型不可拷贝；按引用传递（线程里用 `[&value]` 捕获，或函数形参写成 `std::atomic<int>&`） |
| `error: cannot call member function 'bool std::__atomic_base<_IntTp>::is_lock_free() const' without object` | 把它当成静态成员函数调用（写成了 `std::atomic<int>::is_lock_free()`） | 用对象调用：`a.is_lock_free()`；想问"是否总是无锁"用编译期常量 `std::atomic<int>::is_always_lock_free` |
| 累加结果小于期望值，每次运行都不同 | 多个线程同时读改同一个非原子变量，发生了数据竞争（丢失更新） | 把变量改成 `std::atomic<...>`（本章做法），或用第 42 章的一把锁保护全部访问 |
| 结果**有时**正确、有时错误，改循环次数就"好了" | 数据竞争不保证每次都被触发 | 不要用"跑几次对了"作为判断依据；要复现就把竞争窗口拉长（如 Demo A），或者直接按标准判断有没有竞争 |
| 两个变量都换成了原子变量，但"两个数之和不变"还是会被破坏 | 原子操作只保证单个变量的单次操作，两次原子操作之间仍可被插入 | 这类"多个数据构成的不变量"必须用互斥锁保护一整段代码 |
| 用原子变量替换了锁，程序反而更慢 | 竞争激烈时原子操作同样要反复重试（自旋） | 竞争很激烈、或临界区里本来就不止一个变量时，用锁更合适 |
| `fetch_add` 拿到的是加之前的值，误以为写错了 | 这个成员函数本来就"交回旧值" | 它是"取出旧值再自增"一步完成的写法；只要旧值不要结果就写 `+=` 或 `++` |
