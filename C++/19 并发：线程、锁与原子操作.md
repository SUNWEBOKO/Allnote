## 1 从执行策略到自己动手

第 06 章的执行策略解决的是"一段标准库算法怎么并行"：加一个参数交给库，剩下的我们不用管。但并行这件事并不总能套进现成的算法形状里——可能要同时处理几批互不相关的数据、一边算一边等网络、或者把一件大活按自己的想法切开。这时需要自己说出"哪些工作可以同时做"。

C++ 里表达这件事最基本的工具是**线程**（thread）。`std::thread` 类表示一个执行线程，线程允许多个函数**并发执行**。也就是说，我们可以把一个函数交给一个新线程，让它和原来的执行流同时往下跑。

程序启动时已经有一条执行流，它从 `main` 开始执行，称为**主线程**。用 `std::thread` 创建的都是额外的执行流。操作系统会把这些执行流分配到处理器的不同核心上，所以"同时"是真的同时，而不只是轮流使用一个核心。

`std::thread` 定义在头文件 `<thread>` 里。第 02 章讲过的规则在这里照旧适用：用到什么东西，就包含它所在的那个头文件。

## 2 创建一个线程

创建一个线程要回答两个问题：**它执行什么**，以及**它的输入是什么**。这两个答案就是 `std::thread` 构造函数的参数。

例程 `E:\CPP_Code\CppFromScratch\ch41_threads\thread_basic\thread_basic.cpp` 里先准备了一件"工作"：

```cpp
void printThreadId(int id)
{
    std::cout << "来自线程：thread id = " << id << std::endl;
}
```

然后在 `main` 里启动一个线程来运行它：

```cpp
std::thread t1(printThreadId, 7);

t1.join();
```

逐部分看这一行构造：

- **第一个实参 `printThreadId`** 是"这个线程要执行什么"。能放进去的东西叫**可调用对象**：普通函数名（这里就是）、第 18 章的函数对象、lambda 表达式都可以。
- **后面的实参 `7`** 是交给那个函数的输入，按顺序对应它的参数列表，所以 `printThreadId` 收到的 `id` 就是 `7`。参数可以是任意多个，也可以是零个（不传就只写一个可调用对象）。
- **`t1`** 是这个线程对象的名字。构造完成的那一刻，新线程就已经开始执行了；构造函数返回与"新线程开始跑"之间没有先后保证，两者是并发的。

`main` 里创建 `t1` 之后所处的这条执行流就是主线程，它不会因为 `t1` 的存在而停下来等谁。

## 3 汇合：join

新线程一旦启动就和主线程并行前进。这带来一个必须处理的问题：**主线程怎么知道它已经干完了？** 如果主线程需要用线程算出来的结果，它就必须等到那个线程结束。

答案就是 `join`：

```cpp
t1.join();
```

`join` 的含义是：**当前线程（这里是主线程）在这一点阻塞，直到 `t1` 对应的执行流结束，然后继续往下执行**。`join` 调用完之后 `t1` 就不再对应任何执行流（`t1.joinable()` 变成 `false`），**同一个线程对象只能 `join` 一次**。

拿例程里的顺序来看：

```cpp
std::thread t1(printThreadId, 7);

t1.join();
std::cout << "主线程：t1.join() 之后才继续" << std::endl;
```

因为 `join` 写在线程输出与主线程这行输出之间，所以线程那一行的位置是被固定住的：

```text
=== Demo A: 启动一个线程并等待它完成 ===
来自线程：thread id = 7
主线程：t1.join() 之后才继续
```

如果把 `join` 换成别的位置——比如让主线程先做一大段自己的活再 `join`——那么"来自线程"这一行就可能出现在前面、中间或后面，取决于两个执行流各自跑得多快。**`join` 的位置决定了输出中哪些先后关系是确定的，哪些是不确定的**，这一点在写并发程序时是首要的清醒认识。

### 3.1 不 join 会怎样

如果创建了线程却从头到尾都没 `join`，那在 `main` 返回、`t1` 被销毁（析构）的时候，它还对着一条还在跑的（或者可能已经跑完但没被汇合的）执行流。此时标准规定：**销毁一个仍处于 joinable 状态的 `std::thread` 会调用 `std::terminate`**，程序直接终止。

把上面例程里的 `t1.join();` 注释掉再编译运行（后面的实验会做这一步）。线程那一行出现的位置是竞态的，下面是一次运行时看到的样子：

```text
=== Demo A: 启动一个线程并等待它完成 ===
主线程：t1.join() 之后才继续
=== Demo B: 把结果写回主线程的变量 ===
来自线程：thread id = 7
主线程自己的累加：100000
线程 9 的累加：100000
terminate called without an active exception
```

可以看到两件事：一是这一次"来自线程"那一行跑到了主线程两行输出的**后面**（没有 `join` 就没人约束顺序，换个时间它也可能出现在别的位置）；二是程序最后打印了 `terminate called without an active exception` 然后异常结束，退出码不是 `0`。

标准之所以选择直接终止而不是"悄悄帮我们等"，是因为线程对象的析构函数无法体面地处理这件事：等它结束可能等很久，不等又会产生悬垂状态，标准把这个决定权交给了写代码的人——**要么 `join`，要么在别的地方明确交代这条执行流的去向**。本章的规则很简单：**创建的每个 `std::thread` 都要有对应的 `join`。**

## 4 jthread：析构时自动汇合

每次手写 `join` 都要记得"我创建了几个线程、它们各自要在哪里等"，这和第 09 章"每次 `new` 都要配一个 `delete`"是同一类负担。C++20 为此提供了更省心的线程类型 `std::jthread`。

`std::jthread` 的构造方式和 `std::thread` 完全一样（可调用对象 + 参数），区别只有一条：**`jthread` 在析构时会自动汇合**（如果它还在 joinable 状态，析构函数里调用 `join` 之后再继续销毁）。因为它的析构函数总是会执行，所以"忘记 join 导致程序终止"这类事故就不存在了。

"自动汇合发生在什么时候"很关键：**在对象被销毁的那一刻，也就是它所在的作用域结束时**。例程 `ch41_threads\jthread_vector\jthread_vector.cpp` 用一对花括号把这一点变成了可以看见的东西：

```cpp
{
    std::vector<std::jthread> myThreads;

    for (int i = 0; i < 3; ++i)
    {
        myThreads.emplace_back([i]()
        {
            std::cout << "thread id = " << i << std::endl;
        });
    }
}

std::cout << "=== Demo A 结束 ===" << std::endl;
```

`std::vector<std::jthread>` 是可以的：容器只要求元素能被移动，而线程对象可以移动、不能拷贝。上面这段代码里没有任何 `join`，但走出花括号时 `vector` 析构、三个 `jthread` 逐个析构并各自汇合，所以后面那行 `=== Demo A 结束 ===` 一定排在三个线程输出之后。

如果把这里的 `std::jthread` 全部换成 `std::thread`（其他一字不改），编译照样通过，但运行时会立刻看到和 3.1 节一样的 `terminate called without an active exception`——`vector` 析构时销毁了三个还没汇合的线程对象。

### 4.1 参数是怎么进入线程函数的

`std::thread`（以及 `jthread`）会把实参**拷贝**到自己的内部存储里，然后以右值的形式交给线程函数。这条规则有一个直接后果：**形参是引用的函数不能用它来改主线程的变量**。

例程 `thread_basic.cpp` 里的 `addMany(int times, int& result)` 的第二个形参是引用，所以调用处必须写：

```cpp
std::thread t2(addMany, 100000, std::ref(threadResult));
```

`std::ref` 的作用是"把这个变量按引用交出去，不要拷贝"。如果这里直接写 `threadResult`，编译时会失败：

```text
error: static assertion failed: std::thread arguments must be invocable after conversion to rvalues
```

这条信息不好读，但记住结论就够了：**想让线程改到外面的变量，就把那个变量用 `std::ref` 包起来**（`std::ref` 来自 `<functional>`，第 08 章按引用传参的那套规则在这里以"显式声明引用"的形式出现）。

还有一条更要紧的约束：**被引用的对象必须活得比线程长**。如果传给线程的是某个局部变量的引用，而那个局部变量所在的作用域先结束，线程再访问它就是访问已经销毁的对象（悬垂引用）。本章用到的引用对象都是 `main` 里的变量或全局变量，它们活到程序结束，所以安全。

### 4.2 主线程与线程各自算各自的

例程的 Demo B 让两边各做一份独立的计算，最后再合并：

```cpp
int threadResult = 0;
std::thread t2(addMany, 100000, std::ref(threadResult));

int mainResult = 0;

for (int i = 0; i < 100000; ++i)
{
    mainResult += 1;
}

t2.join();
std::cout << "主线程自己的累加：" << mainResult << std::endl;
std::cout << "线程 9 的累加：" << threadResult << std::endl;
```

输出是固定的两行 `100000`。这里有两点值得停下来看：

- 两个执行流从头到尾没有碰过同一个变量：主线程写 `mainResult`，线程写 `threadResult`。**没有共享的写操作，就没有需要协调的东西**，这是并发程序最好写、也最好核对的一种形态。
- `join` 写在了读取 `threadResult` **之前**。如果在 `join` 之前就读，读到的可能还是 `0`，因为那时线程可能一次都还没写回去。**共享数据必须在汇合之后读**，这是本章最重要的时序规则。

（上面代码里那句"线程 9 的累加"只是源码里写死的标签文字，对应的就是 `t2`，并不是"第 9 个线程"——例程里只有 `t1`、`t2` 两个线程。）

## 5 让并发程序的输出可以核对

前面几段已经把并发程序最反直觉的地方暴露出来了：**输出顺序不确定**。例程 `jthread_vector.cpp` 的 Demo A 让三个线程各自打印一行 `thread id = N`，其中一次实测的输出是这样的：

```text
=== Demo A: 三个线程直接写 std::cout ===
thread id = thread id = 0
1thread id = 
2
=== Demo A 结束 ===
```

三个线程的三段输出咬在了一起，`thread id =` 和数字被拆散到不同的行上。原因并不神秘：`std::cout << "thread id = " << i << std::endl;` 这一句在机器层面是**三次**插入运算——第一次插入字符串 `"thread id = "`，第二次插入数字 `i`，第三次插入 `std::endl`（它就是"换行"本身：向流里插入换行符并刷新缓冲，并不是在三次之外多出来的第四次插入）。而线程切换可以发生在任意两次插入之间，三个线程各自的三次插入交错在一起，先后顺序就完全解释了上面那堆混乱。

同样的程序再运行几次，也可能得到"三行整齐依次出现"的结果，例如：

```text
=== Demo A: 三个线程直接写 std::cout ===
thread id = 2
thread id = 1
thread id = 0
```

**这说明"这次看起来很清楚"完全不能作为并发程序正确的证据**——同样的一段代码只是这次没有撞上而已。

所以要定一条判断标准，把"顺序"和"内容"分开看：

> **顺序不确定是可以接受的，内容必须完整正确。**
>
> "内容完整正确"指的是：该出现的每一份结果都出现了，且每个值都对。比如上面这段，正确的内容是"`thread id = 0`、`thread id = 1`、`thread id = 2` 各出现一次"，至于它们谁先谁后、有没有混在同一行，不属于正确性问题。

按这个标准，我们可以把并发程序的输出写成**可核对**的形状。本章例程用的是两种写法：

**写法一：每个线程只写属于自己的位置。** `jthread_vector.cpp` 的 Demo B 给每个线程分配一个字符串格子：

```cpp
std::vector<std::string> lines(3);

{
    std::vector<std::jthread> myThreads;

    for (int i = 0; i < 3; ++i)
    {
        myThreads.emplace_back([i, &lines]()
        {
            lines[i] = "thread id = " + std::to_string(i) + " 完成";
        });
    }
}

for (const std::string& line : lines)
{
    std::cout << line << std::endl;
}
```

每个线程只写 `lines[i]` 这一个元素，彼此不碰同一个格子；等所有线程汇合之后，由主线程按 `0`、`1`、`2` 的固定顺序读出来打印。输出每次运行都完全一致：

```text
=== Demo B: 每个线程只写自己的格子 ===
thread id = 0 完成
thread id = 1 完成
thread id = 2 完成
汇总：共运行 3 个线程
```

这里还顺带说明了一个常见疑问：**多个线程同时写同一个 `std::vector` 的不同元素是安全的**。竞争只发生在"同一个内存位置"上，而不同元素各自有独立的存储位置。反过来，如果某个线程让 `vector` 扩容（比如在别的线程还在写元素时 `push_back`），那些元素会被搬到新内存上，原本的"位置"就变了，这时就不再安全——所以这种分片写法要求**先在并发开始前把容器的大小定好，线程运行期间不扩容、不增删元素**。

**写法二：线程只做计算，结果按固定顺序汇总。** 例程 `thread_results.cpp` 里四个线程各算一个值写进 `results[i]`，全部汇合之后主线程按顺序打印并求和：

```text
=== 4 个线程分别计算结果 ===
=== 按固定顺序汇总 ===
worker 0: 1 * 10 = 10
worker 1: 2 * 10 = 20
worker 2: 3 * 10 = 30
worker 3: 4 * 10 = 40
合计：100
```

**让线程只写自己的那一份、由主线程统一输出**，是把"并发"和"可核对"两件事同时做到的最简单办法。需要严格执行"每一行必须完整不被打断"时（例如日志），要用本章第 7 节的互斥锁把整行输出变成一段不可打断的临界区。

## 6 从上一节的问题说起

上一节最后留下了一个没有解决的问题。三个线程各自打印一行 `thread id = N`，实测输出是这样的：

```text
=== Demo A: 三个线程直接写 std::cout ===
thread id = thread id = 0
1thread id = 
2
=== Demo A 结束 ===
```

每一行的内容被拆散、和别的线程的输出咬在了一起。原因在上一节已经看清了：`std::cout << "thread id = " << i << std::endl;` 这一句是三次插入运算（第三次插入的 `std::endl` 负责换行并刷新缓冲），线程切换可以插在任意两次插入之间，三个线程的三次运算交错在一起，就得到了上面这堆文字。

现在换个说法来看这件事：**`std::cout` 是三个线程共同使用的对象**。它内部的缓冲、格式状态、输出位置只有一份，任何线程对它做的每一次操作都会改变它的状态。这样的东西叫**共享资源**。本章第 15 节的另一个例子也一样——几个线程同时读改同一个 `int`，那个 `int` 也是共享资源。

共享资源本身并不可怕，可怕的是**同时**碰它。于是问题变成：怎么规定"同一时刻只允许一个线程碰它"。本节要学的 `std::mutex` 就是干这个的。

## 7 互斥锁与临界区

`std::mutex`（mutex 是 mutual exclusion，互斥）定义在头文件 `<mutex>` 中。它提供的是一把**锁**：一个线程把它**锁上**，其他线程再想锁上这把锁就会被挡住，直到持锁的线程把它**解开**。

围绕一把锁，代码被分成两种区域：

- **临界区（critical section）**：需要独占访问共享资源的那段代码。同一时刻最多只有一个线程能处在临界区里。
- **临界区之外**：互不影响，可以随便并行。

用锁的基本动作只有两个成员函数：

- **`lock()`**：尝试锁上互斥量。如果当前没有别的线程持有它，调用立刻返回；否则调用者**阻塞**在这里，直到锁被释放。
- **`unlock()`**：释放互斥量。这会允许其他正在等待的线程去尝试获取锁。

例程 `E:\CPP_Code\CppFromScratch\ch42_mutex\mutex_cout\mutex_cout.cpp` 里用锁保护"打印一行并计数"：

```cpp
std::mutex m;
int printedLines = 0;

myThreads.emplace_back([i]()
{
    m.lock();

    std::cout << "thread id = " << i << std::endl;
    printedLines += 1;

    m.unlock();
});
```

（这段是**反面教材**，下面马上就会看到它的问题，例程里真正用的是 `lock_guard`。）

三个线程都执行同一段代码，但 `m` 只有一把，所以它们的执行被排成了队：

- 第一个线程调用 `m.lock()` 成功，进入临界区，打印、计数，然后 `m.unlock()`。
- 第二个线程也在 `m.lock()` 上，如果第一个还没解锁，它就停在这一行等待；等锁一放开，它才进入。
- 第三个线程同理。

**锁保护的是"同一时刻只有一个"，不是"谁先谁后"**。这一点决定了后面的一切：排队次序完全由运行时决定，我们只能保证不会同时进去。

## 8 手动加锁的麻烦：忘记解锁与死锁

上面那段代码只用一次没问题，但它把"解锁"变成了一件需要人记着的事，而这正是最容易出错的地方——和第 09 章 `new` 与 `delete` 的配对是同一类负担：`new` 忘记配 `delete` 会漏内存，`lock` 忘记配 `unlock` 的后果更狠。

把例程 `mutex_cout.cpp` 里那段 `std::lock_guard<std::mutex> lock(m);` 换成 `m.lock();` 并且**删掉 `m.unlock();`**，重新编译运行，实测是这样的：

```text
=== Demo A: 用 lock_guard 保护整行输出 ===
thread id = 0
```

（`0` 是哪一个线程先抢到锁的结果，并不固定；本次实测恰好是 `0`。）

程序只打印了一行，然后**再也不结束**（用 `timeout 6 ./mutex_cout.exe` 运行，6 秒后被外部强制终止，退出码 `124`；在终端里直接运行需要按 `Ctrl+C` 才能把它停下来）。

发生了什么？第一个进入临界区的线程拿着锁、打印、然后直接从 lambda 末尾离开了，**锁没有被还回去**。另外两个线程一个卡在 `m.lock()` 上，另一个也卡在 `m.lock()` 上；而 `main` 这边的 `vector<jthread>` 析构时又要等这三条线程结束——于是整条链都停住了。这种"某个线程永远不会释放锁、其他线程永远等下去"的状态就叫**死锁**（deadlock）。

> 而且它**每次运行都会死锁**，不像数据竞争那样时有时无。这也给了一个排查提示：如果并发程序"总是卡住不动"，优先看锁的加解锁是否配对。

## 9 std::lock_guard：把加解锁交给编译器

正确的做法不是"记得手写 `unlock`"，而是**让这件事根本不需要记**。头文件 `<mutex>` 里的 `std::lock_guard` 就是为此设计的：

```cpp
std::lock_guard<std::mutex> lock(m);
```

这一行做的事如下：

- `lock_guard` 是一个"互斥量包装器"：它持有对某个互斥量的引用。
- **构造时**在它自己的构造函数里调用 `m.lock()`。
- **析构时**在它自己的析构函数里调用 `m.unlock()`。
- 因为它是一个局部对象，而局部对象在离开作用域时一定会被销毁，所以**锁一定会被还回去**。

这就是 RAII（Resource Acquisition Is Initialization，资源获取即初始化）：把资源的获取放在构造函数里、释放放在析构函数里，让"作用域的结束"成为"资源归还"的触发点。第 10 章的 `unique_ptr` 用这个套路管指针，第 12 章讲析构函数时用的是同一套思路，这里管的是锁。

用它之后，前面那个 lambda 变成：

```cpp
myThreads.emplace_back([i]()
{
    std::lock_guard<std::mutex> lock(m);

    std::cout << "thread id = " << i << std::endl;
    printedLines += 1;
});
```

没有 `lock()` 也没有 `unlock()`：**加锁和解锁都发生在编译器安排的时刻**（构造函数与析构函数），人只要负责把临界区的范围用一对花括号说清楚。

### 9.1 为什么它必须有一个名字

下面这行看起来一样，其实完全不是一回事：

```cpp
std::lock_guard<std::mutex>(m);      // 想临时持锁？不行，编译不过
```

编译器把它解析成一个**变量声明**：声明一个名叫 `m`、类型是 `std::lock_guard<std::mutex>` 的变量，后面那对括号是多余的。名字被当成了新变量的名字，而 `lock_guard` 没有默认构造函数可调用，所以编译不过。具体报哪几条错，取决于这个名字在作用域里有没有"撞车"，实测有两条触发路径：

**路径一：作用域里没有同名的局部变量。** 例程 `mutex_cout.cpp` 里的 `m` 是全局变量，就属于这一种——编译器看见的是一个全新的局部变量 `m`（它会把全局 `m` 遮住），于是找不到无参构造函数：

```text
warning: unnecessary parentheses in declaration of 'm' [-Wparentheses]
error: no matching function for call to 'std::lock_guard<std::mutex>::lock_guard()'
```

**路径二：同一个作用域里已经有一个类型不同的同名局部变量。** 比如函数里先写了 `std::mutex m;`，再写 `std::lock_guard<std::mutex>(m);`，编译器除了上面那条找不到构造函数的错，还会多报一条重名：

```text
warning: unnecessary parentheses in declaration of 'm' [-Wparentheses]
error: conflicting declaration 'std::lock_guard<std::mutex> m'
note: previous declaration as 'std::mutex m'
```

形参同名（例如 `void g(std::mutex& m)` 里写这一行）走的是路径一，只是中间会多一条 `error: declaration of 'std::lock_guard<std::mutex> m' shadows a parameter`。

结论：**`lock_guard` 必须起一个变量名**，而且这个对象要活到临界区结束

```cpp
std::lock_guard<std::mutex> lock(m);     // 对：lock 活到作用域末尾，末尾自动解锁
```

这也顺带说明为什么 `lock_guard` 不能被拷贝、不能被移动（它代表"我持有这把锁"这一独占状态，实际上也不允许转移），所以它只能像上面这样就地构造。

### 9.2 提前 return 也会解锁

第 8 节那个"忘记解锁"的场景，最典型的成因不是"忘了写"，而是**中间有 `return` 或者抛出异常**，`unlock` 那一行根本没被执行到。`lock_guard` 恰好能兜住这一点——析构函数在 `return` 离开时一样会被调用。

例程 `mutex_cout.cpp` 的 Demo B 把这件事变成了可以看的输出：

```cpp
void criticalSection(std::mutex& mutex, const std::string& name, bool earlyReturn)
{
    std::lock_guard<std::mutex> lock(mutex);

    std::cout << "进入临界区：" << name << std::endl;

    if (earlyReturn)
    {
        std::cout << name << "提前返回，lock_guard 在这里析构并解锁" << std::endl;
        return;
    }

    std::cout << name << "走到函数末尾，lock_guard 在这里析构并解锁" << std::endl;
}
```

`main` 里先用 `earlyReturn = true` 调一次，再用 `false` 调一次。实测输出：

```text
=== Demo B: lock_guard 在提前 return 时也会解锁 ===
进入临界区：第一次调用
第一次调用提前返回，lock_guard 在这里析构并解锁
进入临界区：第二次调用
第二次调用走到函数末尾，lock_guard 在这里析构并解锁
两次调用都拿到了锁，没有死锁
```

第一次调用走的是提前 `return` 的分支，第二次调用仍然顺利进了临界区——说明第一次那把锁已经被还回去了。如果把手写版本写成"只 `lock` 不 `unlock`"，第二次调用就会永远停在 `lock` 上（程序卡死），这也解释了为什么"手写 lock/unlock"应该尽量避免。

### 9.3 抛出异常也会解锁

提前离开还有另一条路径：**抛出异常**。异常向上传播时会做栈展开（stack unwinding），沿途的局部对象照样会被析构，所以 `lock_guard` 在抛出异常时也会解锁。下面这个最小程序和 9.2 的例程形状相同，只是把 `return` 换成了 `throw`；它是自包含的，单独存成一个 `.cpp` 就能编译运行：

```cpp
#include <iostream>
#include <mutex>
#include <stdexcept>
#include <string>

std::mutex m;

void criticalSection(const std::string& name, bool throwError)
{
    std::lock_guard<std::mutex> lock(m);

    std::cout << "进入临界区：" << name << std::endl;

    if (throwError)
    {
        throw std::runtime_error(name + "中途抛出异常，lock_guard 在这里析构并解锁");
    }

    std::cout << name << "走到函数末尾，lock_guard 在这里析构并解锁" << std::endl;
}

int main()
{
    try
    {
        criticalSection("第一次调用", true);
    }
    catch (const std::exception& e)
    {
        std::cout << "捕获异常：" << e.what() << std::endl;
    }

    criticalSection("第二次调用", false);

    std::cout << "两次调用都拿到了锁，没有死锁" << std::endl;

    return 0;
}
```

实测输出：

```text
进入临界区：第一次调用
捕获异常：第一次调用中途抛出异常，lock_guard 在这里析构并解锁
进入临界区：第二次调用
第二次调用走到函数末尾，lock_guard 在这里析构并解锁
两次调用都拿到了锁，没有死锁
```

第一次调用抛出异常后并没有卡在锁上，第二次调用照样进了临界区——锁是在异常传播、`lock_guard` 析构的那一刻被还回去的。这恰好是"手写 `lock`/`unlock`"最危险的地方：异常路径往往不是写代码时能想到的那条路径，而它偏偏会把 `unlock` 整行跳过。

## 10 用锁保护的是"共享数据"，不是"某几行代码"

回到 Demo A 的输出。加了锁之后，同一次实测的输出是：

```text
=== Demo A: 用 lock_guard 保护整行输出 ===
thread id = 0
thread id = 2
thread id = 1
=== 全部线程结束，共输出 3 行完整的输出 ===
```

连续运行多次，三个 `thread id` 行的排列会变（实测中见过 `0/2/1`、`2/1/0`、`1/2/0`、`0/1/2`），但**每一行都是完整的，而且永远不多不少三条**。这正是本章第 5 节立下的标准：顺序不确定可以接受，内容必须完整正确。锁能做到的事情就是这一件——把"打印这一行"的三次插入运算变成不可打断的整体，至于谁先谁后，仍然由调度决定。

这里有两个容易踩空的点：

**第一，临界区必须把对共享数据的所有访问都包进去。** 例程里 `printedLines += 1;` 也写在锁里面。原因和下一节要讲的完全一样：`+=` 不是一步操作，它读、改、写三步之间同样可能被插进来。**如果一段代码访问了被某把锁保护的数据，却没有持有那把锁，保护就等于不存在。**

**第二，锁要跟着数据走。** 例程把 `std::mutex m;` 与它保护的 `printedLines` 写在相邻的位置，并在注释里说明"下面这个变量归这把锁管"。如果同一个共享数据被两把不同的锁分别保护，或者某些访问根本不加锁，那么无论锁用得多么规范都不起作用——保护一个数据的锁**必须**是所有访问者共用的同一把。

还有一个实践上的细节：加锁会带来开销。每次进出临界区都有代价，而且持锁期间别的线程只能等，所以在临界区里应该**只放必须独占的代码**，把耗时但与共享数据无关的计算挪到锁外面去。

## 11 数据竞争：不加锁的累加会丢更新

现在看另一个必须搞清楚的问题：多个线程同时改同一个变量，到底会错在哪里。

例程 `E:\CPP_Code\CppFromScratch\ch42_mutex\mutex_sum\mutex_sum.cpp` 里有两个函数干同一件事：把 `total` 累加 `times` 次。区别是 `addSafe` 在循环里多了一行 `std::lock_guard`：

```cpp
void addUnsafe(long long& total, int times)
{
    for (int i = 0; i < times; ++i)
    {
        total += 1;
    }
}

void addSafe(long long& total, std::mutex& mutex, int times)
{
    for (int i = 0; i < times; ++i)
    {
        std::lock_guard<std::mutex> lock(mutex);
        total += 1;
    }
}
```

`main` 里让 4 个线程各调用一次，各累加 250000 次，所以期望值是 1000000。

**Demo A（不加锁）的实测**：实际值每次运行都不同。采集 15 次运行的结果（只列部分）：

| 第几次运行 | 实际值 | 与期望值 1000000 的关系 |
| --- | --- | --- |
| 1 | 346320 | 少约 65% |
| 2 | 342999 | 少约 66% |
| 3 | 422538 | 少约 58% |
| 4 | 324049 | 少约 68% |
| 5 | 254325 | 少约 75% |

15 次运行**没有一次**等于 1000000，也没有一次比它大。

**Demo B（加锁）的实测**：实际值每次都是 `1000000`，与期望值分毫不差。

两段代码只差一行 `std::lock_guard`，为什么差距这么大？看一下 `total += 1;` 在机器层面做的事：

1. **读**：把 `total` 当前的值从内存取到寄存器；
2. **改**：在寄存器里把它加一；
3. **写**：把结果写回 `total` 所在的内存。

这三步必须按顺序完成，但它们**不是不可分割的一步**。假设 `total` 现在是 5，两个线程各自执行这句：

```text
线程 1：读 total → 得到 5
线程 2：读 total → 得到 5          ← 线程 1 还没来得及写回
线程 1：写入 5 + 1 = 6
线程 2：写入 5 + 1 = 6            ← 覆盖了线程 1 的结果
```

两次递增做完，`total` 却只从 5 变成 6，**有一次递增凭空消失了**。这叫**丢失更新**（lost update）。线程越多、循环越密，两个线程同时落在这条细小窗口里的机会就越多，丢失也就越严重——这正是 Demo A 里少了百分之六七十的来源。

标准对这件事的表述更严格。按 C++ 内存模型的说法：如果一个表达式的求值要写某个内存位置，另一个表达式的求值要读或改同一个内存位置，这两个求值就是**冲突的**；如果程序里存在两个冲突的求值、且它们来自不同线程、又没有同步措施，就发生了**数据竞争**（data race）。而**一旦存在数据竞争，程序的行为就是未定义的**。

"未定义行为"这个词在第 2、9 章出现过，含义在这里格外重要：

- 未定义不等于"一定出错"。它意味着**标准不再对结果作任何承诺**——可能算错，可能这次恰好算对，也可能以我们想不到的方式出错（编译器甚至可以在有竞争的前提下做各种激进优化）。
- **因此"这次结果正确"完全不能说明代码没问题。** 用 `mutex_sum` 自己去试就会看到：不加锁的那一段在多次运行中结果一直在变，偶尔甚至会恰好等于期望值。那一次并不是"没出问题的证据"，只是没撞上而已。

把期望值和实际值一起写进输出、每次都对一遍，是并发程序最基本的自保方式——`mutex_sum.cpp` 打印的最后一行就是"结论：实际值与期望值完全一致"，一眼就能看出结果可信不可信。

## 12 一次锁住多个互斥量：std::scoped_lock

单个共享变量用一把锁就够了。但有些操作要**同时**动两样东西，而它们各自有自己的锁。

例程 `E:\CPP_Code\CppFromScratch\ch42_mutex\mutex_scoped_lock\mutex_scoped_lock.cpp` 里有两个账户，每个账户自带一把锁：

```cpp
struct account
{
    int balance;
    std::mutex m;

    explicit account(int initialBalance) : balance(initialBalance)
    {
    }
};
```

转账要从 `from` 扣钱、给 `to` 加钱，这两步必须一起完成——中间不能让别的线程看到"钱已经扣了但还没到账"的状态。所以一次转账要同时拿住两个账户的锁。

**如果按"先锁一个、再锁另一个"的顺序写，就会死锁。** 假设两个方向同时进行：线程 1 从 A 转到 B（先锁 A 再锁 B），线程 2 从 B 转到 A（先锁 B 再锁 A）。只要时序凑巧——线程 1 拿到 A、线程 2 拿到 B，然后各自等对方手里那把——两边就永远等下去。把例程里的

```cpp
std::scoped_lock lock(from.m, to.m);
```

换成

```cpp
std::lock_guard<std::mutex> lockFrom(from.m);
std::lock_guard<std::mutex> lockTo(to.m);
```

重新编译运行，实测就是这样：只打印了两行标题，然后程序卡死，用 `timeout 6` 运行 6 秒后被强制终止（退出码 `124`）。

```text
=== Demo A: 两个方向的转账同时进行，每次 1 元，各 100000 次 ===
初始余额：A = 1000，B = 1000
```

`std::scoped_lock` 解决的就是这件事。它的构造函数可以一次接收**多个**互斥量：

```cpp
void transfer(account& from, account& to, int amount, int times)
{
    for (int i = 0; i < times; ++i)
    {
        std::scoped_lock lock(from.m, to.m);

        from.balance -= amount;
        to.balance += amount;
    }
}
```

它内部使用标准里 `std::lock` 的策略：**尝试加锁，一旦发现某些锁暂时拿不到，就把已经拿到的全部退掉，然后再重试**。这样就不会出现"双方各持一把、互相等待"的局面。只锁一个互斥量时它也是可用的，行为与 `lock_guard` 等价——所以"拿不准用哪个"时，用 `scoped_lock` 不会错。

### 12.1 用一个不变量核对结果

并发程序怎么核对结果？除了"每次打印期望值再对一遍"，还有一个更有力的办法：**找一个无论执行顺序如何都必须成立的不变量，再拿实际结果去比对**。

`mutex_scoped_lock` 用的不变量是**总额不变**：

```cpp
std::cout << "A 的余额：" << a.balance << std::endl;
std::cout << "B 的余额：" << b.balance << std::endl;
std::cout << "总额：" << (a.balance + b.balance) << "（初始总额 2000，必须不变）" << std::endl;
```

实测输出（每次运行都相同）：

```text
=== Demo A: 两个方向的转账同时进行，每次 1 元，各 100000 次 ===
初始余额：A = 1000，B = 1000
=== Demo B: 汇总（所有线程结束之后） ===
A 的余额：1000
B 的余额：1000
总额：2000（初始总额 2000，必须不变）
```

为什么完全确定？两个方向各做 100000 次、每次 1 元，金额互相抵消，所以余额必然回到初始值。不管线程怎么交错、谁先执行哪一次转账，总额都不该变过。

这里要说清一个容易弄混的地方：本章第 12 节里那个换成两把 `lock_guard` 的版本，**唯一的问题是死锁，而不是结果错误**。每个 `balance` 都由它自己那把锁保护，`main` 又在两个线程都汇合之后才读，所以它只要能跑完，总额一样会是 2000；它卡死的原因是两个方向加锁顺序相反，和"结果算错"是两回事。

检查不变量，比检查某一次具体数值更能说明保护有没有做到位。

顺带注意：`main` 里读 `a.balance`、`b.balance` 时没有加锁，这是对的——所有线程都已经汇合结束，此刻没有任何其他线程在访问这两个账户。锁只在**可能并发访问**的时候才需要；汇合之后的读取属于本章第 4 节讲的"jthread 自动汇合之后再汇总"的场景。

## 13 怎么选

| 场景 | 用什么 | 说明 |
| --- | --- | --- |
| 保护一段代码，只涉及一把锁 | `std::lock_guard` | 最简单，加解锁全自动，覆盖绝大多数情况 |
| 一次要锁住两把或更多锁 | `std::scoped_lock` | 内部按 `std::lock` 的策略一次拿到全部，避免互相等待 |
| 只锁一把锁，但想统一写法 | `std::scoped_lock` | 单锁用法与 `lock_guard` 等价，不必记两种 |
| 需要临时解锁再重新加锁、或需要"尝试加锁" | `std::unique_lock`（后续内容） | 更灵活也更重，本章的例子用不到 |
| 只保护一个变量的加减、而且不需要与其他数据保持一致性 | 本章第 17 节的 `std::atomic` | 不用锁，但适用范围窄 |
| 由某一把锁保护的**多个**变量之间有必须同时成立的关系（如总额不变） | 必须用锁 | 原子操作只能保证单个变量的单次操作，保不住变量之间的关系 |

互斥锁的方案通用、可靠，但代价也很直接——**每个线程都要排队**，本来可以并行的部分被串行化了。于是自然要问：有没有更轻的办法？下面几节就来看这个更轻的办法，以及它的适用边界。

## 14 从互斥锁到原子操作

考虑最普通的一种共享数据：一个计数器。多个线程各自把同一个计数器加一，除此之外什么也不做。对这种"单个变量上的单个操作"，C++ 提供了比锁更贴身的工具——**原子操作**（atomic operation）。

本节安排是先看清问题的本质（为什么三步操作会出错），再引入原子类型，最后划清"原子能做什么、不能做什么"的边界。

## 15 读-改-写与丢失更新

本章第 11 节已经把 `total += 1` 拆成了读、改、写三步，也解释了丢失更新是怎么发生的：**线程切换可以发生在任意两条指令之间**，也可能两个线程真的在不同核心上同时执行，两个线程都读到同一个旧值、各写回一份结果，一次递增就被覆盖掉了。这里不再重复那张时序表，直接看怎么把这种交错的窗口**故意拉长**，让错误每次运行都必然发生。

例程 `E:\CPP_Code\CppFromScratch\ch43_atomics\atomic_counter\atomic_counter.cpp` 的 Demo A 是这么做的：

```cpp
int sharedValue = 0;

void slowIncrement()
{
    const int value = sharedValue;

    std::this_thread::sleep_for(std::chrono::milliseconds(20));

    sharedValue = value + 1;
}
```

读和写之间夹了 20 毫秒，第二个线程几乎必然在第一个线程写回之前就已经完成了"读"这一步。`main` 里启动两个这样的线程并汇合，实测输出（多次运行都相同）：

```text
=== Demo A: 把竞争窗口拉长，两个线程各递增 1 次 ===
期望值：2
实际值：1
结论：两次递增只留下一次的效果
```

**这份输出是要留下来的核对依据**：两次递增、结果却是 1，说明有一份被覆盖了。拉长窗口只是为了"让错误稳定出现"——真实程序里这个窗口可能只有几个时钟周期，所以同样的错误往往是偶发、难查的（这一点下一节会看到实测统计）。

## 16 数据竞争与未定义行为

数据竞争与未定义行为的定义本章第 11 节已经给出：两个**冲突的**求值（一个写、另一个读或改同一个内存位置）来自不同的线程，而又没有同步措施保证一个在另一个之前发生，程序就发生了数据竞争，**行为是未定义的**。标准同时给出了避免数据竞争的三种途径：

1. **让两个操作在同一个线程里**。单线程程序里不存在数据竞争——同一个线程内的操作天然有先后顺序。
2. **使用标准原子操作**。如果这些操作本身是原子的，它们就不再"冲突"，本章第 17～19 节讲的就是这条路。
3. **建立发生顺序（先行关系）**。如果一个冲突操作保证在另一个之前发生，就不构成竞争。**加锁正是建立这种顺序的手段**：本章第 9 节里 `lock_guard` 保证同一时刻只有一个线程在临界区里，临界区之间的先后关系被锁排好了。

由于未定义行为意味着"标准不再对结果作任何承诺"，**"我运行了几次都对"完全不能证明代码没有数据竞争**。

用本章的例程可以亲手验证这件事。Demo B 让两个线程各循环 100000 次 `total += 1`（普通 `int`，不加任何保护），把 `timesPerThread` 的值改小再运行，会看到下面这样一组实测统计：

| 每个线程的循环次数 | 期望值 | 实测（运行次数） | 结果 |
| --- | --- | --- | --- |
| 100 | 200 | 10 次 | 10 次全部恰好等于 200 |
| 1000 | 2000 | 6 次 | 6 次全部恰好等于 2000 |
| 10000 | 20000 | 5 次 | 5 次全部恰好等于 20000 |
| 50000 | 100000 | 5 次 | 5 次全部恰好等于 100000 |
| 100000 | 200000 | 20 次 | 13 次小于 200000（如 152515、177667），7 次恰好等于 200000 |

这正是把丢失更新的窗口放大到极限时的后果：**循环次数少时，一个线程往往在另一个线程真正开始之前就跑完了，两次递增自然不重叠，结果"看起来完全正确"；循环次数一多，重叠的机会多了，错误才开始露面——而且即便在这个规模上，也仍有三分之一的运行看不出任何异常。**

视频里演示的正是这件事：循环 100 次时每次都得到正确结果，把次数加大以后结果开始在期望值以下波动。**要记住的结论是：存在数据竞争时结果不可信，而不是"小循环就没问题"。**

## 17 std::atomic：把三步变成一步

如果一个问题来自"读-改-写三步会被交错"，那么解决办法就是让这三步**不能再被拆开**。这就是原子操作的含义：**一个原子操作在执行过程中不可被分割，两个原子操作之间必定有一个先完成、另一个后完成，绝不会出现"都读到同一个旧值"的中间状态。**

C++ 把它做成了类型：`std::atomic<T>` 定义在头文件 `<atomic>` 里（cppreference 上关于原子操作的族系都列在这个头文件下）。把 Demo B 里的累加函数换成原子的版本：

```cpp
void addManySafe(std::atomic<int>& total, int times)
{
    for (int i = 0; i < times; ++i)
    {
        ++total;
    }
}
```

用法上的变化只有一处：**类型从 `int` 变成 `std::atomic<int>`**。`++`、`+=` 这些运算符原子类型都有，写法和普通整数一样，只是每一次运算都是不可分割的原子读-改-写。于是两个线程的 `++` 被排成了一个确定的前后顺序：

| 时刻 | 线程 1 | 线程 2 | 内存里的 total |
| --- | --- | --- | --- |
| 1 | 读到 0，加一，写回 |  | 1 |
| 2 |  | 读到 1，加一，写回 | 2 |

Demo C 的实测输出（多次运行都相同）：

```text
=== Demo C: 两个线程各递增 100000 次，用 std::atomic<int> ===
期望值：200000
实际值：200000
```

**每一次运行都精确等于期望值**，与 Demo A 的稳定复现错误、Demo B 的时对时错形成完整对照。注意这里**没有用锁**：同一个计数器由两个线程同时递增，但每一次递增都是原子的，所以不会互相覆盖。用"锁"和用"原子"都能消除这一类竞争，区别在于原子操作不需要线程排队等待临界区（对单个变量的单次操作尤其划算）。

顺便说一个相关的概念：原子类型在底层尽量用处理器提供的原子指令实现，这样的实现叫**无锁（lock-free）**。`std::atomic<int>::is_always_lock_free` 是一个编译期常量，用来问"这个类型是不是总是无锁实现"；例程 `atomic_ops.cpp` 打印的实测结果是：

```text
std::atomic<int> 是否总是无锁实现：是
```

如果某个类型太宽（远远超过机器字长），标准库可能不得不借助内部的锁来模拟原子性——那时"原子"仍然正确，只是可能不快。这个标志回答的正是这个问题，而**不影响正确性**。

## 18 原子类型与成员函数

整数、无符号整数等常见类型都有对应的别名，写法上比模板形式更短：

```cpp
std::atomic_int a {10};              // 等价于 std::atomic<int> a {10};
std::atomic_uint b {5u};             // 等价于 std::atomic<unsigned int>
std::atomic_llong c {0};             // long long 也有别名，等价于 std::atomic<long long>
```

访问原子变量的方式有两类，语义上有差别，值得分清楚。

**第一类是运算符**：`+=`、`-=`、`++`、`--` 以及按位运算 `&=`、`|=`、`^=`。它们读起来和普通整数一样，但每一次都是原子的。例程 `E:\CPP_Code\CppFromScratch\ch43_atomics\atomic_ops\atomic_ops.cpp` 里对 `a` 连续做了这些运算，实测输出：

```text
=== Demo A: 原子整数上的算术运算符 ===
a 初始值：10
a += 5 之后：15
a -= 3 之后：12
++a 之后：13
a 的值（--a 之后）：12
```

**第二类是成员函数**，它们能做运算符做不到的事：

| 成员函数 | 作用 | 需要留意的点 |
| --- | --- | --- |
| `load()` | 读出当前值 | 读这个动作本身也是原子的，不会读到"改到一半"的状态 |
| `store(v)` | 写入一个值 | 写入是原子的 |
| `fetch_add(n)` | 加 `n`，返回**加之前**的旧值 | "取出旧值再加"是一步完成的，可以当发号器用 |
| `fetch_sub(n)` | 减 `n`，返回旧值 | 同上 |
| `exchange(v)` | 写入 `v`，返回写入前的旧值 | 换值一步完成 |
| `compare_exchange_weak(expected, desired)` | 比较后写入：当前值等于 `expected` 才写入 `desired` 并返回 `true` | 第一个参数是引用，失败时会被回填成当前实际值 |

`fetch_add` 返回旧值这点很容易误判，例程专门把它打了出来：

```text
=== Demo B: fetch_add 交回的是加之前的旧值 ===
fetch_add(100) 交回：12
之后 a 的值：112
```

`++a` 这种写法在底层就是 `fetch_add(1)`，只是不要返回值而已。

`compare_exchange_weak` 是这几个成员函数里最需要理解的一个。它的意思是"**如果当前值还是我期望的那个，就把它换成新值**"，常用于"只在没人动过的情况下才更新"。它的第一个参数既是输入也是输出：**失败时会把当前实际值写回这个参数**，所以调用之后这个变量里可能已经不是你写的期望值了。例程把调用前后的值都打印出来，实测输出：

```text
=== Demo C: exchange 与 compare_exchange_weak ===
exchange(7) 交回：112
之后 a 的值：7
调用前：a = 7，期望值 = 7
compare_exchange_weak(把 7 换成 42) 是否成功：1
调用后：a = 42，期望值参数 = 7
```

这次期望值正好等于实际值，所以换成功了，`a` 变成 42。名字里的 `weak` 表示它**允许"假失败"**：即使值相等也可能返回 `false`（它在某些处理器上由两条指令组合实现），因此标准用法是把它放进一个循环里重试。**只要记住"失败时它会回填"，就不会被它搞得莫名其妙。**

最后一个必须知道的限制：**原子类型不可拷贝、不可移动**。它是"某个特定内存位置"的代表，拷贝一份就变成两个不同的原子变量了，所以编译器直接禁止这件事。要用它就得按引用传：

```cpp
std::atomic<int> total {0};
// 传给线程时按引用捕获（本章第 4 节的规则在这里同样适用）
myThreads.emplace_back([&total]() { /* ... */ });
```

## 19 什么时候用原子、什么时候必须用锁

原子操作看起来比锁轻便得多，但它能做的事比锁少得多。它保护的是**单个变量上的单次操作**，仅此而已。

| 场景 | 选择 | 原因 |
| --- | --- | --- |
| 一个计数器被多个线程各自加一 | `std::atomic<int>` | 单变量的单次读-改-写，原子操作正好覆盖 |
| 一个标志位被线程置位、被别的线程读取 | `std::atomic<bool>` | 同上，读写都是原子操作 |
| 把一个数按位设置/清除（如状态位） | 原子类型的 `\|=`、`&=` | 位运算同样是原子读-改-写 |
| 一段输出必须整行不被拆开 | 互斥锁 | 要保护的不是一个变量，而是"一串操作作为整体" |
| 两个变量之间必须保持某种关系（如本章第 12 节的"两个账户总额不变"） | 互斥锁 | 两次独立的原子操作之间仍可能被别的线程插进来，关系照样会被破坏 |
| 临界区里要读写多个变量、或者要调用别的函数 | 互斥锁 | 原子类型只能保护它自己那一次操作 |

把这张表压成一句话：**原子操作保证"这一个变量上的这一次操作"完整，锁保证"这一段代码"独占**。选哪种，取决于你要保护的东西是一个变量，还是一段逻辑。

需要强调的是：**用原子操作替换锁，只有在"共享数据恰好只是一个变量、且对它的每一次访问都是单次操作"时才成立**。如果你把本章第 12 节的转账例子里的两个 `balance` 都改成原子变量，各扣各加，那么"总额不变"这个不变量一样会被破坏——因为两次原子操作之间仍然存在空隙。这种时候必须回到互斥锁。

### 19.1 边界说明：本章没有展开的东西

本章讲到的原子操作，用的都是默认的内存序 `std::memory_order_seq_cst`（顺序一致性）：它最直观——每个原子操作都像是按代码顺序发生，所有线程看到的原子操作有一个统一的先后顺序。标准还允许把内存序放宽（`relaxed`、`acquire`、`release` 等）来换性能，但随之而来的是"写代码的人必须自己保证哪些操作之间存在先后关系"这套更难的规则，本章不展开。**在没弄清这些规则之前就把内存序放宽，等于把"锁写错"换成了一种更难发现的错误。**

同样没有展开的还有**伪共享（false sharing）**：多个线程各写各的变量，如果这些变量恰好落在同一条缓存行里，硬件仍然会为整条缓存行来回搬运，性能可能比用锁还差。它属于性能话题，不影响正确性。

最后交一句底：`std::thread` 还有一个 `detach()`，把线程和线程对象分开、让它在后台自己跑。它看着省事，实际很难用对——一旦 `detach`，就再没有 `join` 可以等它，也就无法保证它访问的数据（`main` 里的局部变量，甚至 `std::cout` 的缓冲）在它运行期间还活着，而程序结束时它可能还在跑。所以本章的规则始终是：**创建的每个 `std::thread` 都要有对应的 `join`**，或者直接用 `jthread` 让它自动汇合，不要用 `detach`。

一句话收束：原子操作只保证"单个变量上的单次操作"不可分割，它既保不住多个变量之间的关系，也保不住"一段代码"的独占，更不能替代锁。**原子不是万能的，该用锁的地方仍然要用锁。**

### 20.1 实验一：`thread_basic` 创建、传参、join

`thread_basic\thread_basic.cpp` 里定义了 `void printThreadId(int id)` 与 `void addMany(int times, int& result)`，`main` 里分别用它们启动了 `t1`（`join` 紧跟在后面）和 `t2`（`join` 放在主线程做完自己的活之后）。

（上面输出里的"线程 9 的累加"中，那个"9"是 `thread_basic.cpp` 中写死的标签文字，对应的其实是 `t2`，不是"第 9 个线程"。）

**验收标准**：输出与上面逐字符一致；编译时 `-Wall` 没有警告。

**改值实验**：把 `main` 里那个 `for (int i = 0; i < 100000; ++i)` 的 `100000` 改成 `200000`，**先预测**输出会变成哪样，再重新编译运行。实测结果：

```text

=== Demo B: 把结果写回主线程的变量 ===

```

第一行累加变成 `200000`，而第二行没变——因为线程那一份的循环次数写在线程的参数里（`addMany` 的 `100000`）。两边的循环次数是各自独立的，这也是"两个线程各算各的"最直观的证据。

**去掉 join 的实验**：把 `t1.join();` 注释掉，重新编译运行。线程那一行出现的位置是竞态的，下面是一次运行时看到的样子：


注意这里有两个变化：这一次线程那一行跑到了主线程输出之后（没有 `join` 的约束，换个时间它也可能出现在别的位置），程序最后异常终止（退出码非 `0`）。看完把 `join` 恢复。

### 20.2 实验二：`jthread_vector` 一组线程与自动汇合

`jthread_vector\jthread_vector.cpp` 里有两段：Demo A 让三个 `jthread` 直接往 `std::cout` 写，Demo B 改成"每个线程写自己的格子、主线程按固定顺序打印"。

**预期输出**：Demo B 的部分以及前后两行标题每次运行都完全一致，Demo A 的三行不确定。下面是一次实测的完整输出（Demo A 恰好咬在一起的那一种）：

```text
=== Demo A: 三个线程直接写 std::cout ===
thread id = thread id = 0
1thread id = 
2
=== Demo A 结束 ===
=== Demo B: 每个线程只写自己的格子 ===
thread id = 0 完成
thread id = 1 完成
thread id = 2 完成
汇总：共运行 3 个线程
```

**验收标准**（把顺序和内容分开判断）：

1. 除了 Demo A 那一段，其余每一行都与上面列出的完全一致；
2. Demo A 那一段里 `0`、`1`、`2` 三个数字各出现一次（不管它们被排成几行、会不会咬在一起）；
3. 连续运行 10 次，"汇总：共运行 3 个线程"这一行每次都在最后，且永远是 `3`；
4. 编译时 `-Wall` 没有警告。

**观察顺序实验**：把 Demo A 那一段整体放在 `for` 里再跑十几次（或者干脆多运行几次程序），至少会看到下面这几类结果：三行顺序打乱、三行顺序正好递增、以及上面那种咬在一起的输出——`0`、`1`、`2` 的排列其实是任意的，还会出现跨行的交错，混出来的形状远不止三种。**这些都是这份代码的正常表现**——因为三个线程被同时交给操作系统调度，谁先拿到 CPU、每次拿到多久，取决于当时系统里还有谁在抢 CPU。

**改值实验**：把 Demo B 里 `std::vector<std::string> lines(3);` 的 `3` 和循环里的 `i < 3` 一起改成 `5`，**先预测**会多输出哪几行，再重新编译运行。预期会多出 `thread id = 3 完成`、`thread id = 4 完成` 两行，最后一行变成 `汇总：共运行 5 个线程`。

**换类型实验**：把两处 `std::jthread` 都改成 `std::thread`（其余一字不改），重新编译运行。实测程序会在 Demo A 结束前后立刻打印：

```text

```

原因是 `vector` 析构时销毁了三个还没有汇合的 `std::thread` 对象。看完改回 `jthread`。

### 20.4 实验四：`mutex_cout` 用锁保护整行输出

`mutex_cout\mutex_cout.cpp` 的 Demo A 由三个 `jthread` 各打印一行并递增一次计数器，打印与计数都在 `lock_guard` 保护下；Demo B 用两次单线程调用演示"提前 `return` 也会解锁"。

**预期输出**：

```text
=== Demo A: 用 lock_guard 保护整行输出 ===
thread id = 0
thread id = 2
thread id = 1
=== 全部线程结束，共输出 3 行完整的输出 ===
=== Demo B: lock_guard 在提前 return 时也会解锁 ===

第一次调用提前返回，lock_guard 在这里析构并解锁
进入临界区：第二次调用
第二次调用走到函数末尾，lock_guard 在这里析构并解锁
两次调用都拿到了锁，没有死锁
```

其中三个 `thread id` 行的**顺序**每次运行可能不同（实测中出现过 `0/2/1`、`2/1/0`、`1/2/0`、`0/1/2`），其余各行每次都完全一致（实测的样子就是上面这份，第一行恰好是 `thread id = 0`、第三行是 `thread id = 1` 的那种）。

**验收标准**：

1. 其余所有行与上面逐字符一致；
2. 三个 `thread id` 行里 `0`、`1`、`2` 各出现一次，每行都以 `thread id = ` 开头、以单个数字结尾（不会再出现本章第 5 节那种咬在一起的输出）；
3. `=== 全部线程结束，共输出 3 行完整的输出 ===` 这一行总是在那三行之后，而且数字永远是 `3`；
4. 连续运行 10 次，第 2、3 条都成立；
5. 编译时 `-Wall` 没有警告。

**改值实验**：把 Demo A 里创建线程的循环条件 `i < 3` 改成 `i < 5`，**先预测**输出会变成什么样，再重新编译运行。预期会多出两行 `thread id = 3`、`thread id = 4`，最后一行变成 `共输出 5 行完整的输出`——数字由 `printedLines` 真正统计得出，不是写死的字符串。看完改回 `3`。

**死锁实验**：把 Demo A 里的 `std::lock_guard<std::mutex> lock(m);` 换成 `m.lock();`（并且**故意不写** `m.unlock();`），重新编译运行。实测现象是只打印一行 `thread id = N`（N 是哪个线程先抢到锁是不定的），然后程序**再也不结束**。在终端里按 `Ctrl+C` 终止；或者用 `timeout 6 ./mutex_cout.exe` 运行，观察它被外部终止（退出码 `124`）后打印的内容。看完把 `lock_guard` 改回来。

### 20.5 实验五：`mutex_sum` 加锁与不加锁的对照

`mutex_sum\mutex_sum.cpp` 的 Demo A 用 4 个线程各累加 250000 次、不加任何保护；Demo B 用同样的线程数、同样的次数，但每一步都在 `lock_guard` 保护下。

**预期输出**（Demo A 的"实际值"一行每次运行都不同，其余各行每次都一致）：

```text
=== Demo A: 4 个线程各加 250000 次，不加锁 ===
期望值：1000000
实际值：346320
结论：实际值与期望值不符，说明有更新被覆盖
=== Demo B: 4 个线程各加 250000 次，用 lock_guard 保护 ===
期望值：1000000
实际值：1000000
结论：实际值与期望值完全一致
```

（上面 Demo A 的 `346320` 是某一次实测的值，你运行时得到的数字几乎一定不同。）

**验收标准**：

1. Demo B 的 `实际值` **每次**都必须是 `1000000`，结论必须是"完全一致"——这是互斥锁部分最重要的一条；
2. Demo A 的 `实际值` 连续运行 10 次并记录下每次的数字：正常情况下每一次都小于 `1000000`，而且互不相同（实测 15 次全部如此）。如果某次恰好等于 `1000000`，程序会打印"这次恰好等于期望值，但程序仍有数据竞争，结果不可信"——这同样属于数据竞争的表现，不算验收失败，但要在记录里注明；
3. 除上面两类行之外，其余各行逐字符一致；
4. 编译时 `-Wall` 没有警告。

**改值实验**：把 `const int threadsPerDemo = 4;` 改成 `8`，重新编译运行。**先预测**：期望值会变成 `2000000`（8 × 250000），Demo A 的实际值会更离谱（更多线程同时抢同一个变量），Demo B 仍然必须是精确的 `2000000`。实测印证了这三点。

### 20.6 实验六：`mutex_scoped_lock` 两把锁与不变量

`mutex_scoped_lock\mutex_scoped_lock.cpp` 里两个账户各 1000 元、各带一把锁，两个线程做方向相反、金额相同的转账，每次转账用 `std::scoped_lock` 一次锁住两个账户。

**预期输出**（逐字符与实测一致，每次运行都相同）：

```text
=== Demo A: 两个方向的转账同时进行，每次 1 元，各 100000 次 ===
初始余额：A = 1000，B = 1000
=== Demo B: 汇总（所有线程结束之后） ===
A 的余额：1000
B 的余额：1000
总额：2000（初始总额 2000，必须不变）
```

**验收标准**：输出与上面逐字符一致（程序必须能自己结束，不会卡住）；`-Wall` 无警告。

**死锁实验**：把 `std::scoped_lock lock(from.m, to.m);` 换成两行独立的 `std::lock_guard`：

```cpp
std::lock_guard<std::mutex> lockFrom(from.m);
std::lock_guard<std::mutex> lockTo(to.m);
```

重新编译运行。实测现象是打印完两行标题后程序**卡死不再前进**（`timeout 6` 运行会被强制终止，退出码 `124`）。原因是两条转账方向加锁的顺序正好相反，各自持有一把锁等另一把。看完改回 `scoped_lock`。

**改值实验**：把两处 `transfer` 调用的金额（第一个 `1`、第二个 `1`）改成不一样的数，例如线程 1 每次转 2 元、线程 2 每次转 1 元，**先预测**A、B 的余额和总额会各变成多少，再重新编译运行。实测输出：

```text
=== Demo A: 两个方向的转账同时进行，每次 1 元，各 100000 次 ===
初始余额：A = 1000，B = 1000
=== Demo B: 汇总（所有线程结束之后） ===
A 的余额：-99000
B 的余额：101000
总额：2000（初始总额 2000，必须不变）
```

**总额仍然是 2000，没有偏离。** 原因在"转账"这个动作本身：每次都是"一边减、一边加"，两边的金额相同，所以不管金额被改成多少、A 和 B 的余额变成什么，总额都自动守恒。真正被改变的是各自的余额——从 `1000` 变成了 `-99000` 和 `101000`，回不到初始值了。

这说明"总额不变"这个不变量由**转账动作的对称性**保证，它检验的是"每一次转账都完整地一减一加"，用来检测"金额写错了"并不合适；要核对金额，得换一个别的量（比如各自最终的余额）去比。另外注意：输出第一行里的"每次 1 元"是例程里写死的标题文字，没有跟着参数变。看完改回来。

### 20.7 实验七：`atomic_counter` 三种累加的对照

`atomic_counter\atomic_counter.cpp` 里分三段：Demo A 用拉长窗口的方式稳定复现竞争，Demo B 用普通 `int` 紧跟视频里的循环实验，Demo C 把同一个循环换成 `std::atomic<int>`。

**预期输出**：Demo A 与 Demo C 每次运行都完全一致，Demo B 的"实际值"与"结论"两行取决于当次运行（下面是一次实测的完整输出）：

```text
=== Demo A: 把竞争窗口拉长，两个线程各递增 1 次 ===
期望值：2
实际值：1
结论：两次递增只留下一次的效果
=== Demo B: 两个线程各递增 100000 次，用普通 int ===
期望值：200000
实际值：186096
结论：实际值小于期望值，有更新被覆盖了
=== Demo C: 两个线程各递增 100000 次，用 std::atomic<int> ===
期望值：200000
实际值：200000
```

**验收标准**：

1. Demo A 的两行（`实际值：1`、`结论：两次递增只留下一次的效果`）必须每次都是这个样子——这是"稳定复现数据竞争"的依据；
2. Demo C 必须每次都精确等于 `200000`，20 次运行零例外；
3. Demo B：连续运行 20 次并记录，把结果分成"小于 200000"和"恰好等于 200000"两类分别数一数（实测结果是 13 次小于、7 次恰好相等）。**两类都算通过**，因为 Demo B 要证明的正是"有竞争时结果不可信"；
4. 编译时 `-Wall` 没有警告。

**改值实验（对应视频里的对比）**：把 `const int timesPerThread = 100000;` 改成 `100`，**先预测** Demo B 会变成什么样，再重新编译运行。实测结果和统计如下：

- `100` 次：连续 10 次运行，Demo B **每次都恰好等于 200**（视频里"小循环时结果正确"就是这么来的）；
- `1000` 次：连续 6 次运行，每次都恰好等于 2000；
- `10000` 次：连续 5 次运行，每次都恰好等于 20000；
- `50000` 次：连续 5 次运行，每次都恰好等于 100000。

**这条实验的结论比数字更重要**：Demo B 的代码从头到尾一个字没变，只是循环次数不同，结果就时而正确、时而错误。**"结果正确"从来不是"没有数据竞争"的证据**，Demo A 的稳定复现才是这份代码真正状态的暴露。做完请把数值改回 `100000`。

### 20.8 实验八：`atomic_ops` 原子类型与成员函数
