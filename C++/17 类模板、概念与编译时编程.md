# 17 类模板、概念与编译时编程

## 学习目标

完成本章后，你应当能够：

1. 用 `template <typename T>` 定义类模板并用尖括号实例化，说明每个实例是彼此独立的类型、成员函数"用到才生成"意味着什么。
2. 给类模板同时写类型参数和非类型参数，并说出后者"必须在编译期确定"的限制。
3. 说明无约束的模板会带来什么问题，并用简写语法、`template <概念 T>` 和 `requires` 子句给模板参数加约束。
4. 用 `requires` 表达式定义自己的概念、用逻辑运算符组合概念，并读懂"约束不满足"的报错。
5. 写 `constexpr` 函数与 `constexpr` 变量，配合 `static_assert` 在编译期完成并检查计算，说出 `constexpr`、`consteval`、`constinit` 三者的语义边界。

## 1 从函数模板到类模板

第 05 章学过函数模板：如果同一个算法要为多种类型服务，不必把函数写好几份，只要写一份带 `T` 的模板，让编译器按实际用到的类型生成对应版本。当时的一句话是"把一部分工作交给编译器"。

现在把同样的问题放到类上。假设我们要一个"长度可变的数组"，它应该能装 `int`、能装 `double`、也能装我们自己定义的结构体。如果按第 11 章的方式写类，就得为每种元素类型各写一个类：`int_array`、`double_array`、`student_array`……它们的数据成员、构造函数、成员函数逻辑完全一样，只有元素类型不同。这显然是重复劳动，而且这些重复的类之间没有任何关系——一个函数没法同时处理它们。

**类模板**解决的正是这件事：把一个类里"待定的类型"抽出来当参数，只写一份定义，由编译器按使用时的具体类型生成真正的类。

其实我们早就一直在用它：第 03 章的 `std::array<int, 5>`、第 07 章的 `std::vector<int>`、第 10 章的 `std::unique_ptr<T[]>` 都是类模板的实例。所谓 STL（标准模板库）里的容器，绝大多数就是类模板——`std::vector` 本身不是一个类型，它是一个"类型工厂"：给出元素类型，才有 `std::vector<int>` 这个类型。

## 2 定义一个类模板

### 2.1 语法

把 `template <typename T>` 写在 `struct`（或 `class`）的上一行，然后在类里把待定的类型写成 `T`：

```cpp
template <typename T>
struct dynamic_array
{
    int size;
    std::unique_ptr<T[]> data;

    dynamic_array(int new_size) : size(new_size), data(new T[new_size])
    {
    }

    void fill(T value)
    {
        for (int i = 0; i < size; ++i)
        {
            data[i] = value;
        }
    }
};
```

逐部分看：

- `template <typename T>` 声明了"下面这个类有一个类型参数，名字叫 `T`"。这个名字是我们自己取的类型占位名，写成 `U`、`element_type` 都行，`T` 是惯例（type 的首字母）。
- 类里凡是出现 `T` 的位置都是"以后会被替换掉"的位置：`std::unique_ptr<T[]>` 是数据成员的类型，`dynamic_array(int)` 之外的 `fill(T value)` 里 `T` 是参数类型。
- `template <typename T>` 只作用于紧跟着的那一个类定义，所以每个类模板都要各写一行。它不会"传染"到后面定义的别的类。

### 2.2 实例化：给出类型才能用

类模板本身不是一个类型，不能直接拿来创建对象。用的时候必须在尖括号里指定类型，这个动作叫**实例化**：

```cpp
dynamic_array<int> array(10);        // 编译器用 T = int 生成一个类
dynamic_array<double> double_array(10);
```

编译器看到 `dynamic_array<int>` 时，会拿 `int` 把整份定义替换一遍，生成一个真正的类——相当于它替我们手写了一个 `dynamic_array_int`。看到 `dynamic_array<double>` 时再生成一份 `dynamic_array_double`。两份代码没有任何共享，只是来源是同一份模板。

### 2.3 每个实例都是独立的类型

这一点必须记牢：**`dynamic_array<int>` 和 `dynamic_array<double>` 是两个毫不相干的类型**，它们之间没有任何转换关系：

```cpp
dynamic_array<int> ints(3);
dynamic_array<double> doubles(3);

// ints = doubles;                     // 编译错误：两个类型不能互相赋值
// void handle(dynamic_array<int>&);   // 传 double 版本进去也是错误
```

这和 `int` 与 `double` 的关系不同：`int` 能隐式转成 `double`，而两个模板实例之间不存在这种转换——它们是编译器生成的两个独立类。这也解释了为什么模板会让编译出来的程序变大：用到几种类型，就有几份完整的类代码。

## 3 类模板的成员

### 3.1 成员的类型可以来自 T

模板参数 `T` 一旦确定，类里所有跟着它写的位置都会跟着变：

| 位置 | 在 `dynamic_array<int>` 里 | 在 `dynamic_array<double>` 里 |
| --- | --- | --- |
| 数据成员 | `std::unique_ptr<int[]> data` | `std::unique_ptr<double[]> data` |
| 成员函数参数 | `void fill(int value)` | `void fill(double value)` |
| 成员函数返回类型 | 若写 `T get()` 就是 `int get()` | 若写 `T get()` 就是 `double get()` |

也就是说，一个类模板能提供一个类型的"参数化版本"，而它在某一处被使用时究竟长什么样，取决于那次实例化给出的类型。

### 3.2 成员函数"用到才生成"

类模板和函数模板一样采用**按需实例化**：只有在代码里真正调用到某个成员函数时，编译器才会为它生成那一份实现。

这带来一个非常实用的后果：**只要不调用，`T` 不支持的成员函数就不会被生成，也就不用检查。**例如 `print()` 里用了 `std::cout << data[i]`，如果拿一个没有定义 `<<` 的结构体去实例化，只要不调用 `print()`，程序照样能编译通过；一旦调用，编译器就会为它实例化并报出 `no match for 'operator<<'`。

反过来说，当模板报错时，需要学会读这类信息——它会先告诉你"我在实例化哪个函数、用的是哪个 `T`"，再给出真正的错误行：

```text
In instantiation of 'void dynamic_array<T>::print() [with T = student]':
  required from here
error: no match for 'operator<<' (operand types are 'std::ostream' ... and 'student')
```

读法是从上往下：`In instantiation of ... [with T = student]` 说明"出问题的是 `T = student` 这一次实例化"，错误本身不是模板写错了，而是这个类型不满足成员函数里的要求。

## 4 多个模板参数

### 4.1 类型参数之外还有非类型参数

模板参数不一定都是类型。`std::array<int, 5>` 里的 `5` 就是一个**非类型模板参数**：它是一个编译期常量，被用来决定数组的长度。我们自己也能这样写：

```cpp
template <typename T, std::size_t N>
struct fixed_buffer
{
    T data[N];

    void fill(T value);
    void print() const;
    T sum() const;
};
```

- `T` 决定装什么，`N` 决定装多少个；
- `N` 的类型写成 `std::size_t`（无符号整数类型，标准库用它表示大小），也可以写 `int`；
- `N` 必须由使用时的实参在编译期确定，因为编译器要真的生成一个长度为 `N` 的定长数组。写成 `fixed_buffer<int, n>`（`n` 是运行时变量）会编译失败：
  `error: the value of 'n' is not usable in a constant expression`。

这一点正是 `fixed_buffer` 与 `dynamic_array` 的根本区别：前者把"长度"放进类型（零次动态分配），后者把"长度"放进构造函数参数（构造时才决定）。

### 4.2 类外定义成员函数要多写两行

在类外定义模板类的成员函数时，必须把模板参数列表重复一遍，并且在类名后面带上参数：

```cpp
template <typename T, std::size_t N>
void fixed_buffer<T, N>::fill(T value)
{
    for (std::size_t i = 0; i < N; ++i)
    {
        data[i] = value;
    }
}
```

三处必须有：`template <typename T, std::size_t N>` 这一行、类名后面的 `<T, N>`、以及参数列表里照样用的 `T` 和 `N`。漏掉任何一处，编译器就没法把这份定义和模板里的成员对应起来，于是报出下面这类错误：

```text
error: 'template<class T, long long unsigned int N> struct fixed_buffer' used without template arguments
```

### 4.3 参数是类型的一部分

`fixed_buffer<int, 4>` 和 `fixed_buffer<int, 8>` 是两个不同的类型，因为它们给的模板实参不同。所以：

- 它们之间不能互相赋值；
- 作为函数参数时不会被当作同一个类型；
- 长度不同的两个缓冲不算"同一种容器"。

### 4.4 模板定义要对使用它的代码可见

模板不是运行时的东西，编译 `dynamic_array<int> array(10);` 这一行时，编译器需要看到 `dynamic_array` 的**完整定义**（而不是像普通函数那样只要一个声明）。所以在单文件例程里一切正常，但把类模板的成员函数定义单独放进一个 `.cpp`、只在别处留声明，就会出现"编译通过、链接失败"的现象（链接器找不到那个未被生成的函数）。正确做法是把模板的定义放在头文件里，让每个用到它的源文件都能看到。本章的三个例程都是单文件自包含，不涉及这个问题；这里只是先把坑标出来。

类模板把"待定的类型"交给了编译器，但它也把函数模板的一个老问题原样带了过来：模板对传进来的类型几乎不做任何检查。这个问题值得单独拿出来看清楚。

## 5 模板太自由带来的问题

第 05 章的模板让一份代码服务多种类型，代价是**模板对类型几乎没有任何要求**。看这个函数：

```cpp
template <typename T>
void print(T value)
{
    std::cout << value << std::endl;
}
```

它接受任何能打印的类型。如果作者的意图是"只用于整数"，这个意图只存在于注释或别人脑子里，编译器一无所知。使用者完全可以这样调用：

```cpp
print(10.352);      // 编译通过，但这不是这个模板被设计出来要处理的东西
```

后果分两种：

- **运气不好的时候**，函数体里某个操作在新类型上不成立，编译器在模板实例化**深处**报出一大串错误。真正的原因（"这个类型不该传进来"）淹没在几十行模板展开信息里。
- **运气更不好的时候**，代码**编译通过、正常运行**，只是结果不符合期望——这类问题要到运行期才暴露，代价最大。

把"这个类型不该传进来"这类问题也提前到编译期拦下，是模板这条主线一直缺少的一环。这一节给出语言层面最直接的答案：**把模板的适用范围从注释里的约定，变成编译器能检查的规则**。承担这件事的语言设施叫**概念**（concept）。

## 6 概念是什么

概念是一个**编译期就能算出真假的布尔量**，用来回答"某个类型满足某组要求吗"。C++20 在 `<concepts>` 里提供了一整套标准概念，常用的有：

| 标准概念 | 含义 |
| --- | --- |
| `std::integral<T>` | `T` 是整数类型（含 `bool`、`char`） |
| `std::signed_integral<T>` / `std::unsigned_integral<T>` | `T` 是有符号 / 无符号整数类型 |
| `std::floating_point<T>` | `T` 是浮点类型 |
| `std::same_as<T, U>` | `T` 和 `U` 是同一种类型 |
| `std::convertible_to<From, To>` | `From` 能转换成 `To` |
| `std::derived_from<D, B>` | `D` 派生自 `B` |
| `std::movable<T>` / `std::copyable<T>` | `T` 能移动 / 能拷贝 |

因为概念的值就是一个 `bool`，它可以放在任何能用常量表达式的地方，包括 `static_assert`：

```cpp
static_assert(std::integral<int>);
static_assert(!std::integral<double>);
```

（节选自例程 `constrained_print\constrained_print.cpp`。）

**这几行值得仔细看**：`std::integral` 覆盖的类型比直觉更宽——`short`、`char`、`bool` 都算整数类型，`double`、`float` 不算。如果不确定某个类型是否满足某条概念，写一行 `static_assert` 让编译器回答，比猜要快得多。

## 7 给模板参数加约束的两种写法

### 7.1 简写模板语法：概念写在 `auto` 前面

第 05 章见过用 `auto` 参数写模板：

```cpp
void print(auto value);         // 等价于 template <typename T> void print(T value)
```

C++20 允许在这个 `auto` 前面放一个概念名，用来收紧它接受的范围：

```cpp
void print(std::integral auto value);       // 只有整数类型能进来
```

这就是**简写模板语法**：它仍然是模板（每个不同的类型各生成一份），只是把"类型必须满足什么"写在了参数上，读起来像一句自然语言的声明。它和下面 7.2 节的长写法完全等价。

简写语法也可以用在返回类型上，两个位置的约束都要满足：

```cpp
std::integral auto halfOf(std::integral auto value)
{
    return value / 2;
}
```

（节选自例程 `constrained_print\constrained_print.cpp`。注意 `value / 2` 是整数除法，`halfOf(7)` 得到 3 而不是 3.5。）

### 7.2 `requires` 子句：两种位置

需要给多个模板参数写约束、或者约束比较复杂时，用 `requires` 子句。它有两个位置，效果相同：

```cpp
// 位置一：紧跟在模板头之后
template <typename T>
    requires std::integral<T>
T addOne(T value)
{
    return static_cast<T>(value + 1);
}

// 位置二：尾置 requires 子句，放在参数列表之后
template <typename T>
T halfOf(T value) requires std::integral<T>
{
    return value / 2;
}
```

（节选自例程 `explicit_requires\explicit_requires.cpp`。）

`requires` 子句里写的是一个**编译期布尔表达式**，所以概念、`||`、`&&`、`!` 以及 `sizeof` 之类的常量表达式都能用：

```cpp
template <typename T>
    requires (std::integral<T> && (sizeof(T) <= 4))
```

最省事的一种写法其实介于两者之间：`template <std::integral T>`。它把概念直接写在模板参数的位置上，和 `template <typename T> requires std::integral<T>` 等价，读起来更紧凑：

```cpp
template <std::integral T>
T addOne(T value);      // 与上面第 7.1 节的写法等价
```

三种写法（`std::integral auto` 参数、`template <std::integral T>`、`requires` 子句）表达的是同一件事。选哪种只影响可读性：**单个参数、约束简单**用简写语法；**多个参数或需要组合条件**用 `requires` 子句；**类模板或需要给读者强调类型名**用 `template <概念 T>`。

### 7.3 约束在什么时刻检查

每次用某个类型实例化模板时都会检查一遍约束：不满足就不生成这个版本，也不会有任何运行期开销。这是概念与运行期 `if` 判断的根本区别——**约束只影响"能不能编译"，不影响运行时的速度**。

约束也不要求参数是常量，它约束的是**类型**：例程里 `addOne(fromInput)` 用的是普通的 `int` 变量，一样通过。

## 8 定义自己的概念

标准概念只覆盖最基础的类型性质。要表达"这个类型必须能相加""这个类型必须能打印"这类领域内的要求，就得自己定义概念，工具是 **`requires` 表达式**。

### 8.1 `requires` 表达式

`requires` 表达式的写法是：花括号里放一段"如果这个类型能用，就应该写得出来"的代码。编译器只检查它能不能成立，**不会真的执行**。

```cpp
template <typename T>
concept Addable = requires(T a, T b)
{
    { a + b } -> std::convertible_to<T>;
};
```

逐部分读：

- `template <typename T> concept 名字 = ...`：定义一条名为 `Addable` 的概念；
- `requires(T a, T b)`：括号里声明这次检查要用到的"假的"变量，它们只存在于检查中；
- `{ a + b } -> std::convertible_to<T>`：这是一条**复合要求**——`a + b` 必须合法，而且它的结果必须能转换成 `T`。

第二条复合要求同样常见：

```cpp
template <typename T>
concept Printable = requires(std::ostream& os, T value)
{
    { os << value } -> std::convertible_to<std::ostream&>;
};
```

（节选自例程 `custom_concept\custom_concept.cpp`。）

这两个概念可以直接用 `static_assert` 验证：

```cpp
static_assert(Addable<int>);
static_assert(Addable<double>);
static_assert(!Addable<const char*>);      // 两个指针不能相加
```

`requires` 里的要求可以写成几种形式：`{ 表达式 } -> 概念`（检查表达式合法且结果满足概念）、单纯写 `a + b;`（只检查合法性）、以及 `typename T::value_type;` 这类嵌套要求。日常用得最多的是第一种。

### 8.2 自定义类型同样满足概念

概念检查的是"这个类型能不能做这些事"，而不是"它继承自谁"。例程里给一个二维向量加上 `operator+`（第 13 章的运算符重载）和输出运算符：

```cpp
struct Vec2
{
    int x;
    int y;
};

Vec2 operator+(Vec2 lhs, Vec2 rhs)
{
    return Vec2 {lhs.x + rhs.x, lhs.y + rhs.y};
}
```

`Vec2` 没有继承任何东西、也没有注册任何接口，但它自动满足 `Addable` 和 `Printable`——因为这两条概念要求的运算它确实提供了。这种"不问你是谁、只问你能不能做"的检查方式，是概念最像"约定"的地方：**约束的是一种能力，不是一种血统**。

### 8.3 组合概念

概念之间可以用逻辑运算符组合，写出更精确的要求：

```cpp
template <typename T>
concept AddableAndPrintable = Addable<T> && Printable<T>;

template <typename T>
concept SmallIntegral = std::integral<T> && (sizeof(T) <= 4);
```

`SmallIntegral` 要求"是整数类型，并且不超过 4 字节"，因此 `int`、`short`、`char` 满足，`long long`（8 字节）和 `double` 都不满足。`&&` 表示两条都要成立，`||` 表示任一成立即可，`!` 表示取反。

概念还能直接用于模板参数，读起来就是把要求写在签名上：

```cpp
template <Addable T>
T sum3(T a, T b, T c)
{
    return a + b + c;
}
```

## 9 概念如何参与重载

概念出现在重载里时，有一条重要规则：**多个候选同时可行时，约束更强的那个胜出。**

```cpp
template <typename T>
void describe(T value);                    // 无约束，兜底

template <std::integral T>
void describe(T value);                    // 要求整数

template <std::floating_point T>
void describe(T value);                    // 要求浮点
```

例程 `concept_overloads` 实测四种调用：`describe(42)` 走整数版本，`describe(2.5)` 和 `describe(1.5f)` 走浮点版本，而 `describe("text")` 传的是字符串字面量（类型是 `const char*`），两条概念都不满足，于是落到那个**无约束**的版本。

这里的选法是确定的，不依赖报错顺序：满足 `std::integral` 的版本比无约束版本"约束更强"，编译器按这条规则挑选。所以**保留一个无约束的兜底版本**是一种实用做法：约束不够强的类型有地方可去，不会直接编译失败。

另外，`std::integral` 与 `std::floating_point` 互不重叠，一个类型不可能同时满足两者，因此这两个重载不会产生"选不出来"的歧义。自己定义概念时要留意这一点：如果两条概念可以同时被同一个类型满足，又都出现在重载里，就需要用 `&&`、`!` 把它们的适用范围区分开。

## 10 读"约束不满足"的报错

约束失败时的第一行看起来很像"这个函数不存在"：

```text
error: no matching function for call to 'print(double)'
  • there is 1 candidate
    • candidate 1: 'template<class auto:6>  requires  integral<auto:6> void print(auto:6)'
      • template argument deduction/substitution failed:
        • constraints not satisfied
          • required for the satisfaction of 'integral<auto:6>' [with auto:6 = double]
            concept integral = is_integral_v<_Tp>;
          • the expression 'is_integral_v<_Tp> [with _Tp = double]' evaluated to 'false'
```

（用 `print(3.14)` 调用 `void print(std::integral auto value)` 时的实测输出，节选。）

解读这几行的顺序：先看 `constraints not satisfied`，它说明不是"重名写错了"或"参数个数不对"，而是**约束没过**；再往下看 `required for the satisfaction of ...` 指名了是哪条概念；最后一行 `evaluated to 'false'` 给出结论。定位问题时**从下往上看**比从上往下读快得多。

两个细节值得记住：

- 简写语法生成的模板参数在诊断里**没有名字**，显示成 `auto:6`，看不出实际类型是什么。如果这个提示让你困扰，把它改写成显式的 `template <std::integral T>`，报错里就会显示 `T`。
- 报错最后有时会附上 `set '-fconcepts-diagnostics-depth=' to at least 2 for more detail`，按它的建议加参数可以看到更深一层的原因（比如自定义概念里究竟是哪一条要求不成立）：

```text
"E:/msys64/ucrt64/bin/g++.exe" -std=c++20 -Wall -fconcepts-diagnostics-depth=2 constrained_print.cpp -o constrained_print.exe
```

自定义概念失败时，这一层信息尤其有用——它会直接指出 `the required expression '(a + b)' is invalid` 这样的位置，而不用我们自己在一组要求里猜。

无论是类模板按类型生成代码，还是概念在实例化时检查约束，这些工作全部发生在编译期。编译期其实还能做更多事——比如把计算本身也搬过去。下面就看围绕这一目标的几个关键字。

## 11 为什么把计算搬到编译期

我们一直默认一件事：程序里的算术是在**运行期**做的。变量、循环、函数调用，都在程序跑起来之后执行。

但有一个不对称的事实：**程序编译一次，可能运行很多次**。服务器上常驻的服务、每天定时跑的数据处理脚本、被反复调用的库函数——编译那一次花掉的时间是"一次性成本"，而运行期花掉的时间是"每次运行都要付"的成本。凡是输入在编译期就确定、结果永远不变的计算，都可以提前到编译期做完，把每次运行的开销省掉。

编译期求值还有第二个好处：**错误可以提前到编译期暴露**。一个在运行期才会算出来的越界、溢出或类型不匹配，要等到程序跑到那一行才被发现；把同样的计算放到编译期，编译器在编译时就能报错。

这两种收益有一个共同的代价：编译时间会变长，而且这类计算只能使用编译期就能确定的数据。这一部分的三个关键字就是围绕"哪些东西可以在编译期求值"展开的。

## 12 `constexpr` 函数

把一个函数声明成 `constexpr`，含义是**这个函数允许在编译期求值**：

```cpp
constexpr int factorial(int n)
{
    return n <= 1 ? 1 : n * factorial(n - 1);
}
```

这里用递归实现阶乘（第 04 章的函数与递归）：$n! = n \times (n-1) \times \cdots \times 1$，基例是 $0! = 1! = 1$，所以 $5! = 120$。

### 12.1 "允许"这两个字很重要

`constexpr` 不等于"必须编译期算"。它真正的含义是：**当一个 `constexpr` 函数的实参本身是常量表达式时，编译器可以在编译期把结果算出来；实参来自运行期数据时，它照样能在运行期被调用。**同一份函数体同时服务这两种场景：

```cpp
constexpr int f5 = factorial(5);     // 实参是常量 → 编译期算出 120

int n = 6;                           // 普通变量，编译期不知道它的值
int f6 = factorial(n);               // 只能在运行期调用
```

这是 `constexpr` 最有价值的地方：写库的人不必为"编译期用"和"运行期用"各写一份实现。它和模板的情形很像——第 05 章的模板让同一份代码服务多种类型，`constexpr` 让同一份代码服务两个求值时机。

### 12.2 怎么确认它真的在编译期算完了

光看输出是看不出来的：编译期算出的 120 和运行期算出的 120 打印出来一模一样。有三种可靠的确认方式。

**第一种是 `static_assert`**（下一节细讲）——它的条件必须在编译期确定，能通过就说明右边的函数确实在编译期求值了。

**第二种是看反汇编。** `objdump -d -C` 会打印出程序的机器指令并还原符号名（`-C` 是 demangle，把修饰过的函数名还原成可读形式）。下面这个完整的小程序只做编译期求值：

```cpp
#include <iostream>

constexpr int factorial(int n)
{
    return n <= 1 ? 1 : n * factorial(n - 1);
}

int main()
{
    constexpr int result = factorial(5);
    std::cout << result << std::endl;
    return 0;
}
```

编译之后反汇编它，`main` 内的指令是这样的（只摘关键几行）：

```text
0000000140001490 <main>:
   14000149d:	c7 45 fc 78 00 00 00 	movl   $0x78,-0x4(%rbp)
   1400014ab:	ba 78 00 00 00       	mov    $0x78,%edx
   1400014b3:	e8 30 00 00 00       	call   1400014e8 <std::ostream::operator<<(int)>
```

`0x78` 就是十六进制的 120——编译器把结果直接写进了指令，**没有 `call factorial`**，运行期不需要再做任何计算。

例程 `factorial_constexpr` 同时包含编译期与运行期两种用法，反汇编它能看到两边的差别：

```text
   1400014a6:	c7 45 fc 78 00 00 00 	movl   $0x78,-0x4(%rbp)   # Demo A：120 直接写成常量
   14000150a:	c7 45 f8 06 00 00 00 	movl   $0x6,-0x8(%rbp)    # Demo B：n = 6
   140001516:	e8 b5 16 00 00 00    	call   140002bd0 <factorial(int)>   # Demo B：运行期真的调用
```

**第三种是看时间**：把同样的计算跑上几百万次，对比编译期版本与运行期版本的耗时。这种方式受优化等级影响很大，不如前两种可靠。

### 12.3 函数体里能写什么

C++11 刚引入 `constexpr` 时限制很严：函数体只能是一条 `return` 表达式。现在这些限制已经放开，`constexpr` 函数里可以有：

- 局部变量与赋值；
- `if`、`switch`、循环；
- 递归调用自己；
- 调用其他 `constexpr` 函数。

只有一条底线：**所有参与计算的量都必须是编译期能确定的**。一旦函数体里碰了运行期才有的东西（读文件、调 `std::random_device`、用输入的值），这次调用就不能在编译期完成——`constexpr` 函数在这种情况下会退回运行期执行；而在**必须**是常量的位置（`constexpr` 变量的初始化、`static_assert` 的条件），编译器会直接报错。

### 12.4 溢出边界

阶乘增长极快，用 `int` 装的时候要盯着边界：

$$\text{12!} = 479001600 \quad \text{（还在 int 范围内）}, \qquad \text{13!} = 6227020800 \quad \text{（已超出）}$$

本机的 `int` 上限是 $2147483647$，所以 `factorial(13)` 开始溢出。溢出是有符号整数的未定义行为，编译期求值也躲不开这个限制——它只是把错误提前到了编译期而已。这类"范围有限"的计算，正是 `static_assert` 最该守住的地方。

## 13 `constexpr` 变量与 `static_assert`

### 13.1 `constexpr` 变量

`constexpr` 写在变量前面，要求**用常量表达式初始化**：

```cpp
constexpr int f5 = factorial(5);        // 合法：右边是常量表达式
int n = 5;
constexpr int bad = factorial(n);       // 非法：n 不是常量表达式
```

第二行会编译失败，报错是：

```text
error: the value of 'n' is not usable in a constant expression
note: 'int n' is not const
```

`constexpr` 变量隐含 `const`：它的值不能再改。因为编译期就已经定下来了，所以它能被用在**要求写死常量**的地方，例如数组长度、`std::array` 的第二个模板参数（第 4 节讲过的非类型模板参数）、`case` 标签：

```cpp
std::array<int, factorial(4)> buffer {};     // 长度 24，编译期确定
```

### 13.2 `static_assert`：把检查放到编译期

`static_assert(条件, "说明")` 在编译期检查一个常量表达式，条件为假就直接**编译失败**。它不产生任何运行期代码：

```cpp
static_assert(factorial(5) == 120, "5! should be 120");
static_assert(factorial(0) == 1, "0! should be 1");
```

写错时的报错非常直接：

```text
error: static assertion failed: 5! should be 120
  • the comparison reduces to '(120 == 121)'
```

最后一行会告诉你编译器实际算出来的两个值，定位问题不用猜。`static_assert` 只能放在能写声明的地方，但它和 `constexpr` 一样，把"我心里认为这里应该是多少"变成了编译器负责执行的规则。

### 13.3 在编译期造一张表

`constexpr` 函数体里可以循环、可以操作 `std::array`，所以"在编译期算出一张查找表"是很自然的用法：

```cpp
constexpr std::array<int, 10> makeSquares()
{
    std::array<int, 10> result {};

    for (int i = 0; i < 10; ++i)
    {
        result[static_cast<std::size_t>(i)] = i * i;
    }

    return result;
}

constexpr std::array<int, 10> squares = makeSquares();   // 全局的编译期常量表

static_assert(squares[9] == 81, "squares[9] should be 81");
```

（节选自例程 `constexpr_table\constexpr_table.cpp`。）

命名空间作用域上的 `constexpr` 变量会在**静态初始化**阶段就位，内容直接存在可执行文件的只读数据段里，程序启动时不需要执行任何计算。用它的时候可以是运行期：例程里用普通变量 `int index = 6;` 去访问 `squares[index]`，得到 36，说明"编译期造数据"和"运行期用数据"是两件互不冲突的事。

查表法在需要反复计算同一组值的场景（三角函数近似、CRC 校验、颜色转换）里很实用：算一次、用无数次。

## 14 `consteval`：强制编译期求值

`constexpr` 是"允许"，`consteval` 是"必须"。用 `consteval` 声明的函数叫**立即函数**（immediate function），每一次调用都必须在编译期求值，没有运行期版本可退：

```cpp
consteval int square(int x)
{
    return x * x;
}

constexpr int limit = square(10);     // 合法：实参是常量
int n = 5;
std::cout << square(n);               // 非法：n 不是常量表达式
```

第二段代码的报错是：

```text
error: call to consteval function 'square(n)' is not a constant expression
error: the value of 'n' is not usable in a constant expression
note: 'int n' is not const
```

第一种错误（`call to consteval function ... is not a constant expression`）只在 `consteval` 上出现，看到它就能确定问题是"这个调用拿不到编译期可用的实参"。

`consteval` 的用途是**把"只能编译期做的事"写进接口**。一个典型的例子是编译期的字符串检查、编译期的单位换算表构造——这些函数的返回值必须参与后续的编译期计算，如果允许它在运行期被调用，那类代码就会在别处报出更难懂的错。用 `consteval` 声明，误用的代价从"错误发生在很远的地方"变成"错误就在这一行"。

## 15 `constinit`：只保证静态初始化

`constinit` 管的是另一件事：它要求变量在**程序启动之前**（静态初始化阶段）就完成初始化。

```cpp
constinit int counter = 100;      // 静态初始化，但它不是常量
```

它的两个要点：

- **它不表示变量是常量。** `counter` 可以被修改，例程里 `counter += 1;` 之后打印出 101。这一点和 `constexpr` 变量完全相反。
- **它要求初始化表达式是常量表达式。** 写成运行期才能确定的值会编译失败：

```text
error: 'constinit' variable 'counter' does not have a constant initializer
error: call to non-'constexpr' function 'std::random_device::result_type std::random_device::operator()()'
```

`constinit` 解决的是"静态初始化顺序"问题：多个全局对象之间的初始化顺序在跨编译单元时没有保证，一个全局对象用另一个还没初始化好的全局对象来初始化，就会读到无意义的值。给它加 `constinit`，编译器会强制要求它的初始化不依赖任何运行期逻辑，从根上排除这类问题。这一点只需要知道语义边界：**`constinit` 是"初始化时机"的约束，与"能不能改"无关。**

## 16 三者对照与选择

| 关键字 | 用在哪 | 要求 | 值能不能改 | 典型用途 |
| --- | --- | --- | --- | --- |
| `constexpr` 函数 | 函数 | 允许编译期求值，也可以在运行期调用 | —— | 既能编译期用、也能运行期用的通用计算（阶乘、表格构造） |
| `constexpr` 变量 | 变量 | 必须用常量表达式初始化 | 不能（隐含 `const`） | 编译期常量、表格、用作数组长度 |
| `consteval` | 函数 | 每次调用都必须在编译期求值 | —— | 只应存在于编译期的计算，把误用挡在编译期 |
| `constinit` | 变量 | 必须静态初始化（初始化是常量表达式） | 能改 | 全局状态、需要在启动前就绪且运行期会变化的变量 |

选择思路很直接：

1. 需要一个"编译期就知道、之后不变"的值 → `constexpr` 变量；
2. 需要一个既能编译期求值、又能在运行期用运行期数据调用的函数 → `constexpr` 函数；
3. 需要一个"只能在编译期用"的函数 → `consteval`；
4. 需要一个"启动前就初始化好、但之后会被修改"的全局变量 → `constinit`。

还有一条工程上的提醒：把计算搬到编译期，代价是编译时间变长、可调试性下降（编译期算出来的值在调试器里没有调用栈可看）。真正值得搬的是那些"结果固定、调用频繁、开销可见"的计算，而不是把所有函数都标上 `constexpr`。
