## 1 对象消失以后，那块内存归谁

第 24 章的构造函数解决的是"对象出生时该做什么"。这一章处理另一半：**对象消失时该做什么**。

大多数对象不需要特殊处理。`int`、`std::array<int, 3>` 这类对象的所有数据都直接装在自己身体里，对象一消失，它占的那点空间自然被收回，不需要谁去做额外的事。

但从第 18 章开始，我们手里多了一种对象：**通过 `new` 申请来的内存**。它可以理解成一张"钥匙"，对象自己只保存钥匙，也就是那个指针；真正装数据的空间在别的地方。这就带来一个新问题——**对象消失的时候，钥匙被丢掉了，可门后面的房间还锁着**。那块内存既没有被释放，也没有任何人再持有它的地址，程序再也无法访问它。这种现象叫**内存泄漏**（memory leak）。

本章要处理的典型情况是一个自定义的动态整数数组类型：数据成员是 `int* array`，构造函数里 `new int[size]` 申请空间，然后在程序里正常使用它。这个类型能用、能算，唯一的毛病是"用完不还"。程序跑完一次没什么感觉，但这类代码放进循环或长期运行的服务里，占用的内存会一直涨上去。

**析构函数就是为这件事存在的**：它是对象的"收尾指令"，在对象被销毁的那一刻自动执行，用来把对象曾经获取的资源交还回去。

## 2 析构函数的写法

### 2.1 名字与三条限制

析构函数的写法与构造函数是对称的：

| | 构造函数 | 析构函数 |
| --- | --- | --- |
| 名字 | 类名本身，如 `int_array` | `~` 加上类名，如 `~int_array` |
| 参数 | 可以有任意个 | **一个都不能有** |
| 返回类型 | 不写 | 不写（连 `void` 都不写） |
| 调用者 | 创建对象时由编译器调用 | 销毁对象时由编译器调用 |

例子：

```cpp
struct int_array
{
    int* array;

    int_array(int size)
    {
        array = new int[size] {};
    }

    ~int_array()
    {
        delete[] array;
    }
};
```

三点要记住：

- 名字是 `~` 加类名，`~` 读作"波浪线"。这个符号是析构函数唯一的记号，**没有第二种写法**。
- **不能带参数**。析构函数的执行时机由编译器决定，调用者无处传参，所以带参数的析构函数没有意义。写了会直接报错：`error: destructors may not have parameters`。
- **不能写返回类型**。连 `void` 都不写。写了 `void ~int_array() {...}` 会报 `error: return type specification for destructor invalid`。这和构造函数是同一套规则：这两个特殊成员函数的"返回类型位置"是留空的。

### 2.2 它不该被手动调用

析构函数与普通成员函数最大的区别在于**触发方式**。它不需要、也不该由我们按名字调起来：

```cpp
int_array a(10);
// a.~int_array();      // 语法上允许，但几乎总是错的，不要这样写
```

语言确实允许写出这种显式调用（构造函数连这个余地都没有），但它几乎总是错的原因和"重复释放"有关：析构函数的正当执行时机由编译器在三个时刻安排，你手动调一次，编译器到点还会再调一次，同一个资源就被释放了两遍。本章第 4 节把这三个时刻列清楚。

换一个角度说，析构函数是一个**特殊成员函数**：它在对象生命周期结束时被调用，用途是释放对象在生命周期中获取的资源。这句话里有两个词是关键——"生命周期结束"决定它什么时候跑，"释放资源"决定它该写什么。写析构函数时只要问自己一句：**这个对象活着的时候拿到了什么，需要在它死后交还？**

## 3 配对：`new` 配 `delete`，`new[]` 配 `delete[]`

回到例程 `E:\CPP_Code\CppFromScratch\ch25_destructors\manual_cleanup\manual_cleanup.cpp`。它的构造函数和析构函数正好把第 18 章的申请与释放配对起来：

```cpp
int_array(int size)
{
    std::cout << "ctor: allocate " << size << " ints" << std::endl;
    array = new int[size] {};
}

~int_array()
{
    std::cout << "dtor: free the ints" << std::endl;
    delete[] array;
}
```

有两个细节值得展开。

**第一，`new int[size] {}` 末尾的那对花括号。** 数组形式的 `new` 如果只写 `new int[size]`，元素是**默认初始化**的，也就是没有被赋任何值，读它们属于未定义行为。加上一对空的 `{}` 才变成**值初始化**，整块内存被置零。两种写法申请内存的效果一样，区别只在元素有没有初始值。本章例程统一写成 `new int[size] {}`，这样即使我们只设置了第 0 个元素，其余元素也有确定的值可读。

**第二，`delete[]` 与 `delete` 的区别。** `new int[10]` 一次申请了 10 个 `int`，释放时必须写 `delete[] array;`，让运行库知道"要释放的是一整块数组，不是单个对象"。写成 `delete array;` 会编译通过、`-Wall` 也可能一句警告都没有，但它属于未定义行为——**这是那种"代码看着对、行为不对"的问题里最难查的一类**，因为编译器不会替你拦下来。

### 3.1 程序里的输出顺序说明了什么

例程里 `main` 只做了三件事：创建对象、设置并打印 `a.array[0]`、`return 0`。运行结果是：

```text
=== Demo A: construct an object of 10 ints ===
ctor: allocate 10 ints
a.array[0] = 10
=== Demo B: leave main ===
dtor: free the ints
```

注意 `dtor` 那行出现的**位置**：它在 `=== Demo B: leave main ===` 之后。原因不是我们在这行后面写了释放代码，而是 `main` 的 `return 0;` 执行完，局部对象 `a` 超出作用域被销毁，编译器在这里插入了一次 `~int_array()` 调用。**析构函数是"到期自动执行"，不是"写在哪儿就在哪儿执行"。**

如果删掉 `~int_array()`，程序的行为完全一样，只是再也没有 `delete[]` 这一句，那块 40 字节的内存就永远回不来了——**输出看不出来，泄漏也没有任何提示**。这解释了为什么析构函数必须由写类型的人负责：使用这个类型的人根本看不到指针背后的内存。

## 4 析构函数的三个触发时刻

例程 `E:\CPP_Code\CppFromScratch\ch25_destructors\scope_lifetime\scope_lifetime.cpp` 里定义了一个不管理任何资源、只在创建和销毁时各打印一行的 `tracker` 类型，专门用来看清时机：

```cpp
struct tracker
{
    const char* name;

    tracker(const char* label) : name(label)
    {
        std::cout << "construct " << name << std::endl;
    }

    ~tracker()
    {
        std::cout << "destruct " << name << std::endl;
    }
};
```

它的三个触发时刻是：

**一、花括号作用域结束。** 一对 `{}` 就是一个作用域。在一对花括号里创建的对象，离开这对花括号时立刻被销毁：

```cpp
{
    tracker inner("inner");
    std::cout << "still inside the block" << std::endl;
}
std::cout << "after the block" << std::endl;
```

输出里 `destruct inner` 夹在 `still inside the block` 和 `after the block` 之间。**对象的生命周期跟着作用域走，跟代码的行号无关。**

**二、函数返回。** 函数里的局部对象在函数返回时销毁。`main` 里的局部对象也一样，只不过 `main` 的"返回"就是整个程序结束。

**三、`delete` 一个动态创建的对象。** `new` 出来的对象不受花括号作用域管辖，它的生命周期由 `delete` 划句号：

```cpp
tracker* heap = new tracker("heap");
delete heap;
```

`destruct heap` 紧跟在 `delete heap;` 之后出现，**而不是等到程序结束**。反过来说，如果这里忘了 `delete`，`~tracker()` 永远不会执行——这就是第 3 节说的泄漏在对象层面的样子。

### 4.1 同一作用域内按创建的逆序销毁

在同一个作用域里创建多个对象时，**销毁顺序与创建顺序严格相反**：

```text
construct first
construct second
construct third
destruct third
destruct second
```

理由是**后创建的对象可能用到先创建的对象**：如果后创建的对象持有一个指向先创建对象的引用或指针，先销毁它就会留下一根悬空的指针。反过来（后创建的先销毁）则总是安全的。所以这条规则不是约定，而是唯一说得通的顺序。

同一条规则也适用于**成员对象**：一个对象被销毁时，它自己的数据成员会跟着被销毁，顺序同样与声明顺序相反。下一节要用的 `unique_ptr` 成员正是靠这条规则自动完成释放的。

## 5 RAII：让对象自己管自己的资源

把上面的东西合起来看，会发现一个很有力的模式：

> **对象在创建时获取资源，在销毁时释放资源。** 于是只要对象还活着，资源就一定没被释放；对象一消失，资源就一定被交还。

这个模式叫 **RAII**（Resource Acquisition Is Initialization，资源获取即初始化）。它的价值在于把"别忘了释放"这件事从**人**手里交给**编译器**：

- 不再需要在每个 `return` 之前、每个出错分支上都写一遍释放代码——只要局部对象在作用域里，离开时它必然被销毁；
- 类型的使用者完全不用关心资源管理，拿到对象就用，用完就走；
- 资源管理的逻辑只写一遍，写在类型自己身上。

这不是什么新东西，你其实一直在用。`std::vector`（第 14 章）就是 RAII 的典型：往里面加元素时它自动扩容，你从来不用管它内部那块动态数组是什么时候申请的；`vector` 对象销毁时，它内部的内存一定被释放。**标准库容器的背后就是"构造函数申请、析构函数释放"这一对**，只是已经替你写好了。

## 6 什么时候不用写析构函数：把裸指针换成 `unique_ptr`

`manual_cleanup` 那个类型里，真正需要"手动管理"的其实只有一块数组内存。既然第 19 章的 `unique_ptr` 本身就是一个 RAII 类型（它的析构函数会释放自己独占的资源），那就不必由我们手写删除逻辑。

例程 `E:\CPP_Code\CppFromScratch\ch25_destructors\unique_ptr_no_dtor\unique_ptr_no_dtor.cpp` 把数据成员换成了 `std::unique_ptr<int[]>`：

```cpp
struct int_array
{
    std::unique_ptr<int[]> array;

    int_array(int size) : array(new int[size] {})
    {
        std::cout << "ctor: allocate " << size << " ints" << std::endl;
    }

    // 没有析构函数
};
```

三处变化：

1. **成员的类型从 `int*` 变成 `std::unique_ptr<int[]>`**，尖括号里写 `int[]` 表示"它独占的是一个整数数组"，这样 `unique_ptr` 析构时会用 `delete[]`（而不是 `delete`）释放它。
2. **申请内存的语句搬到了成员初始化列表中**：`array(new int[size] {})`。第 24 章讲过成员初始化列表是数据成员真正被初始化的地方，这里用它把"申请出来的内存"直接交给 `unique_ptr` 保管。构造函数体里不再有 `new`。
3. **析构函数被删掉了**。对象销毁时，它的成员 `array` 也被销毁，`unique_ptr` 的析构函数负责释放那块内存。清理工作还在，只是**从"我们写"变成"成员自己写"**。

运行结果和裸指针版本一样能正常读写 `a.array[0]`，而整个过程没有任何一行释放代码。这就是"现代 C++ 里大多数类不需要自己写析构函数"的原因：**只要把每一个资源都交给一个已经会自我清理的成员去管，编译器拼起来的就是正确的清理流程。**

这里还有一个反方向的观察：`unique_ptr` 拥有独占所有权，所以标准库把它的拷贝构造函数标记为 `= delete`，禁止任何人复制它。这个"禁止复制"的性格会顺带传递到这个结构体上——本例的 `int_array` 也就跟着不可复制了。复制的规则本身是下一章的主题。

### 6.1 那还需要自己写析构函数吗

需要，但判断标准很清楚：

- 类型里**持有需要手工交还的资源**（`new` 出来的内存、打开的文件、系统句柄等裸资源），且**没有把这些资源交给现成的 RAII 成员保管**→ 必须写析构函数。
- 类型里的成员都是"自己会清理自己"的（`int`、`std::array`、`std::vector`、`unique_ptr`、`shared_ptr` 等）→ 不需要写析构函数。写了也不会错，但它做不了任何有价值的事。

用"要不要写析构函数"就能反过来检查类的设计：**如果你的类需要析构函数，说明它在手工管理某个资源，那就要再多问一句——能不能把这个资源交给一个现成的 RAII 类型去管？** 能的话，代码会立刻变短，而且更不容易出错。

这里还要补一个必须提醒的边界。像 `manual_cleanup` 里那种"用裸指针管理内存、自己写析构函数"的类型，只要对象被复制，默认的复制行为会**把指针原样抄一份**（这叫浅拷贝），于是两个对象指向同一块内存，析构时同一块内存被释放两次——**双释放**，属于未定义行为，程序可能崩溃，也可能把别的数据写坏。这是下一章要正面解决的问题。

### 7.1 实验一：手写析构函数

`manual_cleanup\manual_cleanup.cpp`

```text
E:\msys64\ucrt64\bin\g++.exe -std=c++20 -Wall -g manual_cleanup.cpp -o manual_cleanup.exe
./manual_cleanup.exe
```

**预期现象**（四行，逐字符一致）：

```text

=== Demo B: leave main ===

```

**验收标准**：`-Wall` 无警告；`dtor: free the ints` 出现在最后一行，也就是在 `=== Demo B: leave main ===` **之后**。能说出它为什么在这一行之后（`main` 返回，局部对象 `a` 超出作用域被销毁，编译器自动调用 `~int_array()`）。

**改值实验**：把 `main` 里的 `int_array a(10);` 改成 `int_array a(5);`，先不运行，判断输出会变成哪一行不同。预期只有构造函数那行变为 `ctor: allocate 5 ints`，第三行 `a.array[0] = 10` 和最后一行 `dtor: free the ints` 都不变——**参数只影响申请多少个元素，不影响元素的取值，也不影响析构行为**。改完重新编译运行核对。

### 7.2 实验二：销毁时机与顺序

`scope_lifetime\scope_lifetime.cpp`

```text
E:\msys64\ucrt64\bin\g++.exe -std=c++20 -Wall -g scope_lifetime.cpp -o scope_lifetime.exe
./scope_lifetime.exe
```

**预期现象**：

```text
=== Demo A: an object inside a block ===
construct inner
still inside the block
destruct inner
after the block
=== Demo B: three objects in one scope ===
construct first
construct second
construct third
destruct third
destruct second
leaving the block, first is still alive
=== Demo C: a dynamically allocated object ===

```

**验收标准**：`-Wall` 无警告；能逐段解释四处 `destruct` 各自是被什么触发的（A 是花括号结束、B 是内层花括号结束、C 是 `delete`、D 是 `main` 返回）；能说出 `third` 为什么排在 `second` 前面销毁。

**改值实验**：把 Demo C 里的 `delete heap;` 注释掉再编译运行，预期输出**只少一行** `destruct heap`，其余各行完全不变；而且程序不会报任何错。这一行消失就是内存泄漏在输出上的样子：**对象的析构函数从未执行**。编译时还会多出一句 `warning: unused variable 'heap' [-Wunused-variable]`，原因是注释掉 `delete heap;` 之后 `heap` 就再没有任何人使用——它恰好从侧面说明这块内存已经被彻底丢开了。看完把 `delete heap;` 还原。

`unique_ptr_no_dtor\unique_ptr_no_dtor.cpp`

```

**验收标准**：`-Wall` 无警告；能说出这个版本里"释放内存"发生在哪一句代码上（答案是没有任何一句：它发生在离开内层花括号时，`unique_ptr` 成员的析构函数里）。

**改值实验**：把 `main` 里那对内层花括号 `{ ... }` 删掉，让 `int_array a(10);` 直接留在 `main` 作用域中，并把 `=== Demo B ===` 那段输出也删掉。预期输出只剩三行：

```

内存仍然会被释放，只是时间推迟到 `main` 返回。这验证了"释放时机由作用域决定，不需要我们写代码"。

## 8 常见错误与排查

| 报错或现象 | 原因 | 处理 |
| --- | --- | --- |
| `error: destructors may not have parameters` | 给析构函数写了参数，如 `~int_array(int size)` | 删掉参数列表里的内容，写成 `~int_array()` |
| `error: return type specification for destructor invalid` | 给析构函数写了返回类型，如 `void ~int_array()` | 返回类型位置留空，连 `void` 也不写 |
| `error: expected unqualified-id before '~' token` 或 `error: '~x' is not a member of ...` | `~` 后面的名字写错，不是当前类/结构体的名字 | 名字必须与类名完全一致，注意大小写 |
| `error: use of deleted function 'int_array::int_array(const int_array&)'` | 结构体里有 `unique_ptr` 成员（它禁止复制），却写了复制对象的代码 | 不要复制这类对象；规则与替代写法见第 26 章 |
| `error: no matching function for call to 'int_array::int_array()'` | 定义了一个需要 `size` 的构造函数，创建对象时却没给参数 | 创建时补上参数：`int_array a(10);` |
| 程序正常运行，内存占用却持续上涨 | 构造函数里有 `new`，但没有配对的 `delete`/`delete[]`（也没有 RAII 成员） | 在析构函数里补上释放语句，或改用 `unique_ptr` 成员；这类问题**没有任何编译期提示** |
| 程序在退出时异常终止（实测：两次 `dtor` 都打印后进程以非零码结束） | 管理裸指针的类型被复制，默认复制只抄了指针，两个对象析构时释放同一块内存（双释放，未定义行为） | 本章例程范围内不要复制这类对象；正确的复制行为见第 26 章 |
| 用 `delete array;` 释放 `new int[size]` 申请的内存 | `delete` 与 `new[]` 不配对 | 改成 `delete[] array;`；注意编译器通常**不会**给警告，问题在运行时才可能暴露 |

## 9 本章验收

1. 三个例程都编译通过，`-Wall` 无警告，输出与 7.1、7.2、7.3 节的预期现象逐字符一致。
2. 能默写一个 `~int_array()` 的声明，并说出"无参数、无返回类型、名字是 `~` 加类名"这三条限制分别对应什么报错。
3. 能说出对象被销毁的三个时刻，并解释同一作用域内多个对象为什么按创建的逆序销毁。
4. 能用一句话说清 RAII：对象创建时获取资源、销毁时释放资源；并能指出 `std::vector`、`std::unique_ptr` 都是 RAII 类型的例子。
5. 完成过 7.2 的改动实验，能解释"注释掉 `delete heap;` 后少的那一行输出"为什么就是内存泄漏。
