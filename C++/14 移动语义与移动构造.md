## 1 复制并不总是可行的选项

第 12 章教会了我们的类型如何被复制，也顺带留下了一个反面案例：`unique_ptr` 不能复制。这类类型的存在不是标准库故意为难人，而是因为**复制在某些情况下根本不能成立**。

`std::unique_ptr` 的语义是"独占所有权"：一块动态分配的内存，同一时刻只能有一个所有者负责释放它（第 12 章讲的双释放就是有两个所有者的后果）。如果允许复制，世界上立刻就有两个 `unique_ptr` 认为自己独占同一块内存，这个类型最基本的保证就没了。所以标准库把它的拷贝构造函数标成了 `= delete`。

除了这种"功能上不允许复制"的情况，还有一类是"复制得起但不划算"。一个装着几百万个元素的 `vector`，复制它要把每一个元素都拷一遍，时间与内存都翻倍；而很多时候复制出来的那份只是被拿去用一次就丢掉。**这一步拷贝是可以省掉的。**

省掉它的办法就是本章的主题——**移动**（move）：

> **复制**是把源对象里的内容抄一份给新对象，源对象保持原样；
> **移动**是把源对象持有的底层资源**转移**给新对象，源对象不再持有它。

以 `unique_ptr` 为例，移动一个管理着 10 个 `int` 的 `unique_ptr` 并不会拷贝那 10 个 `int`，它只是把"这块内存归谁管"交接过去——**无论那块内存有多大，移动的成本都一样，都是交接一个指针**。这就是"窃取"这个词的来源：新对象把参数手里的资源拿走，参数手里留下的只有一副空壳。

## 2 不能复制，那就移动

例程 `E:\CPP_Code\CppFromScratch\ch28_move_semantics\unique_ptr_move\unique_ptr_move.cpp` 从"复制失败"开始：

```cpp
std::unique_ptr<int[]> p1 = std::make_unique<int[]>(10);
// std::unique_ptr<int[]> p2 = p1;   // 编译错误：拷贝构造被删除
```

取消注释后得到的是第 12 章见过的那类报错：

```text
error: use of deleted function 'std::unique_ptr<_Tp [], _Dp>::unique_ptr(const std::unique_ptr<_Tp [], _Dp>&) [with _Tp = int; _Dp = std::default_delete<int []>]'
```

改成移动就可以：

```cpp
std::unique_ptr<int[]> p2 = std::move(p1);
```

运行结果说明了全部：

```text
=== Demo A: an lvalue unique_ptr ===
p1.get() == nullptr: false
=== Demo B: after std::move ===
p1.get() == nullptr: true
p2.get() == nullptr: false
p2 owns the same buffer: true
=== Demo C: p2 is usable, p1 must not be read ===
p2[0] = 10
```

三行 `true`/`false` 值得逐条读：

- 移动**之前**，`p1.get()` 不是空指针——它手里有资源；
- 移动**之后**，`p1.get()` 变成了空指针，`p2.get()` 不是空的；
- 最能说明问题的是第三句：`p2` 管的正是移动前 `p1` 管的那块内存（例程里事先用 `raw` 记下了地址来比较）。**没有新申请内存，也没有拷贝数据，只是这块内存换了个主人。**

`unique_ptr` 为数组类型提供了下标运算符，所以 `p2[0] = 10;` 照旧能用，用法和移动前完全一样。

### 2.1 移动构造函数长什么样

移动这件事也是由构造函数完成的，叫**移动构造函数**（move constructor）。它的形状和拷贝构造函数几乎一样，只有一处不同：

```cpp
point(const point& p);      // 拷贝构造函数：参数是 const 左值引用
point(point&& p);           // 移动构造函数：参数是右值引用（两个 &）
```

**参数类型从 `const point&` 变成 `point&&`**，这就是 `&&`（右值引用）第一次出现的地方。写法上的两个差别都有原因：

- **不能加 `const`**。移动的目的正是"把 `p` 手里的资源搬走"，这就必须修改 `p`（把它清空）。如果参数是 `const point&&`，函数体内就没法动它，移动也就无从谈起。
- **不要写成 `point&`**。`point(point&)` 是一个合法的重载，而且对非 `const` 左值它比 `const point&` 更匹配：于是 `point p2 = p1;` 会走这个函数，把 `p1` 真的搬空——本该复制的地方发生了移动，很容易造成源对象被意外清空。

至于标准的移动构造函数内部该怎么写，是本章第 9 节的内容；这里先把"如何让编译器选择移动"讲清楚。

## 3 左值与右值：编译器靠什么区分

同一个 `unique_ptr`，`p1 = p2` 不允许、`p1 = std::move(p2)` 允许，差别在于**传进去的东西是左值还是右值**。

C++ 里描述"值"的类别有好几个（glvalue、prvalue、xvalue 等），本章只讲其中最常用的两个就够了：

| | 左值（lvalue） | 右值（rvalue） |
| --- | --- | --- |
| 典型样子 | 变量、`p1`、`x` | 立即数 `42`、函数返回的临时对象 |
| 有没有名字 | 有 | 通常没有 |
| 能不能取地址 | 能 | 不能 |
| 能不能重复使用 | 能，后面的语句还可以用 | 用完就没了 |
| 名字的由来 | 历史上常出现在赋值号左边 | 常出现在赋值号右边 |
| 与之匹配的引用 | `T&`（左值引用） | `T&&`（右值引用） |

判断一个表达式是左值还是右值，最实用的标准是：**它有没有名字、能不能在后面继续用。** `p1` 有名字，所以是左值；`std::make_unique<int[]>(10)` 的返回值是一个没有名字的临时对象，所以是右值。

这条区分之所以关键，是因为**默认行为完全不同**：

- 传**左值**时，编译器认为"这个名字后面还会被用到"，所以选择**复制**（调用拷贝构造函数）；
- 传**右值**时，编译器知道"这个临时对象用完就没了，没人会再需要它的旧值"，所以选择**移动**（调用移动构造函数）。

例程 `E:\CPP_Code\CppFromScratch\ch28_move_semantics\lvalue_rvalue\lvalue_rvalue.cpp` 用最基本的 `int` 演示了引用与值类别的绑定关系：

```cpp
int x = 10;
int& ref = x;         // 左值引用绑定左值，正确

int&& rref = 42;      // 右值引用绑定右值（临时量），正确
```

反过来写都是错的：

```text
error: cannot bind non-const lvalue reference of type 'int&' to an rvalue of type 'int'      // int& ref = 42;
error: cannot bind rvalue reference of type 'int&&' to lvalue of type 'int'                 // int&& rref = x;
```

第一行是第 08 章就有的规则（不能用一个"可能要修改"的引用去绑定一个准备丢掉的临时值）；第二行是本章的新规则：**右值引用 `T&&` 只能绑定右值。** 正因为如此，`unique_ptr` 的移动构造函数参数是 `unique_ptr&&`，它只接受右值——而 `p1` 是左值，所以直接写 `p2 = p1` 时编译器宁可用（已被删除的）拷贝构造函数，也不会去用移动构造函数。

## 4 `std::move`：只改变值类别，不搬任何数据

问题来了：如果手里只有左值（`p1` 是个变量，有名字），怎么才能让编译器去调用移动构造函数？

答案是用 `std::move`。它的说明可以概括为：**指示某个对象可以被移动，以便高效地转移它的资源。** 用法：

```cpp
std::unique_ptr<int[]> p2 = std::move(p1);
```

它来自 `<utility>` 头文件（`std::move` 就定义在那里）。要理解它，最关键的一点是——

> **`std::move` 在运行时什么都没做。** 它不申请内存、不搬数据、不改变被"移动"的对象；它做的唯一一件事是**把值的类别从左值变成右值**，也就是给编译器一个许可："这个东西可以被移动。"

它也不是强制命令。`std::move(p1)` 只是说"允许搬走 `p1`"，至于真的搬不搬、怎么搬，取决于类型有没有实现移动构造/移动赋值——`unique_ptr` 实现了，所以搬得干脆利落；如果某个类型没有移动构造函数，编译器就会退回去调用拷贝构造函数，**`std::move` 并不能让一个不会移动的类型移动起来**。

例程二里有一个很直观的验证：

```cpp
int x = 10;
int&& moved = std::move(x);     // 把 x 的类别变过来，绑定到右值引用
moved = 30;                     // 改 moved 就是改 x
```

运行输出里 `x` 和 `moved` 都等于 `30`，而这两行打印的其实是同一个对象。更直接的证据是本章实验二的改值实验：在 `std::move(x)` 之后、`moved = 30;` 之前打印 `x`，得到的仍然是 `20`——**`std::move` 只是类型系统里的一次转换，没有任何运行时代价。**

顺便要记住一个反直觉的点：**有名字的右值引用本身是左值。** 上面 `moved` 的类型是 `int&&`，但 `moved` 是个有名字的变量，所以它是一个左值：如果你想把它再移动给别人，还得再写一次 `std::move(moved)`。这正是"具名对象必须显式 `std::move`"这条规则的一部分——**只要有名字，编译器就会保守地认为它后面还会被用到。**

## 5 移动之后，源对象是什么状态

这是移动语义里最容易被忽略、也最容易写出 bug 的部分。标准的规定是：

> 被移动的对象处于**有效但未指定**的状态（valid but unspecified）：它仍然是一个完好、可以安全销毁、可以重新赋值的对象，但它之前保存的**值不再有意义**，不该再去读。

具体分成两类来看：

- **有明确保证的类型：`unique_ptr`。** 标准规定它被移动之后一定变成空指针。例程一里 `p1.get() == nullptr` 返回 `true` 是可以依赖的：只要发现它是空的，就知道资源已经交出去了。这类类型让"移动后检查"成为合法的写法。
- **没有明确保证的类型：`std::string`、`std::vector` 等大多数标准容器。** 它们被移动后的状态由实现决定：常见的情况是被移走的那一个变成空容器（因为底层缓冲区已经不属于它了），但**标准没有承诺这一点**，所以不要依赖它，也不要写出"移动后反正它是空的，我就直接当空容器用"这类代码。可以做的只有覆盖（给它重新赋值）或销毁这类不依赖它原值的操作，读旧值是不行的。

把它们合起来就是一条安全的使用规则：**标准只保证移动后的源对象"有效但未指定"，所以只应做覆盖、销毁这类不依赖它原值的操作，不要读它的旧值。** 例程一里 `p2[0] = 10;` 是合法的，而任何读 `p1` 旧值的写法都不合法。

## 6 什么时候用移动：把资源交出去

移动最典型的舞台是**把资源从一个地方交给另一个地方**。例程 `E:\CPP_Code\CppFromScratch\ch28_move_semantics\move_into_vector\move_into_vector.cpp` 里，一个函数负责生产资源、一个 `vector` 负责收集：

```cpp
std::unique_ptr<int> make_value(int value)
{
    return std::make_unique<int>(value);
}

int main()
{
    std::vector<std::unique_ptr<int>> values;

    std::unique_ptr<int> ptr = make_value(10);
    values.push_back(std::move(ptr));

    values.push_back(make_value(20));
    values.push_back(make_value(30));
    ...
}
```

两处写法不同，正好对应前面两句规则：

- **`std::move(ptr)`**：`ptr` 是有名字的变量（左值），编译器默认会把它当成"以后还要用"，所以要我们明确写一句"它可以搬走"。搬完之后 `ptr` 变成空指针，例程里打印 `ptr.get() == nullptr: true` 就是在确认这件事。
- **`make_value(20)` 不写 `std::move`**：函数返回的是一个没有名字的临时对象（右值），本来就可以被移动，`push_back` 会直接把资源搬进 `vector`。**这里写 `std::move` 是多余的**，但也不会出错。

对应的实用规则：

> **具名对象要搬走时必须显式 `std::move`；函数返回的临时对象不必写。**

例程最后的遍历打印 `*value = 10/20/30`、`total = 60`，说明三个资源都在 `vector` 里完好可用。整个过程**一次也没有复制 `int` 数据**——放进容器的只是三个指针。这正是"把函数产出的结果收集进容器"这个常见需求的正确成本：如果每个元素都要复制一遍，资源一多就很可观。

反过来说，写 `values.push_back(ptr);`（不写 `std::move`）会编译失败，报错链的末尾是：

```text
error: no matching function for call to 'construct_at(std::unique_ptr<int>*&, const std::unique_ptr<int>&)'
```

报错信息里出现 `const std::unique_ptr<int>&`，就是在说"这里需要的是一个只能读、需要复制一份的引用，而 `unique_ptr` 不能复制"。**看到 `push_back` 相关的报错里带着 `const ...&`，第一反应就应该是"漏了 `std::move`"。**

## 7 从"知道要移动"到"自己写移动"

本章第 1—6 节讲了移动语义的三件事：怎么区分左值和右值、`std::move` 只是把值类别改成右值、移动之后的源对象处于"有效但未指定"的状态，也演示了 `unique_ptr` 被移动时会发生什么——但那是标准库类型，它的移动构造函数是别人写好的。接下来补上缺的那一块：**我们自己的类型，移动构造函数得自己写。**

编写这个函数最常出现的场景就是容器，因为容器天生要做一件事：把外面造好的对象收进来。第 1 节已经给出了两个理由：**有些类型根本不能复制**（比如 `unique_ptr`，只能被移动），**有些类型复制得起但不划算**（比如装着几百万个元素的容器，复制一遍的时间和内存都翻倍，而复制出来的那份往往只用一次就丢掉）。

要真正把这件事做对，光有本章第 4 节的 `std::move` 是不够的——`std::move` 只是"允许搬走"的一句话，**真正动手搬的是移动构造函数**。下面先看清"没有它的时候到底发生了什么"。

## 8 没有移动构造函数时会怎样

例程 `E:\CPP_Code\CppFromScratch\ch29_move_constructor\move_constructor_basic\move_constructor_basic.cpp` 里的类型故意让每条构造路径都打印一行，这样每次发生的是复制还是移动，从输出里就能直接看出来（节选，注释略）：

```cpp
struct S
{
    int value = 0;

    explicit S(int new_value = 0) : value(new_value)
    {
        std::cout << "Constructor! value = " << value << std::endl;
    }

    S(const S& other) : value(other.value)
    {
        std::cout << "Copy Constructor! value = " << value << std::endl;
    }

    S(S&& other) noexcept : value(0)
    {
        std::swap(value, other.value);
        std::cout << "Move Constructor! value = " << value << std::endl;
    }
};
```

`main` 里对三种写法各调用一次 `push_back`：

```cpp
std::vector<S> v1;
S s(10);
v1.push_back(s);              // 有名字的左值
```

`vector::push_back` 有两个重载，它们的分工是：

| 重载 | 参数类型 | 做的事 |
| --- | --- | --- |
| `push_back(const T& value)` | `const` 左值引用 | 把 `value` **复制**成新元素（第 07 章用的就是这个） |
| `push_back(T&& value)` | 右值引用 | 把 `value` 的资源**搬**进新元素 |

`s` 是有名字的变量，是左值，只能绑定到第一个重载，所以结果是复制。输出两行也正好对应两块内存：

```text
Constructor! value = 10
Copy Constructor! value = 10
```

第一行是 `main` 里那个 `s` 被构造出来，第二行是在 `vector` 的内存里构造出一个副本。

### 8.1 只加 `std::move` 并不能让它移动

按本章第 6 节的规则，给 `s` 套上 `std::move` 就应该走移动了。可是把例程改成下面这样，结果仍然是复制：

```cpp
std::vector<S> v2;
S t(20);
v2.push_back(std::move(t));   // 期望移动，实际仍然复制
```

原因不在 `std::move`，而在 `S` **根本没有移动构造函数**：`S` 里只写了普通构造函数和拷贝构造函数，没有 `S(S&&)`。`std::move(t)` 把一个右值交给了 `push_back`，`push_back(T&&)` 也确实被选中了，但它内部需要"用一个右值构造 `S`"，而此时**唯一能做到这件事的就是拷贝构造函数**（`const S&` 可以绑定右值），于是还是复制。

这里有一条必须记住的规则：

> **移动构造函数不会被隐式声明的条件：** 只要**拷贝构造函数、拷贝赋值运算符、移动赋值运算符、析构函数**这四者中有任意一个被用户声明过，编译器就**不**再隐式声明移动构造函数。

例程里的 `S` 用户声明了拷贝构造函数，正好落在第一条上。所以它从一开始就没有移动构造函数，`std::move` 只是让值类别变成右值，而**没有移动构造函数可用的右值只能退回复制**——这也再次印证了本章第 4 节那句话：`std::move` 不是强制命令。

## 9 移动构造函数长什么样

移动构造函数的形状和拷贝构造函数几乎一样，只有两处不同：

```cpp
S(const S& other);            // 拷贝构造函数：const 左值引用，只能读
S(S&& other) noexcept;        // 移动构造函数：右值引用，可以改
```

两处差别都有原因：

- **参数是 `S&&`（右值引用）。** 只有写成右值引用，这个函数才会在"实参是右值"时被优先选中。写成 `S&` 也是合法的重载，但它在实参是非 `const` 左值时比 `const S&` 更匹配，于是 `S b = a;` 会把 `a` 真的搬空——复制的位置上发生了移动，非常容易被误用。
- **不能用 `const`。** 移动的本质就是把参数手里的东西搬到自己身上，这必然要修改参数（把它清空）。如果参数是 `const S&&`，函数体里就动不了它，移动也就无从谈起。这也是"移动之后源对象的值不再有意义"这条规则的另一面。

至于函数体里"搬"这个动作怎么实现，取决于这个类型持有的是什么。

**成员本身是"值"**（`int`、`double` 之类）时，搬与抄的代价一样，直接用 `std::swap` 把值换过来即可，例程 `move_constructor_basic` 用的就是这个写法：

```cpp
S(S&& other) noexcept : value(0)     // 先把新对象初始化为"空"值 0
{
    std::swap(value, other.value);   // 再把值换到自己身上，参数拿到的就是 0
}
```

这样写完之后，新对象拿到了对方的值，对方留下一个明确的"空"值，而不是一个不可预料的值。

**成员是资源**（裸指针、`unique_ptr`、容器、字符串等）时，应该把成员**移动构造**过来，而不是复制。这时候要在成员初始化列表里对成员用 `std::move`：

```cpp
int_buffer(int_buffer&& other) noexcept
    : data(std::move(other.data)), length(other.length)   // 接管对方的指针
{
    other.length = 0;                                     // 源对象进入"空但完好"的状态
}
```

**这里有个容易被忽略的坑：成员初始化列表里忘写 `std::move`，成员就会被复制。** 因为形参 `other` 虽然是个右值引用，但 `other` 这个**名字**本身是左值（本章第 4 节讲过"有名字的右值引用是左值"），不加 `std::move`，编译器就按"用一个左值初始化成员"处理，于是老老实实复制一份。结果就是：移动构造函数写是写了，资源却照抄了一遍，一点都没省。

最后是 `noexcept`。它出现在函数声明的末尾，含义是"这个函数承诺不抛异常"。移动构造函数该加它的理由是**容器要知道这件事**：`vector` 扩容时要把已有元素搬到新内存，如果搬的过程中抛了异常，旧内存里的元素已经被改动过，容器无法保证"要么全成、要么原样"（强异常安全）。所以库的规则是：**只有当元素的移动构造函数是 `noexcept` 时，`vector` 才敢用移动来搬元素；否则它退回去用复制**，因为复制只读源对象，出错时源对象还是完好的。这条判断在标准库里由 `std::move_if_noexcept` 完成，而它只在类型**仍然可以复制**时才退回复制；如果类型连拷贝构造函数都没有（比如 `unique_ptr`），退回复制无从谈起，那就只能移动。加了 `noexcept` 而函数体里又真的抛异常，程序会直接 `std::terminate`，所以这个承诺必须是真的——对"交接指针"这类操作来说，它确实是。

> 除了移动构造函数，还有一个配套的**移动赋值运算符** `S& operator=(S&& other)`，它管的是"已存在的对象接手别人的资源"。规则与移动构造函数完全平行（第 13 章讲过运算符重载，写法可以直接类推），本章只讲构造函数，两者通常一起实现。

这里还有一条边界要说明：本节的 `S` 以及本章第 12 节的 `int_buffer`，都只写了构造函数（`S` 的成员是 `int`，连析构函数都不需要），没有写析构函数、拷贝赋值运算符和移动赋值运算符。它们是"讲清移动构造"的片段，不是完整的资源持有类。一个**完整**的资源持有类应当按 Rule of Five 补齐这五个成员（第 12 章），否则赋值表达式 `a = b;`、`a = std::move(b);` 会落到编译器隐式生成的版本上，而隐式版本对裸指针之类的资源是错的。

## 10 实现之后再运行：三条添加路径

补上移动构造函数之后，同样三种写法就分化成了三条路径：

| 写法 | 实参的值类别 | 选中的 `push_back` 重载 | 实际发生 |
| --- | --- | --- | --- |
| `v1.push_back(s)` | 左值 | `push_back(const S&)` | 拷贝构造函数 |
| `v2.push_back(std::move(t))` | 右值（`std::move` 转换而来） | `push_back(S&&)` | 移动构造函数 |
| `v3.push_back(S(30))` | 右值（无名临时对象） | `push_back(S&&)` | 移动构造函数 |

例程 `move_constructor_basic` 的完整输出把三条路径依次摆在了一起：

```text
=== Demo A: push_back with a named lvalue copies ===
Constructor! value = 10
Copy Constructor! value = 10
=== Demo B: std::move turns the same lvalue into an rvalue ===
Constructor! value = 20
Move Constructor! value = 20
t.value after the move: 0
=== Demo C: a temporary object is moved without std::move ===
Constructor! value = 30
Move Constructor! value = 30
=== Demo D: the three vectors really own their elements ===
v1[0].value = 10
v2[0].value = 20
v3[0].value = 30
```

逐段读：

- **Demo A** 是"不得不复制"的情形：`s` 后面可能还要用，编译器不会擅自把它搬空。
- **Demo B** 与 Demo A 的唯一差别就是参数外面多了一层 `std::move`。输出从 `Copy Constructor!` 变成了 `Move Constructor!`，说明移动确实是"我们明确允许之后"才发生的。`t.value after the move: 0` 这一行则说明移动是有代价的：`t` 被清成了空值。这是我们自己写的 `std::swap` 决定的，**源对象留下的具体值由实现者自己选**（对标准库容器就不要假设它一定是空的）。
- **Demo C** 说明临时对象不用写 `std::move`：它没有名字，用完就没了，编译器直接按右值处理。本章第 6 节的实用规则在这里同样成立——**具名对象要搬走必须显式 `std::move`，函数返回的临时对象不必写**。
- **Demo D** 是收尾检查：三种写法的最终结果完全一样，`vector` 里各装着一个值正确的元素。**移动与复制的区别只在于"怎么构造出来的"，不在于"构造出来的东西有什么不同"。**

## 11 什么类型是可移动的，什么类型只能移动

前面那条"用户声明了拷贝构造就没有隐式移动构造"的规则，展开来可以归成三种常见情形（用户声明析构函数会触发同一条规则，效果和声明拷贝构造函数一样，留到实验五验证）。例程 `E:\CPP_Code\CppFromScratch\ch29_move_constructor\implicit_move_rules\implicit_move_rules.cpp` 用一个"探针"成员把它们逐个验证了一遍：探针在被复制和被移动时各打印一行，并把自己的来历记在 `origin` 成员里。

```cpp
struct plain                   // 什么特殊成员函数都不声明
{
    tracked member;
};

struct with_copy               // 用户声明了拷贝构造函数
{
    tracked member;
    with_copy() = default;
    with_copy(const with_copy& other) : member(other.member) { }
};

struct move_only               // 用户声明了移动构造函数
{
    tracked member;
    move_only() = default;
    move_only(move_only&& other) noexcept : member(std::move(other.member)) { }
};
```

运行结果：

```text
=== Demo A: no user-declared special member functions ===
plain: is_copy_constructible = true, is_nothrow_move_constructible = true
constructing p2 from std::move(p1):
    tracked: default constructor
    tracked: move constructor
    p2.member.origin = move
=== Demo B: a user-declared copy constructor suppresses the move constructor ===
with_copy: is_copy_constructible = true, is_nothrow_move_constructible = false
constructing w2 from std::move(w1):
    tracked: default constructor
    tracked: copy constructor
    w2.member.origin = copy
=== Demo C: a user-declared move constructor deletes the copy constructor ===
move_only: is_copy_constructible = false, is_nothrow_move_constructible = true
constructing m2 from std::move(m1):
    tracked: default constructor
    tracked: move constructor
    m2.member.origin = move
```

三种类型，三段输出，可以得到三条结论：

1. **`plain`：什么都不声明，编译器全都给你。** 隐式声明的移动构造函数会逐个成员地移动，并且会继承成员的 `noexcept` 性质（探针的移动构造是 `noexcept`，所以 `plain` 也是），因此 `is_nothrow_move_constructible` 为 `true`。这也是"默认情况下类型就是可移动的"的原因。
2. **`with_copy`：声明了拷贝构造，移动构造就不生成。** 结果是 `std::move` 传进来的右值只能退回复制（输出里是 `tracked: copy constructor`），`is_nothrow_move_constructible` 变成了 `false`——因为退回用的那个拷贝构造函数并不保证不抛异常。同理，**用户声明析构函数**也会产生同样的后果（这是同一条规则里的第四项）：只要类型需要自定义清理动作，编译器就不再擅自生成移动构造函数。
3. **`move_only`：声明了移动构造，拷贝构造被定义为删除。** 于是 `is_copy_constructible` 变成 `false`，`move_only m3 = m1;` 直接编译失败，这个类型只能移动。独占所有权的类型正是这个形状。

这两个 traits（`std::is_copy_constructible_v`、`std::is_nothrow_move_constructible_v`）不是摆设：标准库内部就是用后者判断"能不能放心搬元素"的。看清这一点，也就看清了本章第 9 节 `noexcept` 为什么重要。

顺带说明一个易错点：`std::is_move_constructible_v<with_copy>` 是 `true`——**这不代表它真的能"移动"**，只代表"可以用一个右值把它构造出来"，而那一步实际走的是复制。判断"移动是否高效"要看 `is_nothrow_move_constructible`，判断"到底调用了哪个函数"只能看运行结果。

## 12 让移动真正搬走资源

上面例程用的成员是 `int`，搬和抄的代价一样，看不出差别。差别要在**持有堆内存**的类型上才看得到。例程 `E:\CPP_Code\CppFromScratch\ch29_move_constructor\move_constructor_resource\move_constructor_resource.cpp` 里的 `int_buffer` 持有一块动态分配的 `int` 数组，两条路都显式写了出来：

```cpp
// 拷贝：必须另申请一块内存，再把每个元素抄一遍
int_buffer(const int_buffer& other)
    : data(std::make_unique<int[]>(other.length)), length(other.length)
{
    for (std::size_t i = 0; i < length; ++i)
    {
        data[i] = other.data[i];
    }
}

// 移动：不申请内存，只把指针接过来
int_buffer(int_buffer&& other) noexcept
    : data(std::move(other.data)), length(other.length)
{
    other.length = 0;
}
```

运行结果：

```text
=== Demo A: a buffer with four elements ===
a.size() = 4
a[0] = 7, a[3] = 7
=== Demo B: copying allocates a second block ===
b and a share the same block: false
b.size() = 4, b[0] = 7
=== Demo C: moving hands the block over ===
c keeps a's old block: true
a is empty now: true
a.size() = 0
=== Demo D: the moved-to buffer still works ===
c.size() = 4, c[0] = 7, c[3] = 7
=== Demo E: the buffer can be moved into a vector ===
buffers.size() = 1
buffers[0].size() = 4, buffers[0][0] = 7
```

Demo B 和 Demo C 是这一章的中心对照，两句话就能说清：

- **复制得到的是一块新内存**（`b and a share the same block: false`）。元素内容一样，但成本是"申请 + 逐个拷贝"，元素越多越慢。
- **移动得到的是原来那块内存**（`c keeps a's old block: true`）。整个过程只交接了一个指针，**成本与元素个数无关**——这正是"移动比复制便宜"的确切含义，而不是"移动一定更快一点点"。
- **移动之后源对象进入可安全销毁的空状态**（`a.size() = 0`）：`unique_ptr` 成员被移走后变成空指针，`length` 被我们显式清零。它仍然是一个完好的对象：可以销毁（`delete` 空指针是合法的）、可以重新赋值，但**它的旧内容已经不属于它了，不该再去读**（本章第 5 节那条"有效但未指定"的规则）。
- **Demo E** 回到本章的动机：把资源交给容器时，具名对象要写 `std::move`，这一步之后 `vector` 就真的持有了那份资源，而不是把它复制一份。

## 13 返回局部对象：RVO、NRVO 与 `return std::move`

最后一块拼图在**返回值**上。函数返回一个局部对象时，编译器本来就可以直接把那个对象构造在调用者拿到结果的位置上，一次拷贝或移动都不做——这个优化叫**返回值优化**（RVO，返回具名对象时叫 NRVO）。C++17 起，返回一个临时对象（prvalue）的拷贝消除是强制的；返回具名对象则由编译器决定做不做。

```cpp
tracker return_local()
{
    tracker local;
    return local;              // NRVO：不调用拷贝/移动构造函数
}
```

NRVO 不做的时候，`return local;` 也是安全的：具名的局部对象会被当成右值，调用移动构造函数——所以这里不需要、也不应该手写 `std::move`。而写成 `return std::move(local);` 会把"一个具名的局部对象"变成"一个表达式的结果"，NRVO 的前提被破坏，于是**一定**多发生一次移动构造：

```cpp
tracker return_move_local()
{
    tracker local;
    return std::move(local);   // 抑制 NRVO：多一次移动构造函数调用
}
```

用一个把三条构造路径都打印出来的类型就能看到差别：

```cpp
struct tracker
{
    tracker() { std::cout << "constructor" << std::endl; }
    tracker(const tracker&) { std::cout << "copy constructor" << std::endl; }
    tracker(tracker&&) noexcept { std::cout << "move constructor" << std::endl; }
};
```

把两个函数依次调用一遍，`-std=c++20 -Wall -g` 实测输出：

```text
=== return local ===
constructor
=== return std::move(local) ===
constructor
move constructor
```

`return local;` 那一段只有一次 `constructor`：对象直接构造在调用方的位置，没有任何拷贝或移动。`return std::move(local);` 那一段多出一行 `move constructor`，而且 GCC 会在这一行直接给出警告（`-Wall` 里就带着它）：

```text
warning: moving a local object in a return statement prevents copy elision [-Wpessimizing-move]
```

结论只有一句：**返回局部对象时直接写 `return local;`，不要画蛇添足写成 `return std::move(local);`**——后者除了多一次移动，还会顺手关掉编译器本来能做的优化。本章第 6 节"函数返回的临时对象不必写 `std::move`"说的也是同一件事。
