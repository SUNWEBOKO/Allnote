## 1 问题：初始化发生在"创建对象之后"

第 11 章我们这样创造一个坐标点：

```cpp
Point p;
p.x = 10;
p.y = 20;
```

第一句创建对象，后两句才把值填进去。能用，但有两处别扭。

**第一处是顺序上的**：对象在被创建的那一刻，它的成员还没有任何有效的值。虽然只有很短的一瞬间，但那段时间里这个对象是"半成品"——如果后面漏掉了某一句赋值，它会一直保持这个状态。第 11 章 `Sensor` 那个例子已经碰到过这个问题：数据成员是私有的、又没有初值，就必须小心地保证在读取之前先调用 `setValue`。

**第二处是写法上的**：创建对象和设置初值本来就是同一件事，却被拆成了三条语句。而"给一个点设置坐标"这种动作用一个成员函数就能表达清楚，不必让调用者逐条照做：

```cpp
Point p {10, 20};
```

要写成这个样子，需要让类型自己规定"对象被创建出来的时候该怎么初始化"。C++ 用两种机制来承担这件事：**默认成员初始化**（简单的一条）和**构造函数**（完整的一条）。下面先讲前者，再重点讲后者。

## 2 默认成员初始化：在声明处给初值

最简单的办法是在数据成员的声明处直接写初值（例程 `E:\CPP_Code\CppFromScratch\ch24_constructors\ctor_default_member_init\ctor_default_member_init.cpp`）：

```cpp
struct Point
{
    int x = 10;
    int y = 20;

    void print()
    {
        std::cout << "x = " << x << std::endl;
        std::cout << "y = " << y << std::endl;
    }
};
```

这叫作**默认成员初始化**。有了它之后：

```cpp
Point p;        // p.x = 10, p.y = 20
```

只要某个成员没有被别的方式指定初值，它就取声明处的这个值。这样"忘记设置"的后果从"成员值不确定"变成了"成员取默认值"，安全得多。

**这里要和第 11 章的一条结论对账。** 第 11 章说过，空花括号 `Point p {};` 会把成员全部置零。这句话在成员**没有**默认值的时候成立：此时空花括号的含义就是"取各自类型的零值"，和 `int count {};` 得到 0 是同一个规则。但当成员写上了默认值，`Point p {};` 得到的就不再是 0，而是声明处的值。例程的 Demo B 和 Demo D 把这两种情况并排放在一起：

| 写法 | `Point`（`int x = 10;`） | `RawPoint`（`int x;`） |
| --- | --- | --- |
| `T p;` | `x = 10` | 不确定的值 |
| `T p {};` | `x = 10` | `x = 0` |

换句话说，**先看成员有没有默认值，再判断空花括号会得到什么**。这不是两条互相矛盾的规则，而是同一条规则的两次应用：空花括号表示"每个成员都用'没被指定时该取的值'"，而这个值要么来自成员自己的默认值，要么是这个类型的零值。

**默认成员初始化不会妨碍聚合初始化。** `Point r {1, 2};` 照样合法，得到 `x = 1`、`y = 2`——花括号里给了值，就按给的值来，默认值只是"没给的时候"的兜底。所以三种创建方式可以共存：

```cpp
Point a;            // 10, 20
Point b {};         // 10, 20
Point c {1, 2};     // 1, 2
```

## 3 构造函数：把初始化写成一段代码

默认成员初始化只能给一个固定的初值。如果初值需要计算、需要根据参数决定、或者创建对象时还要做点别的（比如登记一个编号），就要用到**构造函数**。

构造函数是一个**特殊的成员函数**，用来初始化正在创建的对象。它的写法有三条硬性规定：

```cpp
struct Point
{
    int x;
    int y;

    Point()                                  // 1. 名字与类型相同；2. 没有返回类型
    {
        x = 10;
        y = 20;
        std::cout << "构造函数被调用" << std::endl;   // 3. 函数体里可以写别的语句
    }
};
```

（这是一段示意写法，本章例程里的构造函数改用下一节的成员初始化列表来给初值。）

1. **名字必须与类型名相同**（这里是 `Point`）。因此编译器看到 `Point(...)` 就知道这是构造函数。也正因为如此，构造函数**不能重命名**：改了名字，它就不再是构造函数，而是一个普通成员函数（而且它没有返回类型，通常还会引发一串报错）。
2. **没有返回类型，连 `void` 都不写**。这不是漏了，而是规定如此：构造函数的职责是"把对象造出来"，不是"交回一个值"。写成 `void Point()` 是错的，编译器会说 `return type specification for constructor invalid`。
3. **我们从来不直接调用它**。代码里不会出现 `Point();` 这样"调用"构造函数的写法；构造函数是在创建对象时**被编译器自动调用**的。写 `Point p;` 时编译器就会找到那个不需要参数的构造函数，用它来初始化 `p`。

构造函数体里的语句和普通函数一样，可以赋值、可以打印。例程 `ctor_init_list` 的 Demo A 里，构造函数先打印一句再让 `main` 打印成员，输出顺序明确显示出：**构造函数在对象创建的过程中就已经跑完了。**

**一个类型可以有多个构造函数**，区别在参数列表——这正是第 04 章讲过的重载。创建对象时给几个实参、什么类型，编译器就挑那个能匹配上的构造函数。

## 4 成员初始化列表：比函数体更早

构造函数体里赋值虽然直观，但有一个更正式的写法，叫**成员初始化列表**——在参数列表和函数体之间、用冒号引出的一段：

```cpp
Point() : x{10}, y{20}          // 初始化列表：成员名{初值}，用逗号分隔
{
    std::cout << "构造函数体开始执行" << std::endl;
}
```

带参数的构造函数同样可以用它：

```cpp
Point(int newX, int newY) : x{newX}, y{newY}
{
}
```

**关键在顺序**：初始化列表在构造函数体**之前**执行，也就是成员先按列表里的值初始化好，然后才进入大括号执行函数体。例程 `ctor_init_list` 的 Demo C 用一个构造函数把这件事做实了：

```cpp
Point(int newX, int newY) : id{1}, x{newX}, y{newY}
{
    std::cout << "函数体里读到的 x = " << x << std::endl;   // 读到 5，说明列表已经跑过
}
```

### 4.1 什么时候必须用初始化列表

有几种情况**只能在**初始化列表里给初值，在函数体里赋值是不行的：

**第一，`const` 成员。** `const` 变量一旦初始化就不能再改（第 02 章），而构造函数体里的 `x = 10;` 是**赋值**，不是初始化——对 `const` 成员来说这就是非法的：

```text
error: uninitialized const member in 'const int' [-fpermissive]
error: assignment of read-only member 'Point::id'
```

例程 `ctor_init_list` 里的 `const int id;` 就属于这一种，它必须在列表里写成 `id{0}`。

**第二，成员本身是自定义类型对象的时候。** 如果成员是另一个类（或 `std::string`、`std::vector` 这类标准库类型）的对象，写进初始化列表就是"用它自己的某个构造函数直接造出来"；写到函数体里则意味着"先默认构造一个，再赋值给它"，多绕了一步。讲到移动（第 14 章）时会看到，这一步绕路不只是效率问题，有些类型根本不允许赋值。这里先记住结论：**能写进列表的成员就写进列表。**

### 4.2 什么时候用函数体

函数体并没有被淘汰：**需要做比"给成员一个值"更复杂的事情时，就在函数体里做**。比如根据条件计算初值、需要循环、需要打印、需要更新某个计数器，这些都放在大括号里，初始化列表只负责把成员的值落定。

### 4.3 一个容易误判的细节

**初始化列表的执行顺序是成员的声明顺序，而不是你在列表里写的顺序。** 假如成员按 `id`、`x`、`y` 的顺序声明，那么无论你把列表写成 `: y{...}, x{...}, id{...}` 还是别的次序，实际都是先 `id`、再 `x`、最后 `y`。于是"用后面的成员去算前面成员的初值"这种写法是危险的：**看起来读到了值，实际上那个成员还没初始化。** 省事的做法是：写列表时按成员的声明顺序写，让读代码的人不用做额外的推理。

## 5 带参数的构造函数：创建时就把值定下来

无参构造函数只解决"有初值"，真正方便的是**带参数的构造函数**——它让"创建对象"和"指定初值"变成同一句话：

```cpp
Point(int newX, int newY) : x{newX}, y{newY}
{
}

Point p {5, 7};     // 创建 p 的同时把坐标定成 5 和 7
```

这和第 11 章的 setter 有点像：都在往数据成员里写值。两者的区别在于**时机**：

| | setter | 构造函数 |
| --- | --- | --- |
| 何时调用 | 对象已经存在，事后单独调用 | 对象创建的那一刻，自动调用 |
| 需要写几行 | 创建一行 + 设置一行（每个成员一次） | 一行 |
| 能不能漏 | 能：忘了调用，对象就停在旧状态 | 不能：不给出匹配的实参，编译就不过 |
| 有没有返回值 | 可以有（比如表示是否被接受） | 没有返回类型，也不能有 |

**构造函数把"忘记初始化"从一种运行时的隐患变成了一种编译错误**，这是它比 setter 更值得用的地方：只要类型规定"创建时必须给两个坐标"，任何忘记给值的调用点都会被编译器拦下来。

## 6 自己写了构造函数之后，编译器会收回一些东西

有一件事必须提前知道，否则它一定会让你意外一次：**只要我们在类型里声明了任何一个构造函数，编译器就不再隐式地生成默认构造函数**（那个不需要参数的版本）。

于是下面这段代码会编译失败：

```cpp
struct Point
{
    int x = 0;
    int y = 0;

    Point(int newX, int newY) : x{newX}, y{newY} {}
};

Point p1 {5, 7};    // 可以：匹配两参构造函数
Point p2;           // 编译错误
```

报错原文是：

```text
error: no matching function for call to 'Point::Point()'
```

后面还会列出所有候选构造函数，以及每个候选为什么不行（例如 `candidate expects 2 arguments, 0 provided`）。这句错误的意思是"没有能匹配空参数列表的构造函数"——而它之所以不存在，是因为**我们自己写了构造函数之后，编译器就把"生成默认构造函数"这件事交回给我们负责了。**

如果确实还需要无参构造，明确告诉编译器"照旧生成一份"即可：

```cpp
Point() = default;
```

`= default` 的含义是"按编译器本来会生成的样子生成这个函数"，不需要写函数体。例程 `ctor_default` 同时演示了三条路：两参构造函数负责带初值创建，`Point() = default;` 负责无参创建，而成员声明处的 `int x = 0;` 保证无参创建出来的对象也是有值的（`= default` 生成的是编译器默认行为，它自己不会给成员赋任何值，值来自成员的默认初始化）。

**还有一条连带变化**：一旦类型有了构造函数，它就不再是聚合类型，**聚合初始化那套"花括号按位置对应成员"的规则随之失效**。花括号此时改为"从中挑一个构造函数来调用"，所以 `Point p {5};` 会失败：

```text
error: no matching function for call to 'Point::Point(<brace-enclosed initializer list>)'
```

这不是"花括号不能用了"，而是花括号的含义变了：它仍然能创建对象，只是必须匹配某个构造函数的参数列表（`Point p {5, 7}` 就没问题）。

最后提醒一条和第 11 章的衔接：**构造函数也是成员，同样受访问限定符约束。** 如果构造函数写在 `private` 段里，类外面就不能创建这个类型的对象：

```text
error: 'Point::Point()' is private within this context
```

这是有意为之的用法——"只允许在某些情况下被创建"的类型就是这么写出来的，等后面讲工厂函数、单例时会用到这个手法。

## 7 对象消失以后，那块内存归谁

本章第 3 节的构造函数解决的是"对象出生时该做什么"。这一部分处理另一半：**对象消失时该做什么**。

大多数对象不需要特殊处理。`int`、`std::array<int, 3>` 这类对象的所有数据都直接装在自己身体里，对象一消失，它占的那点空间自然被收回，不需要谁去做额外的事。

但从第 09 章开始，我们手里多了一种对象：**通过 `new` 申请来的内存**。它可以理解成一张"钥匙"，对象自己只保存钥匙，也就是那个指针；真正装数据的空间在别的地方。这就带来一个新问题——**对象消失的时候，钥匙被丢掉了，可门后面的房间还锁着**。那块内存既没有被释放，也没有任何人再持有它的地址，程序再也无法访问它。这种现象叫**内存泄漏**（memory leak）。

这一部分要处理的典型情况是一个自定义的动态整数数组类型：数据成员是 `int* array`，构造函数里 `new int[size]` 申请空间，然后在程序里正常使用它。这个类型能用、能算，唯一的毛病是"用完不还"。程序跑完一次没什么感觉，但这类代码放进循环或长期运行的服务里，占用的内存会一直涨上去。

**析构函数就是为这件事存在的**：它是对象的"收尾指令"，在对象被销毁的那一刻自动执行，用来把对象曾经获取的资源交还回去。

## 8 析构函数的写法

### 8.1 名字与三条限制

析构函数的写法与构造函数是对称的：

| | 构造函数 | 析构函数 |
| --- | --- | --- |
| 名字 | 类名本身，如 `int_array` | `~` 加上类名，如 `~int_array` |
| 参数 | 可以有任意个 | **一个都不能有** |
| 返回类型 | 不写 | 不写（连 `void` 都不写） |
| 调用者 | 创建对象时由编译器调用 | 销毁对象时由编译器调用 |

例子：

```cpp
struct int_array
{
    int* array;

    int_array(int size)
    {
        array = new int[size] {};
    }

    ~int_array()
    {
        delete[] array;
    }
};
```

三点要记住：

- 名字是 `~` 加类名，`~` 读作"波浪线"。这个符号是析构函数唯一的记号，**没有第二种写法**。
- **不能带参数**。析构函数的执行时机由编译器决定，调用者无处传参，所以带参数的析构函数没有意义。写了会直接报错：`error: destructors may not have parameters`。
- **不能写返回类型**。连 `void` 都不写。写了 `void ~int_array() {...}` 会报 `error: return type specification for destructor invalid`。这和构造函数是同一套规则：这两个特殊成员函数的"返回类型位置"是留空的。

### 8.2 它不该被手动调用

析构函数与普通成员函数最大的区别在于**触发方式**。它不需要、也不该由我们按名字调起来：

```cpp
int_array a(10);
// a.~int_array();      // 语法上允许，但几乎总是错的，不要这样写
```

语言确实允许写出这种显式调用（构造函数连这个余地都没有），但它几乎总是错的原因和"重复释放"有关：析构函数的正当执行时机由编译器在三个时刻安排，你手动调一次，编译器到点还会再调一次，同一个资源就被释放了两遍。本章第 10 节把这三个时刻列清楚。

换一个角度说，析构函数是一个**特殊成员函数**：它在对象生命周期结束时被调用，用途是释放对象在生命周期中获取的资源。这句话里有两个词是关键——"生命周期结束"决定它什么时候跑，"释放资源"决定它该写什么。写析构函数时只要问自己一句：**这个对象活着的时候拿到了什么，需要在它死后交还？**

## 9 配对：`new` 配 `delete`，`new[]` 配 `delete[]`

回到例程 `E:\CPP_Code\CppFromScratch\ch25_destructors\manual_cleanup\manual_cleanup.cpp`。它的构造函数和析构函数正好把第 09 章的申请与释放配对起来：

```cpp
int_array(int size)
{
    std::cout << "ctor: allocate " << size << " ints" << std::endl;
    array = new int[size] {};
}

~int_array()
{
    std::cout << "dtor: free the ints" << std::endl;
    delete[] array;
}
```

有两个细节值得展开。

**第一，`new int[size] {}` 末尾的那对花括号。** 数组形式的 `new` 如果只写 `new int[size]`，元素是**默认初始化**的，也就是没有被赋任何值，读它们属于未定义行为。加上一对空的 `{}` 才变成**值初始化**，整块内存被置零。两种写法申请内存的效果一样，区别只在元素有没有初始值。这部分例程统一写成 `new int[size] {}`，这样即使我们只设置了第 0 个元素，其余元素也有确定的值可读。

**第二，`delete[]` 与 `delete` 的区别。** `new int[10]` 一次申请了 10 个 `int`，释放时必须写 `delete[] array;`，让运行库知道"要释放的是一整块数组，不是单个对象"。写成 `delete array;` 会编译通过、`-Wall` 也可能一句警告都没有，但它属于未定义行为——**这是那种"代码看着对、行为不对"的问题里最难查的一类**。警告是否出现取决于编译器能否在同一函数内追踪到分配点：如果 `new[]` 和 `delete` 写在同一个函数里，GCC 会给出 `-Wmismatched-new-delete`；像本例这样在构造函数里 `new[]`、在析构函数里 `delete`，分成两个函数，通常就一声不响。

### 9.1 程序里的输出顺序说明了什么

例程里 `main` 只做了三件事：创建对象、设置并打印 `a.array[0]`、`return 0`。运行结果是：

```text
=== Demo A: construct an object of 10 ints ===
ctor: allocate 10 ints
a.array[0] = 10
=== Demo B: leave main ===
dtor: free the ints
```

注意 `dtor` 那行出现的**位置**：它在 `=== Demo B: leave main ===` 之后。原因不是我们在这行后面写了释放代码，而是 `main` 的 `return 0;` 执行完，局部对象 `a` 超出作用域被销毁，编译器在这里插入了一次 `~int_array()` 调用。**析构函数是"到期自动执行"，不是"写在哪儿就在哪儿执行"。**

如果删掉 `~int_array()`，程序的行为完全一样，只是再也没有 `delete[]` 这一句，那块 40 字节的内存就永远回不来了——**输出看不出来，泄漏也没有任何提示**。这解释了为什么析构函数必须由写类型的人负责：使用这个类型的人根本看不到指针背后的内存。

## 10 析构函数的三个触发时刻

例程 `E:\CPP_Code\CppFromScratch\ch25_destructors\scope_lifetime\scope_lifetime.cpp` 里定义了一个不管理任何资源、只在创建和销毁时各打印一行的 `tracker` 类型，专门用来看清时机：

```cpp
struct tracker
{
    const char* name;

    tracker(const char* label) : name(label)
    {
        std::cout << "construct " << name << std::endl;
    }

    ~tracker()
    {
        std::cout << "destruct " << name << std::endl;
    }
};
```

它的三个触发时刻是：

**一、花括号作用域结束。** 一对 `{}` 就是一个作用域。在一对花括号里创建的对象，离开这对花括号时立刻被销毁：

```cpp
{
    tracker inner("inner");
    std::cout << "still inside the block" << std::endl;
}
std::cout << "after the block" << std::endl;
```

输出里 `destruct inner` 夹在 `still inside the block` 和 `after the block` 之间。**对象的生命周期跟着作用域走，跟代码的行号无关。**

**二、函数返回。** 函数里的局部对象在函数返回时销毁。`main` 里的局部对象也一样，只不过 `main` 的"返回"就是整个程序结束。

**三、`delete` 一个动态创建的对象。** `new` 出来的对象不受花括号作用域管辖，它的生命周期由 `delete` 划句号：

```cpp
tracker* heap = new tracker("heap");
delete heap;
```

`destruct heap` 紧跟在 `delete heap;` 之后出现，**而不是等到程序结束**。反过来说，如果这里忘了 `delete`，`~tracker()` 永远不会执行——这就是本章第 9 节说的泄漏在对象层面的样子。

### 10.1 同一作用域内按创建的逆序销毁

在同一个作用域里创建多个对象时，**销毁顺序与创建顺序严格相反**：

```text
construct first
construct second
construct third
destruct third
destruct second
```

理由是**后创建的对象可能用到先创建的对象**：如果后创建的对象持有一个指向先创建对象的引用或指针，先销毁它就会留下一根悬空的指针。反过来（后创建的先销毁）则总是安全的。所以这条规则不是约定，而是唯一说得通的顺序。

同一条规则也适用于**成员对象**：一个对象被销毁时，它自己的数据成员会跟着被销毁，顺序同样与声明顺序相反。下一节要用的 `unique_ptr` 成员正是靠这条规则自动完成释放的。

## 11 RAII：让对象自己管自己的资源

把上面的东西合起来看，会发现一个很有力的模式：

> **对象在创建时获取资源，在销毁时释放资源。** 于是只要对象还活着，资源就一定没被释放；对象一消失，资源就一定被交还。

这个模式叫 **RAII**（Resource Acquisition Is Initialization，资源获取即初始化）。它的价值在于把"别忘了释放"这件事从**人**手里交给**编译器**：

- 不再需要在每个 `return` 之前、每个出错分支上都写一遍释放代码——只要局部对象在作用域里，离开时它必然被销毁；
- 类型的使用者完全不用关心资源管理，拿到对象就用，用完就走；
- 资源管理的逻辑只写一遍，写在类型自己身上。

这不是什么新东西，你其实一直在用。`std::vector`（第 07 章）就是 RAII 的典型：往里面加元素时它自动扩容，你从来不用管它内部那块动态数组是什么时候申请的；`vector` 对象销毁时，它内部的内存一定被释放。**标准库容器的背后就是"构造函数申请、析构函数释放"这一对**，只是已经替你写好了。

## 12 什么时候不用写析构函数：把裸指针换成 `unique_ptr`

`manual_cleanup` 那个类型里，真正需要"手动管理"的其实只有一块数组内存。既然第 10 章的 `unique_ptr` 本身就是一个 RAII 类型（它的析构函数会释放自己独占的资源），那就不必由我们手写删除逻辑。

例程 `E:\CPP_Code\CppFromScratch\ch25_destructors\unique_ptr_no_dtor\unique_ptr_no_dtor.cpp` 把数据成员换成了 `std::unique_ptr<int[]>`：

```cpp
struct int_array
{
    std::unique_ptr<int[]> array;

    int_array(int size) : array(new int[size] {})
    {
        std::cout << "ctor: allocate " << size << " ints" << std::endl;
    }

    // 没有析构函数
};
```

三处变化：

1. **成员的类型从 `int*` 变成 `std::unique_ptr<int[]>`**，尖括号里写 `int[]` 表示"它独占的是一个整数数组"，这样 `unique_ptr` 析构时会用 `delete[]`（而不是 `delete`）释放它。
2. **申请内存的语句搬到了成员初始化列表中**：`array(new int[size] {})`。本章第 4 节讲过成员初始化列表是数据成员真正被初始化的地方，这里用它把"申请出来的内存"直接交给 `unique_ptr` 保管。构造函数体里不再有 `new`。
3. **析构函数被删掉了**。对象销毁时，它的成员 `array` 也被销毁，`unique_ptr` 的析构函数负责释放那块内存。清理工作还在，只是**从"我们写"变成"成员自己写"**。

运行结果和裸指针版本一样能正常读写 `a.array[0]`，而整个过程没有任何一行释放代码。这就是"现代 C++ 里大多数类不需要自己写析构函数"的原因：**只要把每一个资源都交给一个已经会自我清理的成员去管，编译器拼起来的就是正确的清理流程。**

这里还有一个反方向的观察：`unique_ptr` 拥有独占所有权，所以标准库把它的拷贝构造函数标记为 `= delete`，禁止任何人复制它。这个"禁止复制"的性格会顺带传递到这个结构体上——本例的 `int_array` 也就跟着不可复制了。复制的规则本身是本章第 13 节起的主题。

### 12.1 那还需要自己写析构函数吗

需要，但判断标准很清楚：

- 类型里**持有需要手工交还的资源**（`new` 出来的内存、打开的文件、系统句柄等裸资源），且**没有把这些资源交给现成的 RAII 成员保管**→ 必须写析构函数。
- 类型里的成员都是"自己会清理自己"的（`int`、`std::array`、`std::vector`、`unique_ptr`、`shared_ptr` 等）→ 不需要写析构函数。写了也不会错，但它做不了任何有价值的事。

用"要不要写析构函数"就能反过来检查类的设计：**如果你的类需要析构函数，说明它在手工管理某个资源，那就要再多问一句——能不能把这个资源交给一个现成的 RAII 类型去管？** 能的话，代码会立刻变短，而且更不容易出错。

这里还要补一个必须提醒的边界。像 `manual_cleanup` 里那种"用裸指针管理内存、自己写析构函数"的类型，只要对象被复制，默认的复制行为会**把指针原样抄一份**（这叫浅拷贝），于是两个对象指向同一块内存，析构时同一块内存被释放两次——**双释放**，属于未定义行为，程序可能崩溃，也可能把别的数据写坏。这是本章第 13 节起要正面解决的问题。

## 13 从已有对象造出新对象

本章第 3 节的构造函数是"从参数造出对象"，本章第 8 节的析构函数是"对象消失时的收尾"。这一部分处理第三种常见需求：**已经有一个对象，想照着它的样子再造一个。**

之前几章里我们已经不知不觉做过很多次了：函数按值传参时，形参是实参的一份副本（第 04 章）；函数按值返回一个对象时，也会产生一个新的对象。为了让"复制一个对象"这件事可以自己定义，C++ 提供了**拷贝构造函数**（copy constructor）。

先看它长什么样。例程 `E:\CPP_Code\CppFromScratch\ch26_copy_constructor\copy_constructor\copy_constructor.cpp` 里有一个最短的可用版本：

```cpp
struct point
{
    int x;
    int y;

    point(int new_x, int new_y) : x(new_x), y(new_y)
    {
    }

    point(const point& p) : x(p.x), y(p.y)
    {
        std::cout << "copy ctor: build (" << x << ", " << y << ") from (" << p.x << ", " << p.y << ")" << std::endl;
    }

    void print()
    {
        std::cout << "x = " << x << ", y = " << y << std::endl;
    }
};
```

对照本章第 3 节的规则看：**名字还是 `point`，也不写返回类型**——这两点和普通构造函数一模一样。差别在参数列表：普通构造函数这里放的是 `int new_x, int new_y`，拷贝构造函数放的是**一个本类型的引用** `const point& p`，`p` 就是"要照着复制的那个对象"。

## 14 签名里的两个决定：引用和 `const`

`point(const point& p)` 这一行有两个必须讲清的地方。

### 14.1 为什么参数必须是引用

假设按值写：

```cpp
point(const point p) : x(p.x), y(p.y) { }      // 错误写法
```

编译器会直接拒绝：

```text
error: invalid constructor; you probably meant 'point (const point&)'
```

原因是**按值传参本身就要先复制一次实参**，而复制需要调用拷贝构造函数——正是我们此刻正在定义的那个函数。这样就形成了"要调用自己才能调用自己"的无限递归。写成引用就没有这个问题：引用只是原有对象的一个别名（第 08 章），传引用不会创建新对象，也就不会触发又一次复制。编译器直接堵死按值的写法，就是为了防止这种无解的递归。

### 14.2 为什么通常加 `const`

拷贝的语义是"照着原对象的样子造一个新的"。这个过程中我们只会**读取**原对象的数据成员（`p.x`、`p.y`），不会去改它。加上 `const` 就是把这句话写进类型里：函数体内不能修改 `p`，编译期就会拦住任何写操作。

不加 `const` 也能编译，但会带来一个实际麻烦。看下面的例子：

```cpp
struct point
{
    int x, y;
    point(int new_x, int new_y) : x(new_x), y(new_y) { }
    point(point& p) : x(p.x), y(p.y) { }        // 没有 const
};

void take(const point& p)
{
    point copy = p;      // 编译失败
}
```

报错是：

```text
error: binding reference of type 'point&' to 'const point' discards qualifiers
```

因为 `p` 是 `const point&`，而拷贝构造函数的参数是 `point&`（非 const 引用），把常量对象交给一个"可能修改它"的引用是非法的。**结论：拷贝构造函数一律写 `const point&`。** 它同时也是"复制不会改动原对象"这一承诺的书面形式，而这条承诺正是后面所有讨论的基础。

## 15 拷贝构造函数在什么时候被调用

这是最容易模糊的一点。判断规则只有一句：

> **凡是"用一个已有对象去初始化一个正在创建的新对象"，调用的都是拷贝构造函数。**

例程一里演示了三种写法：

```cpp
point p2 = p1;      // 拷贝初始化
point p3(p1);       // 直接初始化
print_point(p1);    // 按值传参：形参 p 是新创建的对象
```

三种写法都调用了拷贝构造函数，运行结果里也都能看到那句 `copy ctor: ...` 的打印。其中前两种写法**看着不同，做的事完全相同**，选哪个只是风格问题。

### 15.1 拷贝构造与赋值是两回事

下面两行完全不一样：

```cpp
point p2 = p1;      // p2 是这一刻才诞生的，用 p1 初始化它 → 拷贝构造函数
p2 = p1;            // p2 早就存在了，把 p1 的值覆盖进去 → 赋值，不是拷贝构造
```

区别在于**等号左边的对象是否已经存在**。第二行调用的是"拷贝赋值运算符"，那是另一个函数，写法和运算符重载有关，第 13 章之后会看到它的形式。这里只需要记住这条判断依据：**看左边是不是新对象。**

### 15.2 按值传参也会复制

例程一里还有一个函数：

```cpp
void print_point(point p)
{
    std::cout << "inside the function: ";
    p.print();
}
```

调用 `print_point(p1);` 时，形参 `p` 是一个新创建的对象，用 `p1` 初始化，于是这里又发生了一次拷贝。这解释了第 04 章"形参是实参的副本"这句话的成本：**每一次按值传参都在复制整个对象。** 对 `point` 这种只有两个 `int` 的类型可以忽略；但对一个内部装着几万个元素的类型，这个复制的代价就很大了。第 08 章讲的按引用传参正是为了避免它，而第 14 章会给出另一种更进一步的方案。

例程运行完可以看到，三次拷贝之后 `p1` 的 `x`、`y` 仍然是 `10`、`20`——拷贝构造函数体里只读了 `p` 的成员，没有写。**复制一个对象不应该改变原对象**，这是拷贝构造函数必须守住的性质。

## 16 不写会怎样：编译器隐式生成的拷贝构造函数

例程 `E:\CPP_Code\CppFromScratch\ch26_copy_constructor\implicit_copy\implicit_copy.cpp` 里的 `point` 完全不写拷贝构造函数，但 `point p2 = p1;` 仍然能编译、能跑对。

原因是：**如果你没有声明拷贝构造函数，编译器会隐式声明一个**，它的行为是**逐个数据成员地复制**（memberwise copy）。本例的两个成员都是 `int`，于是 `p2.x` 被初始化为 `p1.x`、`p2.y` 被初始化为 `p1.y`，结果就是一个一模一样的点。

"逐个成员复制"带来的直接后果是**两个对象彼此独立**：例程里把 `p2.x` 改成 `30`、`p2.y` 改成 `40`，`p1` 依然打印 `x = 10, y = 20`。对只含值成员的类型来说，这正是我们想要的默认行为。

如果只是想明确写出"就用编译器给的那个版本"，可以写：

```cpp
point(const point& p) = default;
```

`= default` 的意思是"我声明它存在，但实现交给编译器生成"，效果与不写完全相同。**多数简单类型不需要写拷贝构造函数**，直接用隐式的就够；需要写自己的版本只有两个理由：复制时要多做点事（比如打印、计数），或者默认行为是错的——后者是下一节的内容。

## 17 默认复制什么时候会出错：成员是裸指针

本章第 9 节的 `manual_cleanup` 里有一个用手工管理内存的类型：

```cpp
struct int_array
{
    int* array;
    int_array(int size) { array = new int[size] {}; }
    ~int_array() { delete[] array; }
};
```

它的成员 `array` 是一个裸指针。**指针也是值**，所以逐成员复制会把指针里的地址原样抄一份。意思是复制之后：

- 原对象和新对象的 `array` **指向同一块内存**；
- 两个对象都认为自己负责释放那块内存，析构时就会各释放一次。

这不是"两个副本"，而是"两个对象共享一份资源却被各自当成独占"。同一个资源被 `delete[]` 两次叫**双释放**（double free），属于未定义行为。

在 `manual_cleanup.cpp` 上做一个小实验就能看到这一点：

```cpp
int_array a(10);
int_array b = a;                                     // 默认拷贝构造
std::cout << (a.array == b.array) << std::endl;      // 两个指针是不是同一个地址
```

实测（GCC 16.1.0 / UCRT 运行时）：这一行输出 `1`，说明两个指针确实相等；随后两个析构函数各打印一行 `dtor: free the ints`，进程在退出时异常终止——退出码是 `0xC0000374`（堆损坏；在 MSYS2 bash 下显示为 127，在 PowerShell 下显示为 `-1073740940`，是同一个状态码的不同呈现），整个过程没有任何编译警告。**因为是未定义行为，换一个编译器或运行库表现可能不同**——它也可能安静地跑完，让人完全察觉不到问题所在。这类"看不出错但已经错了"的缺陷，正是拷贝构造函数需要自己掌控的原因。

需要注意的是，**问题的根源不是"默认拷贝构造有 bug"，而是这个类型不该被复制**。`int_array` 里那块内存的所有权是唯一的，复制对象时无法把内存也复制成两份，所以正确处理只有两条路：要么禁止复制（下一节），要么自己写一个"申请一块同样大小的新内存、再把数据逐个拷过去"的拷贝构造函数，也就是**深拷贝**。深拷贝的写法就是本章学的拷贝构造函数，只是函数体里的 `x(p.x)` 换成显式的内存申请与逐元素拷贝；这一部分的重点放在"识别出哪些类型不该被复制、以及怎么禁止它"。

由此可以得到一条实用的经验：**如果一个类需要自己写析构函数（说明它在手工管理某个资源），那它多半也需要自己定义复制行为。** 这条经验在 C++ 里叫"三法则"（Rule of Three）：析构函数、拷贝构造函数、拷贝赋值运算符，要么都不写，要么一起写。本章处理其中的拷贝构造函数，拷贝赋值运算符的写法要用到第 13 章的运算符重载知识。

## 18 禁止复制：`= delete`

有些类型的存在本身就意味着"世界上只能有一个"。例程 `E:\CPP_Code\CppFromScratch\ch26_copy_constructor\delete_copy\delete_copy.cpp` 里的 `owned_int` 就是这种：它独占一块动态分配的 `int`，允许复制必然导致双释放，所以干脆禁止复制。

```cpp
struct owned_int
{
    int* data;

    owned_int(int value) : data(new int(value))
    {
    }

    owned_int(const owned_int& other) = delete;

    ~owned_int()
    {
        delete data;
    }
};
```

`= delete` 写在函数声明后面，意思是"这个函数不允许被使用"。它带来的效果是双重的：

- 编译器**不再隐式生成**拷贝构造函数（因为我们已经声明了它，只是标成了删除）；
- 任何试图拷贝这个类型对象的代码**在编译期直接失败**。

例程里那行复制语句被留成了注释，取消注释后编译会报：

```text
error: use of deleted function 'owned_int::owned_int(const owned_int&)'
```

请注意失败的位置：**编译期**，而不是运行期。这正是 `= delete` 的价值——它把"这个类型不能被复制"变成编译器强制执行的规则，而不是一句只写在文档或注释里、靠人自觉的约定。

标准库里最有名的例子就是 `std::unique_ptr`：它独占自己管理的资源，所以内部把拷贝构造函数（以及拷贝赋值）标记为 `delete`，只保留可以转移所有权的操作。例程里同样创建了一个 `unique_ptr` 并用它，只是那行复制代码被注释掉——取消注释就会看到同一类 `use of deleted function` 报错，报错信息里提到的正是 `std::unique_ptr` 的拷贝构造函数。

### 18.1 一个容易踩的坑：删了拷贝构造，赋值还在

`= delete` 只作用于你删掉的那一个函数。本例删的是**拷贝构造函数**，而 `p2 = p1;` 那种形式调用的是**拷贝赋值运算符**，它并不会因为拷贝构造函数被删除而自动消失。所以下面这段代码**仍然能编译通过**：

```cpp
owned_int a(10);
owned_int b(0);
b = a;              // 编译通过：b.data 和 a.data 指向同一块内存
```

编译通过并不代表正确，它只是说明"复制还在，只是换了个入口"。要彻底堵住复制，两个函数都得处理，其中拷贝赋值运算符的写法要用到第 13 章的运算符重载。这里要建立的认识是：**禁止复制时，先想清楚有哪些入口会复制对象**——初始化、按值传参、赋值，一个都不能漏。
