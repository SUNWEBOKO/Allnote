# STM32 HAL 库 I2C、AHT20 与 OLED 教学文档

## 1. 学完以后能做什么

完成本文后，你应该能够：

- 解释 I2C 为什么只用两根线就能挂多个设备。
- 说清 `SCL`、`SDA`、开漏输出、上拉电阻和逻辑线与之间的关系。
- 根据波形识别空闲状态、起始条件、停止条件、地址字节、读写位和 ACK/NACK。
- 在 CubeMX 中配置 STM32F103 的 I2C1 主机，并理解 `PB6/PB7` 的复用开漏配置。
- 区分 7 位从机地址和 HAL 常用的左移后地址，不再把 `0x3C`、`0x78` 混用。
- 使用 `HAL_I2C_Master_Transmit()`、`HAL_I2C_Master_Receive()`、`HAL_I2C_IsDeviceReady()` 完成基本通信和排查。
- 按 AHT20 手册完成初始化、触发测量、读取 6 字节数据和温湿度换算。
- 理解 I2C 中断/DMA 的非阻塞特性，并用状态机串联发送、等待、接收和解析。
- 理解 SSD1306 OLED 的命令字节、数据字节、整帧刷新模型，并完成一个最小显示实验。
- 看懂像素、页式显存、基本图形、字模和图模之间的关系。

## 2. I2C 解决了什么问题

串口通常是一对一连接。一个 USART 通道往往只连一个设备，如果传感器、EEPROM、显示屏都各占一组串口，STM32 的外设数量和引脚数量很快就不够用了。

I2C 采用总线结构。多个设备共用同一对时钟线和数据线，主机通过地址选择当前要通信的从机：

```text
                 +-- 从机 A
主机 -- SCL -----+-- 从机 B
      -- SDA -----+-- 从机 C
```

在常见 STM32 工程里，STM32 作为主机，传感器、存储器、显示屏等作为从机。I2C 也支持多主机，但本讲义按单主机课程实验展开。

I2C 的关键词可以先记住四个：

| 关键词 | 含义 |
| --- | --- |
| 同步 | 主机提供时钟，通信依赖 `SCL` 节拍 |
| 半双工 | 同一时刻主要沿一条数据线收或发，不是 SPI 那种全双工 |
| 总线式 | 多个设备共用一对线 |
| 地址选择 | 通过从机地址决定当前和谁通信 |

设备数量并不能机械理解为“最多 128 个”。理论上 7 位地址空间很大，但实际还会受到保留地址、地址冲突、总线电容、上拉电阻、线长和时序要求限制。

## 3. 两条总线信号线与电气特性

I2C 只有两条信号线：

| 信号 | 全称 | 作用 |
| --- | --- | --- |
| `SCL` | Serial Clock | 串行时钟线，由主机提供节拍 |
| `SDA` | Serial Data | 串行数据线，传输地址、数据和应答 |

### 3.1 数据位怎么传

每个时钟周期传一位数据，通常高电平表示逻辑 `1`，低电平表示逻辑 `0`。I2C 的基本规则是：

- `SCL` 为低电平时，发送方可以改变 `SDA`。
- `SCL` 为高电平时，`SDA` 必须稳定，接收方就在这段时间采样。
- 数据按高位先行，也就是 MSB first。

因此，普通数据位不能在 `SCL` 为高电平时随意改变 `SDA`，否则会被总线解释成特殊条件。

### 3.2 为什么必须用开漏输出

I2C 的 `SCL` 和 `SDA` 不是普通推挽输出直连，而是总线上所有设备都使用开漏（或开集电极）方式，再由上拉电阻把线路恢复成高电平。

开漏输出的行为可以简单理解为：

- 写入 `0`：主动把引脚拉低。
- 写入 `1`：不主动拉高，而是进入高阻态，相当于“放手”。

| 写入值 | 引脚状态 | 总线可能的电平 |
| --- | --- | --- |
| `0` | 主动下拉 | 低电平 |
| `1` | 高阻态 | 由上拉电阻和其他设备共同决定 |

如果多台设备共用一条线，而大家都能主动向高、向低强推，就可能短路对抗。开漏结构避免了这个问题。

### 3.3 上拉电阻和逻辑线与

`SCL` 和 `SDA` 通常各需要一颗上拉电阻，常见起始值是 `4.7 kΩ`。典型连接如下：

```text
VDD
 |             VDD
4.7 kΩ         4.7 kΩ
 |             |
SCL -----------+----------- 各设备 SCL
SDA -----------+----------- 各设备 SDA
```

线路只要没有设备主动拉低，就会被上拉电阻拉成高电平；只要有任意一个设备拉低，整条线就是低电平。这就是 I2C 常说的“逻辑线与”。

它带来两个直接结果：

- 总线空闲时，`SCL` 和 `SDA` 都是高电平。
- 多主机场景中，设备一边发高一边读到低，说明别的设备正在拉低，它就可能失去仲裁。

对单主机课程实验来说，不需要深入仲裁过程，但必须知道：I2C 的“高电平”不是设备主动推出来的，而是上拉电阻拉出来的。

## 4. I2C 一次通信的基本时序

### 4.1 空闲状态

当总线空闲时：

```text
SCL = 高
SDA = 高
```

### 4.2 起始条件

当 `SCL` 保持高电平时，`SDA` 从高变低，这就是起始条件（Start Condition）：

```text
SCL 为高时，SDA 从高切换到低
```

这个边沿告诉所有从机：主机准备开始一次新的通信。

### 4.3 停止条件

当 `SCL` 保持高电平时，`SDA` 从低变高，这就是停止条件（Stop Condition）：

```text
SCL 为高时，SDA 从低切换到高
```

它表示这次通信结束，总线回到空闲。

### 4.4 地址字节与 R/W 位

起始条件后，主机发送的第一个字节通常是地址字节：

```text
bit7 ~ bit1：7 位从机地址
bit0         ：R/W 位（0 = 写，1 = 读）
```

例如 7 位地址是 `0x3C` 的 OLED，地址位和读写位拼起来后：

```text
7 位地址：0111100       = 0x3C
写地址字节：01111000    = 0x78
读地址字节：01111001    = 0x79
```

这也是 STM32 HAL 里最容易混淆的一点：

- `0x3C` 是 7 位从机地址。
- `0x78` 是左移一位后的 8 位写地址形式。
- `0x79` 是左移后再把最低位置 1 的读地址字节。

很多 HAL API 约定你传入的是“左移一位后的设备地址”，所以代码里常写：

```c
#define OLED_ADDR (0x3C << 1)  // 0x78
```

不要把已经左移过的 `0x78` 再左移，也不要把 `0x78` 当成 7 位地址去记。

### 4.5 ACK 与 NACK

每发完一个字节，都会有第 9 个时钟周期用于应答：

- 接收方拉低 `SDA`，表示 ACK，意思是“这个字节收到了，请继续”。
- 接收方不拉低 `SDA`，保持高电平，表示 NACK。

| 应答 | SDA 电平 | 含义 |
| --- | --- | --- |
| ACK | 低 | 字节接收正常，请继续 |
| NACK | 高 | 无应答、接收异常或传输结束 |

如果主机发地址后没有收到 ACK，往往说明地址不对、设备不在线、接线有误或总线本身有问题。

## 5. 典型 I2C 读写序列

### 5.1 主机写一个字节到从机寄存器

典型顺序如下：

```text
起始 -> 从机地址+W -> ACK -> 寄存器地址 -> ACK -> 数据字节 -> ACK -> 停止
```

这种模式常见于给传感器寄存器写配置值。

### 5.2 主机从从机读一个字节

很多寄存器型从机不会让你直接读，而是先告诉它“我要读哪个寄存器”，再重新发起一次读：

```text
起始 -> 从机地址+W -> ACK -> 寄存器地址 -> ACK
重复起始 -> 从机地址+R -> ACK -> 数据字节 -> NACK -> 停止
```

这就是“先写寄存器地址，再读数据”的常见时序。很多传感器用 `HAL_I2C_Mem_Read()` 时，本质上就是 HAL 帮你完成这条序列。

### 5.3 直接写命令流和寄存器读写的区别

不是所有 I2C 设备都按“寄存器地址 + 数据”的形式工作。

- 对于 MPU6050 这类传感器，经常按寄存器模式操作，适合 `HAL_I2C_Mem_Read()`、`HAL_I2C_Mem_Write()`。
- 对于 SSD1306 OLED，很多时候是直接发“控制字节 + 命令字节”或“控制字节 + 显存数据”，更适合 `HAL_I2C_Master_Transmit()`。

因此，先看芯片手册规定的总线格式，再决定该用哪类 HAL API。

## 6. I2C 与 SPI 简单对比

| 对比项 | I2C | SPI |
| --- | --- | --- |
| 线数 | 2 根：`SCL + SDA` | 常见 4 根：`SCLK + MOSI + MISO + CS` |
| 通信方式 | 半双工 | 全双工 |
| 多从机选择 | 靠地址 | 靠片选线 |
| 速度 | 常见 100 kHz / 400 kHz | 常见可到数 MHz 甚至更高 |
| 适用场景 | 传感器、配置型外设、小屏 | 高速显示、Flash、快速数据采集 |

如果引脚紧张、设备较多、数据量不大，I2C 很合适；如果追求高速刷新和吞吐量，SPI 通常更强。

SSD1306 之所以常见 I2C 版本，就是因为屏幕小、接口省线、接法简单，但代价是整帧刷新速度不如 SPI 版本。

## 7. STM32F103 的 I2C 外设与 CubeMX 配置

### 7.1 I2C 外设能做什么

STM32F103 的 I2C 外设支持：

| 特性 | 说明 |
| --- | --- |
| 主机/从机 | 都支持 |
| 地址长度 | 7 位和 10 位都支持 |
| 速度模式 | 标准模式 `100 kHz`、快速模式 `400 kHz` |
| 中断/事件 | 可配事件中断和错误中断 |

课程实验按最常见的“STM32 作为主机，OLED 作为从机”来用。

### 7.2 CubeMX 配置步骤

以 `I2C1` 为例：

1. 新建工程，目标芯片选择 `STM32F103C8T6`。
2. 在 `SYS` 中保留 `Serial Wire`，避免后续下载调试出问题。
3. 打开 `I2C1`，模式选择 `I2C`。
4. 确认引脚映射为 `PB6 = I2C1_SCL`、`PB7 = I2C1_SDA`。
5. 在参数中把速度先设为 `100 kHz`，先保证能稳定通信，再考虑提速。
6. 工具链选择 `MDK-ARM`，点击 `Generate Code`。

### 7.3 引脚为什么是复用开漏

启用 I2C 后，CubeMX 会把相关引脚配置成复用开漏输出，不需要手动改成推挽。

```text
I2C1_SCL -> PB6
I2C1_SDA -> PB7
模式      -> 复用开漏
```

如果你把它误改成推挽输出，就破坏了 I2C 总线的共享电气结构，通信很容易直接失败。

### 7.4 速度、上拉和时钟拉伸

入门实验建议先用 `100 kHz`，原因很简单：

- 对上拉电阻、线长、信号上升时间要求更宽松。
- 先跑通总线，再排查 OLED 指令和显示逻辑更高效。

`400 kHz` 快速模式虽然更快，但对总线质量要求更高。只有在地址、接线、上拉、电源都确认无误后，才建议尝试。

另外，常见从机会使用时钟拉伸。`Clock No Stretch` 的 `NOSTRETCH` 位实际含义是：主机在接收期间禁止拉伸 SCL（从机把时钟拉低以争取处理时间，主机可以拒绝配合）。不要望文生义地理解成“关闭后整个主机就不能配合拉伸”。课堂工程里保持默认、优先保证兼容性即可。

## 8. HAL I2C 最常用的几个 API

### 8.1 `HAL_I2C_Master_Transmit()`

函数原型：

```c
HAL_StatusTypeDef HAL_I2C_Master_Transmit(
    I2C_HandleTypeDef *hi2c,
    uint16_t DevAddress,
    uint8_t *pData,
    uint16_t Size,
    uint32_t Timeout
);
```

用途：主机向从机直接发送一段连续数据。

典型场景：

- 给 OLED 发送命令流。
- 给 OLED 发送控制字节加显示数据。
- 给某些非寄存器型设备直接发原始字节序列。

参数重点：

| 参数 | 含义 |
| --- | --- |
| `hi2c` | I2C 句柄，例如 `&hi2c1` |
| `DevAddress` | 从机地址，通常传左移后的地址，例如 `OLED_ADDR` |
| `pData` | 发送缓冲区首地址 |
| `Size` | 发送字节数 |
| `Timeout` | 超时，单位 ms |

### 8.2 `HAL_I2C_Master_Receive()`

函数原型：

```c
HAL_StatusTypeDef HAL_I2C_Master_Receive(
    I2C_HandleTypeDef *hi2c,
    uint16_t DevAddress,
    uint8_t *pData,
    uint16_t Size,
    uint32_t Timeout
);
```

用途：主机直接从从机接收数据，不主动携带寄存器地址阶段。

它能用，但并不是所有 OLED 模块都适合这样读状态。SSD1306 的很多成品模块主要被当作“写显示数据”的设备，是否真的支持你当前驱动里的读时序，要看控制器和外围电路。

### 8.3 `HAL_I2C_Mem_Write()` / `HAL_I2C_Mem_Read()`

```c
HAL_I2C_Mem_Write(...)
HAL_I2C_Mem_Read(...)
```

用途：访问带内部寄存器地址的从机。

适合：

- 传感器寄存器配置
- EEPROM 读写
- 各类“先发寄存器地址，再收/发数据”的设备

不适合生搬硬套到所有 OLED 驱动，因为 OLED 常见操作不一定是标准“寄存器地址 + 数据”的格式。

### 8.4 `HAL_I2C_IsDeviceReady()`

这个函数非常适合排查：

- 地址到底对不对。
- 从机是否在线。
- 总线是不是连最基本的 ACK 都拿不到。

它不是万金油，但在“屏幕不亮，到底是地址错还是初始化命令错”的场景里非常有价值。

### 8.5 返回值和错误判断

HAL I2C API 一般返回 `HAL_StatusTypeDef`：

| 返回值 | 含义 | 常见原因 |
| --- | --- | --- |
| `HAL_OK` | 传输成功 | 通信完成 |
| `HAL_ERROR` | 传输错误 | NACK、总线错误、仲裁丢失等 |
| `HAL_BUSY` | 总线忙 | 上次通信未结束、总线被占用 |
| `HAL_TIMEOUT` | 超时 | 从机无响应、SCL/SDA 被持续拉低 |

如果要进一步判断，可以再配合：

```c
HAL_I2C_GetError(&hi2c1);
```

它不能替代接线检查和波形分析，但至少能帮你确认问题是“地址无应答”还是“总线状态异常”。

### 8.6 关于超时参数

`Timeout` 的单位是毫秒。

- `HAL_MAX_DELAY` 适合入门实验，写起来简单。
- 产品代码不建议长期依赖无限等待。

如果总线被某个设备一直拉低，`HAL_MAX_DELAY` 可能让程序长时间卡在发送函数里。教学阶段可以先理解它的作用，实战阶段要有“有限超时 + 恢复策略”的意识。

## 9. AHT20：把 I2C 时序落到真实传感器

AHT20 是一个固定地址的温湿度传感器。它很适合串起前面的知识：STM32 先向从机发送命令，等待传感器完成测量，再读取状态和原始数据。部分模块或商品页面会同时出现 DHT20 标注，实际编程前仍应核对手中器件的数据手册、地址和命令集。

### 9.1 地址与测量流程

AHT20 的 7 位地址是 `0x38`。HAL 接口通常接收左移一位后的地址：

```c
#define AHT20_ADDRESS (0x38U << 1)  /* 0x70 */
```

读操作在线路上的地址字节最低位会变成 `1`，因此逻辑分析仪可能显示 `0x71`。应用代码仍传 `0x70`，读写位由 HAL 处理。

按照数据手册，基本流程为：

```text
上电等待至少 40 ms
-> 读取状态，检查校准使能位
-> 必要时发送 BE 08 00 初始化
-> 发送 AC 33 00 触发测量
-> 等待测量完成
-> 读取 6 字节
-> 检查忙标志
-> 拼接并换算温湿度
```

### 9.2 驱动文件的最小职责

可以把设备逻辑放进 `aht20.c/.h`，让 `main.c` 只负责调用：

```c
HAL_StatusTypeDef AHT20_Init(I2C_HandleTypeDef *hi2c);
HAL_StatusTypeDef AHT20_Read(
    I2C_HandleTypeDef *hi2c,
    float *temperature,
    float *humidity);
```

这种拆分不是为了堆文件，而是把“设备命令与换算”同“主循环业务”分开。驱动仍通过外部传入的 `I2C_HandleTypeDef` 使用 CubeMX 已初始化好的 I2C。

### 9.3 阻塞式初始化

```c
#define AHT20_STATUS_CALIBRATED 0x08U

HAL_StatusTypeDef AHT20_Init(I2C_HandleTypeDef *hi2c)
{
    uint8_t status = 0U;
    uint8_t init_command[3] = {0xBEU, 0x08U, 0x00U};

    HAL_Delay(40U);

    if (HAL_I2C_Master_Receive(
            hi2c,
            AHT20_ADDRESS,
            &status,
            1U,
            100U) != HAL_OK)
    {
        return HAL_ERROR;
    }

    if ((status & AHT20_STATUS_CALIBRATED) == 0U)
    {
        if (HAL_I2C_Master_Transmit(
                hi2c,
                AHT20_ADDRESS,
                init_command,
                sizeof(init_command),
                100U) != HAL_OK)
        {
            return HAL_ERROR;
        }

        HAL_Delay(10U);
    }

    return HAL_OK;
}
```

这里使用有限超时，便于设备断线或总线异常时让调用返回。初始化命令和等待时间应以手中 AHT20 模块的数据手册版本为准。

### 9.4 触发、读取与换算

```c
#define AHT20_STATUS_BUSY 0x80U
#define AHT20_SCALE       1048576.0f  /* 2^20 */

HAL_StatusTypeDef AHT20_Read(
    I2C_HandleTypeDef *hi2c,
    float *temperature,
    float *humidity)
{
    uint8_t measure_command[3] = {0xACU, 0x33U, 0x00U};
    uint8_t data[6] = {0U};
    uint32_t raw_humidity;
    uint32_t raw_temperature;

    if ((temperature == NULL) || (humidity == NULL))
    {
        return HAL_ERROR;
    }

    if (HAL_I2C_Master_Transmit(
            hi2c,
            AHT20_ADDRESS,
            measure_command,
            sizeof(measure_command),
            100U) != HAL_OK)
    {
        return HAL_ERROR;
    }

    HAL_Delay(80U);

    if (HAL_I2C_Master_Receive(
            hi2c,
            AHT20_ADDRESS,
            data,
            sizeof(data),
            100U) != HAL_OK)
    {
        return HAL_ERROR;
    }

    if ((data[0] & AHT20_STATUS_BUSY) != 0U)
    {
        return HAL_BUSY;
    }

    raw_humidity =
        ((uint32_t)data[1] << 12) |
        ((uint32_t)data[2] << 4) |
        ((uint32_t)data[3] >> 4);

    raw_temperature =
        (((uint32_t)data[3] & 0x0FU) << 16) |
        ((uint32_t)data[4] << 8) |
        (uint32_t)data[5];

    *humidity = ((float)raw_humidity * 100.0f) / AHT20_SCALE;
    *temperature =
        ((float)raw_temperature * 200.0f) / AHT20_SCALE - 50.0f;

    return HAL_OK;
}
```

原始湿度和温度都占 20 bit，其中 `data[3]` 的高 4 bit 属于湿度，低 4 bit 属于温度。移位前先转换为 `uint32_t`，可以避免 8 位数据移位时丢失高位。

换算公式为：

$$
RH=\frac{S_{RH}}{2^{20}}\times100\%
$$

$$
T=\frac{S_T}{2^{20}}\times200-50\ ^\circ\mathrm{C}
$$

### 9.5 主循环最小实验

```c
float temperature;
float humidity;

if (AHT20_Init(&hi2c1) != HAL_OK)
{
    Error_Handler();
}

while (1)
{
    if (AHT20_Read(&hi2c1, &temperature, &humidity) == HAL_OK)
    {
        /* 在这里串口输出，或交给后面的 OLED 显示。 */
    }

    HAL_Delay(1000U);
}
```

这条阻塞链最适合第一次跑通设备，但 `HAL_Delay(80)` 和 I2C 收发期间 CPU 不能推进其他业务。下一节用中断和状态机拆开这些步骤。

## 10. 为什么非阻塞 I2C 需要状态机

把函数名从阻塞式改成 `_IT` 或 `_DMA`，并不代表原来的顺序代码会自动正确：

```c
HAL_I2C_Master_Receive_IT(&hi2c1, AHT20_ADDRESS, data, 6U);
Parse(data);  /* 错误：此时通常还没接收完成。 */
```

非阻塞启动函数会立即返回。后续发送、等待、接收和解析必须由“当前状态”决定，而不是靠代码行的先后顺序硬接。

### 10.1 AHT20 的状态划分

```c
typedef enum
{
    AHT20_STATE_READY_TO_START,
    AHT20_STATE_TX_BUSY,
    AHT20_STATE_WAIT_MEASUREMENT,
    AHT20_STATE_RX_BUSY,
    AHT20_STATE_DATA_READY,
    AHT20_STATE_WAIT_NEXT,
    AHT20_STATE_ERROR
} AHT20_State;
```

状态转换如下：

```text
READY_TO_START
-> 启动发送测量命令
-> TX_BUSY
-> 发送完成回调
-> WAIT_MEASUREMENT
-> 等待至少 80 ms
-> 启动接收
-> RX_BUSY
-> 接收完成回调
-> DATA_READY
-> 主循环解析并输出
-> WAIT_NEXT
-> 到达下一测量周期
-> READY_TO_START
```

状态机的价值不是“让代码显得高级”，而是让每一步只在前置条件满足后发生。

### 10.2 非阻塞缓冲区为什么不能是普通局部变量

下面的写法存在生命周期问题：

```c
void AHT20_Start(void)
{
    uint8_t command[3] = {0xACU, 0x33U, 0x00U};
    HAL_I2C_Master_Transmit_IT(
        &hi2c1,
        AHT20_ADDRESS,
        command,
        sizeof(command));
}
```

函数返回后，普通局部数组的存储期结束，但中断发送可能还在读取它。非阻塞传输缓冲区应使用静态、全局或由上层保证生命周期足够长的存储。

## 11. I2C 中断模式与状态机

### 11.1 CubeMX 配置

在 `I2C1 -> NVIC Settings` 中使能：

- `I2C1 event interrupt`
- `I2C1 error interrupt`

事件中断推进地址、发送、接收和停止等正常流程；错误中断处理总线错误、仲裁丢失、无应答等异常。它们属于 I2C 外设的专属数据流程，因此放在本文件中，而不是通用中断文档。

### 11.2 状态与缓冲区

```c
static volatile AHT20_State aht20_state =
    AHT20_STATE_READY_TO_START;

static uint8_t aht20_measure_command[3] =
    {0xACU, 0x33U, 0x00U};
static uint8_t aht20_rx_data[6];

static uint32_t aht20_deadline = 0U;
```

初始化仍可使用前面的阻塞式 `AHT20_Init()`；初始化只执行一次，重点先把周期测量改成非阻塞流程。

### 11.3 主循环推进状态

```c
static uint8_t TickReached(uint32_t deadline)
{
    return ((int32_t)(HAL_GetTick() - deadline) >= 0) ? 1U : 0U;
}

static void AHT20_Task(void)
{
    switch (aht20_state)
    {
        case AHT20_STATE_READY_TO_START:
            if (HAL_I2C_Master_Transmit_IT(
                    &hi2c1,
                    AHT20_ADDRESS,
                    aht20_measure_command,
                    sizeof(aht20_measure_command)) == HAL_OK)
            {
                aht20_state = AHT20_STATE_TX_BUSY;
            }
            else
            {
                aht20_state = AHT20_STATE_ERROR;
            }
            break;

        case AHT20_STATE_WAIT_MEASUREMENT:
            if (TickReached(aht20_deadline) != 0U)
            {
                if (HAL_I2C_Master_Receive_IT(
                        &hi2c1,
                        AHT20_ADDRESS,
                        aht20_rx_data,
                        sizeof(aht20_rx_data)) == HAL_OK)
                {
                    aht20_state = AHT20_STATE_RX_BUSY;
                }
                else
                {
                    aht20_state = AHT20_STATE_ERROR;
                }
            }
            break;

        case AHT20_STATE_DATA_READY:
            /* 检查忙标志，按 9.4 节公式解析并输出。 */
            aht20_deadline = HAL_GetTick() + 1000U;
            aht20_state = AHT20_STATE_WAIT_NEXT;
            break;

        case AHT20_STATE_WAIT_NEXT:
            if (TickReached(aht20_deadline) != 0U)
            {
                aht20_state = AHT20_STATE_READY_TO_START;
            }
            break;

        case AHT20_STATE_ERROR:
            /* 记录 HAL_I2C_GetError()，再按项目策略恢复。 */
            break;

        case AHT20_STATE_TX_BUSY:
        case AHT20_STATE_RX_BUSY:
        default:
            break;
    }
}
```

`TX_BUSY` 和 `RX_BUSY` 状态不需要主循环反复查询硬件；完成时由回调推进。等待测量使用 `HAL_GetTick()` 截止时间，没有在循环中调用 `HAL_Delay(80)`。

`DATA_READY` 中可把 9.4 节的忙标志检查、20 bit 拼接和公式换算提取成 `AHT20_ParseRaw()`，避免阻塞版与非阻塞版各维护一套公式。本例让 `ERROR` 保持锁存，便于初学时在调试器中查看 `HAL_I2C_GetError()`；需要自动恢复时，再由主循环执行总线恢复、重新初始化和限次重试。

### 11.4 完成与错误回调

```c
void HAL_I2C_MasterTxCpltCallback(I2C_HandleTypeDef *hi2c)
{
    if ((hi2c->Instance == I2C1) &&
        (aht20_state == AHT20_STATE_TX_BUSY))
    {
        aht20_deadline = HAL_GetTick() + 80U;
        aht20_state = AHT20_STATE_WAIT_MEASUREMENT;
    }
}

void HAL_I2C_MasterRxCpltCallback(I2C_HandleTypeDef *hi2c)
{
    if ((hi2c->Instance == I2C1) &&
        (aht20_state == AHT20_STATE_RX_BUSY))
    {
        aht20_state = AHT20_STATE_DATA_READY;
    }
}

void HAL_I2C_ErrorCallback(I2C_HandleTypeDef *hi2c)
{
    if (hi2c->Instance == I2C1)
    {
        aht20_state = AHT20_STATE_ERROR;
    }
}
```

HAL 弱回调在整个工程中只能实现一次。若同一条 I2C 总线上还有其他异步设备，应在统一回调中结合 `hi2c->Instance` 和当前事务状态分发，不能让多个驱动文件各自重复定义同名回调。

## 12. 从 I2C 中断切换到 DMA

I2C DMA 仍然是非阻塞流程，状态机和完成回调可以保持不变。区别只是数据搬运从“每个字节由中断服务”改为“DMA 成批搬运”：

```c
HAL_I2C_Master_Transmit_DMA(
    &hi2c1,
    AHT20_ADDRESS,
    aht20_measure_command,
    sizeof(aht20_measure_command));

HAL_I2C_Master_Receive_DMA(
    &hi2c1,
    AHT20_ADDRESS,
    aht20_rx_data,
    sizeof(aht20_rx_data));
```

在 CubeMX 的 `I2C1 -> DMA Settings` 中添加 TX 和 RX，检查方向、Byte 宽度、内存自增和 Normal 模式，并确认相应 DMA 中断已启用。STM32F103 的请求映射固定，具体通道以目标芯片参考手册和 CubeMX 显示为准。

对 AHT20 这种每秒只有少量字节的设备，DMA 不一定比中断模式更值得；这里的意义主要是理解“状态机不依赖搬运者”。选择方式时应先看数据量和任务复杂度，不要为了使用 DMA 而使用 DMA。

## 13. OLED 硬件连接：先把总线接对

本实验使用一块常见的 `0.96 英寸 I2C OLED`，控制器示例为 SSD1306。模块通常有四个引脚：

| OLED 引脚 | 连接 |
| --- | --- |
| `VCC` | 合适的电源电压 |
| `GND` | 系统地 |
| `SCL` | STM32 的 `I2C1_SCL`，示例为 `PB6` |
| `SDA` | STM32 的 `I2C1_SDA`，示例为 `PB7` |

连接关系：

```text
STM32F103                    OLED
PB6  (I2C1_SCL)  ----------  SCL
PB7  (I2C1_SDA)  ----------  SDA
3.3 V             ----------  VCC
GND               ----------  GND
```

接线检查清单：

- STM32 和 OLED 必须共地。
- `SCL` 接 `SCL`，`SDA` 接 `SDA`，不要交叉。
- 确认模块供电电压范围，不要想当然把 5 V 逻辑直接送进不耐 5 V 的引脚。
- 确认上拉电阻是否已经板载；如果模块已带上拉，不要又乱并一堆很小阻值。
- 如果下载程序失败，先检查是否保留了 `Serial Wire`，不要一上来就怀疑 I2C。

## 14. OLED 控制器、地址与命令流

### 14.1 7 位地址和 HAL 地址口径必须区分

SSD1306 常见 7 位地址是 `0x3C`，也有一部分模块因为地址引脚连接不同而变成 `0x3D`。

在 HAL 代码里常见写法是：

```c
#define OLED_ADDR (0x3C << 1)   // 0x78
```

这表示：

- 讲芯片地址时，说 `0x3C` 更准确。
- 写 HAL 发送代码时，经常传 `0x78`。

如果你的模块地址脚状态不同，也可能要换成：

```c
#define OLED_ADDR (0x3D << 1)   // 0x7A
```

所以“屏幕没响应”时，`0x3C/0x3D` 一定要列入第一批排查项。

### 14.2 命令字节和数据字节不是一回事

SSD1306 通过 I2C 收数据时，前面常常要先发一个控制字节，告诉它后面的内容该按什么解释。

当前教学中最重要的两个控制字节是：

| 控制字节 | 含义 |
| --- | --- |
| `0x00` | 后续字节按命令解释 |
| `0x40` | 后续字节按显示数据解释 |

也就是说：

- 发初始化命令时，常见格式是 `0x00 + 命令字节`。
- 发整页显存数据时，常见格式是 `0x40 + 128 字节显示数据`。

如果你把这两个控制字节用错了，I2C 可能通信成功，但 OLED 仍然没有正确显示。

### 14.3 初始化命令不是只背几个字节

课程里经常能见到这些命令：

| 字节 | 常见作用 |
| ---: | --- |
| `0xAE` | 关闭显示 |
| `0x8D`、`0x14` | 使能电荷泵 |
| `0xA6` | 正常显示 |
| `0xAF` | 开启显示 |

它们很重要，但不能把这几条命令误认为“所有 SSD1306 模块的完整初始化序列”。不同模块的供电方式、扫描方向、页寻址设置、偏移配置可能不同，最后都要回到手册和驱动源码核对。

### 14.4 SSD1306 与 CH1116 不能混用初始化序列

OLED 模块可能使用 CH1116，也可能使用 SSD1306。它们的分辨率和页式显存思路相近，但地址、列偏移、供电配置和初始化命令可能不同。本文以 SSD1306 为示例；更换控制器时应替换设备层命令，不能只因为屏幕同为 `128x64` 就照搬全部字节。

> 工程中已有的完整 OLED 驱动位于 `E:\ProjectStm\驱动库\OLED`，包含初始化序列、显存模型和绘图函数，是本文第 15~18 章所讲概念的成品实现。练习时先按本文理解原理，再对照驱动源码核对命令字节。

## 15. 从 I2C 到 OLED：最小通信代码怎么写

### 15.1 直接发送命令流

如果你只是想验证“STM32 能不能往 OLED 发命令”，最小代码可以像这样：

```c
#define OLED_ADDR (0x3C << 1)

uint8_t command[] = {0x00, 0xAE, 0x8D, 0x14, 0xAF};

HAL_StatusTypeDef status = HAL_I2C_Master_Transmit(
    &hi2c1,
    OLED_ADDR,
    command,
    sizeof(command),
    HAL_MAX_DELAY
);
```

这里的第一个字节 `0x00` 就是“后面是命令”的标记。

### 15.2 先确认设备是否在线

在怀疑地址或接线时，可以先做在线检测：

```c
HAL_StatusTypeDef ready = HAL_I2C_IsDeviceReady(
    &hi2c1,
    OLED_ADDR,
    3,
    100
);
```

如果这里都不 `HAL_OK`，先别急着改复杂初始化序列，先去查：

- 地址是不是写错了。
- `PB6/PB7` 是否真的在工作。
- 供电、共地、上拉是否正确。

### 15.3 用板载 LED 辅助观察

可以把 `PC13` 板载 LED 当成最简单的状态指示：

```c
if (status == HAL_OK)
{
    HAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, GPIO_PIN_RESET);
}
else
{
    HAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, GPIO_PIN_SET);
}
```

它只能告诉你程序走到了哪个分支，不能替代逻辑分析仪或示波器，但在“到底有没有进入成功分支”这个层面仍然有帮助。

## 16. OLED 驱动为什么常用“先写显存，再整帧刷新”

很多 SSD1306 驱动不会每画一个点就立刻发 I2C，而是分成两步：

1. 先在 MCU RAM 里维护一块显存缓冲区。
2. 需要显示时，再一次性把整帧数据刷到屏幕。

核心链路可以记成：

```text
应用层绘图/打印 -> OLED 显存缓冲区 -> I2C 整帧刷新 -> OLED 屏幕
```

这么做的好处是：

- 页面逻辑和底层 I2C 发包分离。
- 可以先把整帧内容画完整，再统一显示。
- 减少边画边刷导致的闪烁。

对于 `128x64` 单色屏，常见显存组织是 `8 页 x 128 列`：

- 屏幕高度 64 像素。
- 每页 8 行像素。
- 一共 8 页，所以 `8 x 8 = 64`。

因此，一个像素 `(x, y)` 常常对应到：

```text
page = y / 8
bit  = y % 8
column = x
```

你不一定要现在就把显存位运算背下来，但必须知道：OLED 驱动往往不是“画点就立刻亮点”，而是“改缓冲区，再整体刷新”。

## 17. OLED 实战调用链：初始化、清帧、绘制、刷新

很多课程驱动采用下面这条主线：

```text
初始化 I2C -> OLED_Init(&hi2c1)
每一帧：OLED_NewFrame() -> 绘图/打印 -> OLED_ShowFrame()
```

### 17.1 为什么 `OLED_Init(&hi2c1)` 很常见

不少驱动不会把 `hi2c1` 写死在源码里，而是在初始化时由外部传入：

```c
OLED_Init(&hi2c1);
```

这表示驱动只依赖“一个已经初始化好的 I2C 句柄”，而不是强绑定某个具体外设。这样移植时更灵活，但前提是你传进去的句柄必须和实际硬件连接一致。

### 17.2 为什么画了还不显示

如果驱动采用显存模型，那么：

- `OLED_NewFrame()` 是清空缓冲区。
- `OLED_DrawXXX()`、`OLED_PrintXXX()` 只是改缓冲区内容。
- `OLED_ShowFrame()` 才是真正把内容刷到屏幕。

所以“代码里已经画了矩形和字符串，屏幕还是没变化”的高频原因之一，就是漏掉了 `OLED_ShowFrame()`。

### 17.3 一个典型主循环

```c
OLED_Init(&hi2c1);

while (1)
{
    OLED_NewFrame();

    OLED_Printf(0, 0, OLED_COLOR_NORMAL, "count:%d", count);
    OLED_DrawRectangle(0, 20, 60, 20, OLED_COLOR_NORMAL);

    OLED_ShowFrame();
}
```

这条链背后的意思不是背函数名，而是理解：

- I2C 先初始化好。
- OLED 初始化阶段建立和屏幕的基本通信。
- 每一帧先准备内存里的图像，再统一刷新。

### 17.4 从一个像素到基本图形

假设显存定义为 `oled_buffer[8][128]`，点亮 `(x, y)` 的核心操作是找到页和页内 bit：

```c
void OLED_SetPixel(uint8_t x, uint8_t y, uint8_t on)
{
    uint8_t mask;

    if ((x >= 128U) || (y >= 64U))
    {
        return;
    }

    mask = (uint8_t)(1U << (y % 8U));

    if (on != 0U)
    {
        oled_buffer[y / 8U][x] |= mask;
    }
    else
    {
        oled_buffer[y / 8U][x] &= (uint8_t)(~mask);
    }
}
```

直线、矩形、圆等函数最终都可以归结为“计算哪些坐标应亮，再调用画点”。不同驱动可能把显存维度写成 `[128][8]`，或对列、页做偏移；移植时应先核对数组布局，不能只复制位运算。

### 17.5 字模、图模与字符串

文字和图片不是 OLED 自己理解的高级对象，它们最终仍是一组像素：

```text
字符或图片
-> 按约定格式生成位图数据
-> 把位图贴到显存指定坐标
-> OLED_ShowFrame()
```

- ASCII 字体通常用固定宽高的字模表，根据字符编码找到对应位图。
- 汉字或任意 UTF-8 字符需要驱动能把字符串解码并映射到已准备的字模；字库没有的字符无法凭空显示。
- 图片通常先缩放、二值化，再按驱动要求的横向或纵向取模格式导出。
- 反色绘制本质上是清除或翻转目标像素，不是更换 OLED 的物理颜色。

取模工具的输出格式必须与驱动的读取顺序一致。出现文字错位、图片倾斜或每 8 行交错时，优先检查取模方向、位序、宽高和显存页布局。

## 18. 整帧刷新为什么不能无脑高频调用

SSD1306 的 `128x64` 单色屏，一整帧数据本身就有：

```text
128 x 64 / 8 = 1024 Byte
```

再加上页地址命令、列地址命令、控制字节和 I2C 应答开销，整帧刷新并不轻。

这意味着：

- 在 `100 kHz` 下，整帧刷新明显不算快。
- 在 `400 kHz` 下会好很多，但也不是“可以随便塞进高速中断”的级别。
- 没有画面变化时，不需要无意义地无限刷屏。

因此 OLED 更适合做人机界面、菜单、文字和简单图形显示，不适合拿 I2C 版本做特别高帧率的动态图像任务。

## 19. 分层排障：总线、设备、状态机、显示

| 现象 | 优先检查 |
| --- | --- |
| `HAL_I2C_IsDeviceReady()` 不通过 | 地址、接线、供电、共地、上拉是否正确 |
| `HAL_I2C_Master_Transmit()` 返回 `HAL_ERROR` | 地址格式、SCL/SDA 是否接反、设备是否在线 |
| 返回 `HAL_BUSY` | 总线是否被某个设备持续拉低、上次通信是否异常中断 |
| 返回 `HAL_TIMEOUT` | 时钟线或数据线是否被拉低、速度是否过高、上拉是否过弱 |
| `PB6/PB7` 没波形 | I2C1 是否真的启用、`MX_I2C1_Init()` 是否执行、引脚是否被别的外设占用 |
| AHT20 始终返回忙 | 触发后等待是否足够、状态字节 bit7 是否正确判断 |
| AHT20 数值明显异常 | 6 字节顺序、20 bit 拼接、强制类型转换和换算公式 |
| `_IT`/`_DMA` 启动后数据全为 0 | 是否在完成回调前就解析了接收缓冲区 |
| 状态机停在 `TX_BUSY`/`RX_BUSY` | I2C event/error IRQ、回调实例判断、HAL 错误码 |
| 非阻塞发送偶发乱码 | 发送数组是否为生命周期不足的普通局部变量 |
| OLED 完全不亮 | VCC/GND、地址 `0x3C/0x3D`、控制字节、初始化序列 |
| 通信成功但画面不对 | `0x00/0x40` 是否用反、页寻址/列寻址配置、是否漏掉 `OLED_ShowFrame()` |
| 只在 `100 kHz` 稳定 | 上拉阻值、线长、总线电容、供电噪声、模块板载电阻 |
| 读状态始终失败 | 模块可能主要支持写入，读能力要以控制器和模块电路为准 |

建议按下面顺序排查：

1. 断电检查接线、供电和共地。
2. 确认上拉电阻存在且阻值合理。
3. 把速度先降到 `100 kHz`。
4. 用 `HAL_I2C_IsDeviceReady()` 或地址探测确认从机是否响应。
5. 看 HAL 返回值和 `HAL_I2C_GetError()`，不要只盯着最终数值或屏幕。
6. 非阻塞流程逐个观察状态、启动返回值和完成回调。
7. AHT20 再查状态位、等待时间、字节拼接和换算公式。
8. OLED 再查控制字节、初始化命令、显存布局和 `OLED_ShowFrame()`。
9. 最后才去怀疑更细的控制器差异和时序边界。

如果总线被卡死（SCL/SDA 长期为低，`_IsDeviceReady()` 一直 `HAL_BUSY`/`HAL_TIMEOUT`），可以对 I2C 外设做一次软件复位，而不是反复断电：

```c
HAL_I2C_DeInit(&hi2c1);
__HAL_I2C_RESET_HANDLE_STATE(&hi2c1);
HAL_I2C_Init(&hi2c1);
```

注意：总线上若有从机自己拉低 SCL/SDA，软件复位主机并不能救回总线，仍要先断电定位是哪个设备在占线。

## 20. 速记与自测

### 20.1 一页速记

- I2C 只有两条线：`SCL` 传时钟，`SDA` 传数据。
- 两条线都使用开漏，靠上拉电阻获得高电平。
- 任意设备拉低，总线就是低电平，这就是逻辑线与。
- `SCL` 高电平期间，`SDA` 下降是起始，`SDA` 上升是停止。
- 地址字节里，前 7 位是从机地址，最低位是 `R/W`。
- AHT20 的 7 位地址为 `0x38`，HAL 常用参数为 `0x70`。
- AHT20 每次测量遵循“发送命令 -> 等待 -> 读取 6 字节 -> 检查状态 -> 换算”。
- `_IT` 和 `_DMA` 只负责启动，必须等完成回调后才能解析缓冲区。
- 状态机把发送、等待、接收和解析拆成有前置条件的步骤。
- HAL 里常传左移后的地址，所以 SSD1306 常见 `0x3C` 会写成 `0x78`。
- `HAL_I2C_Mem_Read/Write()` 更适合寄存器型从机，`HAL_I2C_Master_Transmit()` 更适合 OLED 这类直接发命令流的场景。
- SSD1306 常见控制字节：`0x00` 表示命令，`0x40` 表示显示数据。
- 采用显存模型的驱动里，画图只改缓冲区，真正显示必须 `OLED_ShowFrame()`。
- OLED I2C 整帧刷新有带宽成本，不能把它当成无限高速显示接口。
